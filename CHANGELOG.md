# Changelog

All notable changes to Monolith are documented in this file.

## [1.0.8] - 2026-09-02

### Fixed
- **A negative fitted nugget could win the variogram candidate search and silently blank a locality.** The robust fit tries four model families from four starting ranges and keeps the eligible candidate with the lowest weighted-least-squares error. Eligibility tested convergence and the practical range, but not the sign of the nugget, and a convex empirical variogram can drive `fit.variogram` to a negative <i>C<sub>0</sub></i>. Such a model makes <i>&gamma;(h)</i> negative near the origin: it is not conditionally negative definite, and the kriging system built from it has no solution. `gstat::krige()` does not raise there - it returns an undefined prediction at every location - so the run completed, the locality was stored, and the user was shown a blank map and an all-NA metrics row behind a variogram panel reporting a clean converged fit. Non-negativity is now part of eligibility, checked before any error comparison, so an invalid model cannot be compared on fit quality at all. Verified inert on 120 of 120 healthy fields: no run that currently produces a surface changes by any amount. The affected case turns from a blank map into a valid, amber-flagged fit. Scientific Guide §4.1.
- **An entirely undefined surface was stored and reported as a completed locality.** The layer above the variogram search accepted whatever the engine returned: a non-NULL result whose predictions were all NA passed through the rasterize / mask / project chain without complaint, so the locality reached the map, the Area Coverage table and the metrics table as a finished run made of nothing. Both the actual and the predicted surface are now tested for a fully undefined prediction column before they are stored, and the locality is skipped with a warning naming the likely cause (an invalid variogram model or a singular kriging matrix) in the progress panel and as a `[WARN]` line in the Run Log. This is the layer that should have caught the negative-nugget defect above, and it will catch the next one.
- **Ordinary Kriging had no failure path of its own.** RK, RFK and CK each route their own engine failure into a named Ordinary Kriging fallback; OK, the fallback itself, had nothing. A zero-nugget model over near-coincident samples makes the covariance matrix singular, and again `gstat` answers with NA at every location rather than raising: measured on gstat 2.1.5, forty points containing eight pairs 11 mm apart under a zero-nugget Gaussian model return 100% NA. The 2-decimal coordinate dedup removes exact co-location, not points a centimetre apart, and the robust fit produces a zero nugget routinely, so the locality simply vanished from the map with nothing said. OK now retries once with a micro-nugget of 1e-6 of the sill - far below any measurable signal - and says so in the warning file and the Run Log. The retry is gated on an already-empty surface, so it is numerically inert on every run that works.
- **Co-Kriging fitted a coregionalization range it had already computed and thrown away.** A linear model of coregionalization needs one range shared by every direct and cross variogram, so `fit.lmc()` runs with `fit.ranges = FALSE` - which makes the *seed* range the *final* range of the whole system. The seed was half the variogram cutoff, i.e. a quarter of the bounding-box diagonal: a property of the sampling extent, unrelated to the data's spatial structure. The range that weighted least squares had fitted to the primary variable's own variogram was in hand one line earlier and discarded apart from its model family. The LMC is now seeded with that fitted range, carrying its Matern smoothness with it (gstat's <i>a</i> only means a ground distance once the family and &nu; are fixed, and `vgm()` defaults &nu; to 0.5 while the robust fit uses 1.5, so seeding "Mat" without kappa would have stretched the correlation length silently). The extent heuristic remains as the fallback for when the primary fit is itself a heuristic or returns no usable range, and the Run Log now states which of the two was used. **Every CK surface and its CV metrics move**: measured on a short-range fixture (fitted <i>a</i> = 243 m against the heuristic's 685 m) the surface shifted by up to 18% of the field's standard deviation. A CK map produced before this release will not reproduce; re-run it. Scientific Guide §1.4, which now also states plainly that the LMC fits sills only and holds one common range - true before and after, and undocumented either way.
- **Lin's CCC used sample moments where it is defined on population moments.** The variance and covariance terms carried the <i>(n-1)</i> divisor while the squared bias term <i>(&mu;<sub>x</sub> - &mu;<sub>y</sub>)<sup>2</sup></i> in the same denominator is a population quantity. Mixing the two is a different statistic, and it is optimistic in exactly the place CCC exists to be strict: it discounts the systematic offset. Each moment is now scaled by <i>(n-1)/n</i>, reproducing `DescTools::CCC` to 1e-10. The excess is bounded by roughly 1/n: measured +0.66% at n = 12, +0.17% at n = 30, and under 0.1% at the reference dataset's n = 632. **Every reported CCC drops slightly**, most visibly on small localities. The known-answer fixture was re-derived externally to full precision (the recorded 0.9937 was wrong in the fourth decimal) and its tolerance tightened from 0.01 to 1e-5, which is what makes the two definitions distinguishable in the suite at all. Scientific Guide §5.
- **The classification area table was planimetric while every other hectare figure in the app is ellipsoidal, and the comment beside it claimed they matched.** Per-class areas were counted cells times cell area, which is area *in the projection plane*; the interpolation Area Coverage table and the class-zone GIS export both call `terra::expanse`, which measures ground area on the ellipsoid. The two differ by the CRS's area scale factor <i>k</i><sup>2</sup>: measured -0.08% on a UTM central meridian and +0.19% at a zone edge. Small, systematic, and in a column labelled hectares on the ground. The classification table now uses the same `expanse` call as the other two, matching on the class label (the classified raster is categorical, so `byValue = TRUE` reports labels rather than integer ids) and falling back to the planimetric figure only if `expanse` cannot be evaluated. **The displayed hectares move by roughly 0.1%**, in the direction of agreeing with the rest of the app. Scientific Guide §10.3.
- **Moran's I ignored the full-precision request in cross-validation output.** Every other metric in `perform_cv` passes through the rounding closure that honours `round_values`; the three residual-Moran fields called `round()` directly. Harmless today, because the only caller that asks for full precision also switches Moran off, but the two arguments are independent and a future caller combining them would have received a silent mix of rounded and raw values. No current number changes.

### Changed
- **CARTO's Positron and Dark Matter basemaps now take an API key.** CARTO has made a key mandatory for its raster basemaps and stamps an "API key required" watermark across the tiles of any request that arrives without one. Selecting either entry - both now labelled **(key)** and placed last in the basemap dropdown, since they are the only two that need anything - opens a **CARTO API key** box beside the dropdown; the map reloads with the key as soon as typing settles, on the Map Viewer, both comparison panels and the Data Setup validation mini-map at once. `leaflet-providers`' CartoDB entry has nowhere to put a key, so a keyed layer is issued as a plain tile layer built from CARTO's own URL template, with the key percent-encoded into the query string; the layer id, stacking level, subdomains, attribution and both zoom limits are set identically on the keyed and unkeyed paths, so a keyed CARTO basemap is interchangeable with every other one. Without a key the tiles still draw, watermarked, rather than leaving a blank map. The key lives in the session only: it is never written into a run configuration, an export or the run history.
- **Satellite (Esri) is now the default basemap everywhere.** It was already the dropdown's initial value, but activating a theme overwrote it, and seven of the ten themes named a CARTO layer - so most of the app came up on a basemap that is now watermarked, with nothing on screen explaining why. Every theme names the satellite layer instead; the per-theme setting is kept so a future theme can still choose its own. The fallback used when no basemap has been chosen moves from Positron to Esri for the same reason, and the Data Setup CRS locator - a world map read for country outlines, which satellite imagery does not draw - is pinned to Standard Street rather than following the switcher.

### Performance
- **The prediction grid no longer materialises the whole bounding box before clipping it.** Every bounding-box cell was converted to an `sf` point cloud and only then tested against the locality boundary. An `sfc_POINT` stores each node as its own classed `numeric(2)`, about 430 bytes per cell against 16 for a matrix row: measured, a 1-million-cell box costs 427 MB as an `sf` object and 848 MB of peak memory to build, and the Fixed-mode cap of about 4 million cells extrapolates to roughly 1.7 GB - per locality, inside a nested parallel worker, with up to `availableCores() - 1` of them live, and around three times that again for RK/RFK once the covariate grid and the result frame exist. All of it was spent on cells about to be discarded: for a concave, wrapped or multi-part boundary the bounding box routinely holds 1.5-3x the cells that survive. Cell centres are now taken as a plain matrix and converted a block at a time, each block tested against the boundary as it is built and only the survivors kept, so peak memory is one block plus the result. Same predicate, same surviving rows, same order, same columns; the suite asserts the clipped surface is identical at a deliberately tiny block size.
- **Random Forest Kriging no longer re-centres the in-bag matrix once per grid block.** The centring depends only on the fitted forest, not on the block being predicted, but the infinitesimal-jackknife variance recomputed it on every call - fifty times over a 1-million-cell grid at 200 trees. It is computed once and reused. Bit-identical output.
- **Sample-spacing detection no longer infers a failed reprojection from deep object equality.** `calc_metric_spacing` decided whether its transform to Web Mercator had succeeded by comparing the whole transformed point set against the original with `identical()`, tying a numeric scaling decision to sf's internal representation and comparing two large objects to answer a yes/no question. The handler sets a flag instead. No behavioural change.

### Testing
- Extended `test-robust-vgm-fit.R` with the nugget sign screen: a candidate set containing a negative-nugget model driven directly through the eligibility test, and the shipped fit never returning one on a real empirical variogram.
- Extended `test-interpolation-pipeline.R` with the OK micro-nugget retry (the near-coincident fixture returning 100% NA before the retry and 0% after, and a healthy run left untouched), and with the boundary-clip block size: the same concave-boundary run at the shipped block size and at seven cells per block producing identical rasters.
- Extended `test-cv-metrics.R` and the shared CCC fixture with the population-moment definition, re-derived externally to ten significant figures and asserted at 1e-5 - tight enough to separate the two definitions, which the previous 0.01 tolerance was not.
- Extended `test-classification.R` with the ellipsoidal area convention, asserting the cell-count correspondence under a tolerance rather than as exact equality.
- Extended `test-styled-points.R` with the CARTO API key: the keyed URL for both variants, a keyed layer keeping the same layer id, stacking level, subdomains, attribution and zoom terms as the provider path, an absent, empty, blank or `NA` key falling back to the unkeyed provider, the key ignored by every non-CARTO provider, percent-encoding of a key containing reserved characters, and the empty-provider fallback moving to the satellite layer.
- Full suite: 2313 passing, 0 failing, 0 skipped, across 32 test files (up from 2265 at 1.0.7).

## [1.0.7] - 2026-08-25

### Fixed
- **Switching the basemap wiped the interpolated surface, or left a grey rectangle.** The Map Viewer's basemap dropdown swaps tiles on the live widget through a Leaflet proxy, which appends the new layer last. `addRasterImage` does not use an image overlay: it paints the surface as a canvas tile layer, so the interpolated raster and the basemap are siblings in the same Leaflet tile pane on the same default stacking level, and only insertion order kept the surface on top - an order that holds when the map is first built (basemap first, rasters after) and inverts on every swap, so the new basemap painted straight over the result. The previous workaround pushed the swapped-in basemap to a negative stacking level, which put it behind the tile pane's own painted ground in some browsers and answered a basemap switch with a bare grey map instead. Both maps and the Data Setup mini-map now add their tiles through one helper (`add_base_tiles()`) that pins the basemap one level below the rasters, so the widget build and the proxy swap stack identically and the choice is explicit rather than incidental. The same helper fixes a second defect in the swap: the five providers publish to different maximum zooms (Topographic 17, Satellite 19, CartoDB 20), and adding a shallower layer to a map already zoomed past its limit dropped the map's zoom permanently, since switching back to a deeper provider never raised it again. Each provider's depth is now declared as `maxNativeZoom` against a common maximum of 20, so all five cover the same zoom range and the shallower ones upscale their deepest tiles instead of forcing the map out. No numeric result, export or model output is affected.
- **A fine Fixed resolution could exhaust memory during a Random Forest Kriging run.** The trend surface was predicted with `predict.all = TRUE`, which materialises one `grid cells x trees` double matrix in a single allocation: at the Fixed-resolution cap of roughly 4 million cells and 200 trees that is about 6.4 GB, requested inside a nested parallel worker, so the failure reached the user only as the generic "Parallel Interpolation Failed" dialog with nothing pointing at grid size. The grid is now predicted in row blocks of about 4 million matrix cells (~32 MB) each. A random forest predicts every row independently and both uncertainty estimators (infinitesimal jackknife and ensemble spread) are row-independent, so the prediction and variance surfaces are bit-identical to the previous implementation, which the suite now asserts by running the same model at a deliberately tiny block size.
- **Cancelling a run and immediately starting another let the cancelled workers run to completion.** The cancellation flag was one file per session, and starting a run cleared it; workers only read it at their checkpoints, so a locality still inside a kriging or forest fit when the next run began never saw the cancellation and kept computing alongside the new batch on a second set of nested workers. Results were never affected (a stale run's output is discarded by the run token), but the machine carried two full interpolation batches and the retry was slower than the run it replaced. Each run now carries its own flag, so clearing one cannot revoke another.
- **One unwritable table no longer aborts an entire batch export.** The worksheet loop ran unguarded while the figure loop beside it already logged failures per item, so a single registry item whose label reduced to an empty worksheet name (which `openxlsx` rejects) threw out of the download handler: the browser landed on a dead URL, every other selected asset including all figures was lost, and the scratch directory leaked. Sheet names now fall back to the registry id and then to a positional name, each worksheet is written under its own error handler that records the failure in the Run Log, and the workbook is only added to the zip when it holds at least one sheet.
- **The Input Data CRS plausibility guard could replace itself with a Shiny error page.** The guard measured the mapped X/Y columns without coercing them, while the X/Y selectors offer every column in the table and fall back to the first one when no column name matches a coordinate token. On a file with columns such as `POINT_X` / `X_coord` the first column is often a character site identifier, and choosing a CRS then raised an uncaught "non-numeric argument to mathematical function" instead of the guidance the guard exists to give. The columns are now coerced exactly as the two CRS-identification observers beside it already do, and a mapping with no numeric coordinates is reported by name.
- **Repeated cross-validation reported the rounding lattice as fold variance.** The opt-in repeated-CV table takes the mean and standard deviation of each metric across alternative fold realizations, but it aggregated values `perform_cv` had already rounded for display: RPD, RPIQ, NRMSE and SMAPE to two decimals, RMSE, ME, MAE, R², NSE and CCC to four. The mean is barely affected; the SD is not. RPD across ten repeats can only land on a 0.01 lattice, so a genuinely stable metric reported spurious spread or a genuinely variable one reported exactly zero, and for a target that is small in absolute terms (a fraction on 0-1, carbon in kg/kg) the four-decimal rounding *is* the signal. Reporting fold-assignment variance honestly is the entire purpose of the feature. `perform_cv` and `augment_metrics` now take a `round_values` flag and the repeat aggregation passes full precision; the display layer already formats, so the only column that moves is the ± term. **The reference single-realization path is untouched**, so no number in the main Model Performance table changes.
- **The classification covariate-lift significance test used the chi-square approximation where it is least reliable, and called it exact.** `stats::mcnemar.test` is the continuity-corrected chi-square approximation to the binomial, not an exact test; the two descriptions are mutually exclusive, since an exact test needs no continuity correction. The approximation degrades when the discordant total is small, which is the common case here: that total counts only the samples where the covariate model and the spatial nearest-neighbour baseline disagree in correctness, and a well-separated classification on a few hundred points routinely lands under 25. Below that threshold the panel now reports the exact binomial McNemar test and above it the corrected chi-square (Edwards' usual switch point). The p-value shown for the "do the covariates buy anything over spatial position" verdict can therefore change on small discordant tallies, in the direction of correctness. Scientific Guide §10.6.
- **The Regression Kriging trend table presented OLS inference without saying what it assumes.** The panel reports standard errors, t statistics, p-values, t-based confidence intervals and an F test straight from the linear model, all of which assume independent residuals; RK kriges those residuals precisely because they are spatially autocorrelated, which is the condition that voids the assumption. Positive residual autocorrelation lowers the effective sample size, biases the standard errors downward and makes the p-values anti-conservative, so a reader over-declares covariate significance. The app already computes the evidence (residual Moran's I with its expectation) but never connected the two panels. The trend panel now carries the caveat in place and points at the Moran columns as the severity gauge, and both guides state it. **The estimator is deliberately unchanged** — a GLS refit of the trend under the fitted residual variogram, iterated to convergence, is Universal Kriging, a different method — so no coefficient, fit statistic or prediction moves. Scientific Guide §1.2, User Guide 3.
- **The Map Viewer's raster image layers are now retired by count, instead of depending on a full re-render to clear them.** Each surface is added under a positional Leaflet id (`rast_img_1`, `rast_img_2`, ...) and re-added on every restyle. Leaflet replaces a layer whose id matches but never drops one the new pass does not re-add, so a pass that painted fewer images than the one before it left the surplus on the map. Two ways the number could shrink were already in the code: the residual view builds its layer list separately from the raster list and the two need not be the same length, and every branch skips a locality whose raster fails to project for display, which under ids derived from the loop index also left a *hole* in the sequence (ids 1 and 3 for three localities), so the ids no longer described what the map carried. No visible symptom was reproduced, because a new run re-renders the whole widget and that destroys the Leaflet map along with any stale image; the in-place restyle path was relying on that. Each map now records how many images it carries, on the full-render path as well as the proxy one, and the ids are handed out as the images are actually added, so the surplus is removed explicitly rather than accidentally. Display only: no value, surface or metric is affected.
- **Internal, no user-visible change:** the run's tree count (`rf_ntree`) is now forwarded from the dispatcher through the regional driver into the kriging engine instead of relying on the engine's own identical fallback, so the value recorded in the run configuration and the value the forest is grown with cannot drift apart; the Scientific Guide's claim that the count comes from a user-set **RF Trees** control was removed, since no such control exists and the count is pinned at 200; and the per-session progress directory is now removed when the session ends, rather than accumulating one empty directory per visitor for the lifetime of the R process.

### Removed
- **The dead lattice/trellis rendering path, and the two packages that existed only for it.** Nothing in the application has built a `trellis` object since the variogram plots moved to `ggplot2`: both remaining branches were unreachable, one in the plot-export writer and one in the Export Styler's dispatcher. The export branch also opened a graphics device, printed and closed it with no `on.exit`, so a failure inside `print()` left the device open for the rest of the session. `automap` and `latticeExtra` are dropped from the dependency list with them (60 CRAN packages, from 62); neither was called anywhere, and removing them also retires `reshape`, `plyr` and `interp` from `renv.lock`, which no remaining package requires. The run-configuration JSON's software provenance accordingly records `sf`, `gstat`, `fields`, `randomForest` and `terra`: it names the packages that computed the surface, and `automap` never took part. No numeric result changes.

### Changed
- **The IDW power search now honours the selected Cross-Validation Strategy.** Every other cross-validation in the app routes through one fold authority, which reads the sidebar strategy and applies the same small-*n* degradations. The power optimizer did not: it hardcoded five folds above fifty observations with its own seed. Two things followed. The fold *count* differed from the plan the metrics use, and, more seriously, a user who selected **Spatial Block CV** still had the power chosen on a random split. Under spatial autocorrelation a random split leaves each held-out point's near neighbours in the training set, which systematically favours a steeper distance decay, so the surface was built with a power tuned for near-neighbour prediction while the Model Performance table scored it under block holdout: the two halves of one run disagreed about what validation meant. Both now share a single design. **This can change the selected power, and with it the IDW surface**, so an IDW map exported before this release will not necessarily reproduce; re-run the optimizer and record the new power. It also makes the strategy selector the one control that reaches an interpolated map, which the sidebar tooltip and both guides now state. Scientific Guide §4.2 and §5, User Guide 1.b.

### Testing
- Extended `test-idw-optimization.R` with the shared fold authority: the search reproduced against a hand-built `krige.cv` scan over `make_cv_folds` folds under all three strategies, the resolved plan's fold counts (10 random, n LOOCV, 10 blocks at n = 60), the caller's RNG stream left untouched, the default matching the auto plan, and the non-finite fallback returning the documented power of 2.0; `test-interpolation-pipeline.R` with `idw_opt_item` forwarding the strategy to the search over the same deduplicated point set.
- Extended `test-cv-metrics.R` with the metric-rounding flag: `perform_cv` and `augment_metrics` returning full precision under `round_values = FALSE` while the default is bit-identical to before, and `summarise_cv_repeats` recovering the exact SD of three realizations separated by less than the display lattice, where aggregating the rounded values reports zero spread.
- Extended `test-classification.R` with the McNemar switch point: the exact binomial below 25 discordant pairs, the continuity-corrected chi-square at 25, and the two forms disagreeing in that regime.
- Extended `test-styled-points.R` with the Map Viewer's raster image ids: a restyle that paints fewer images than the previous pass retires exactly the ids it did not re-add and none of the ids it did, the surplus is retired in order, and a first render or a longer run issues no removal. The two `test-export-plot.R` trellis cases were removed with the branch they covered.
- Full suite: 2265 passing, 0 failing, 0 skipped, across 32 test files (up from 1863 at 1.0.6).

## [1.0.6] - 2026-08-17

### Added
- **A distance ruler on every Map Viewer map.** The measure control sits in the bottom-left corner of each interactive map and is present on both panels of the comparison and residual views, so the same feature can be measured on the Actual and the Predicted surface without switching views. Click the ruler, place the vertices of a path, and the result appears in that measurement's own pop-up, on the shape itself and reopened whenever it is clicked, reporting length on two explicitly named bases: the **ground** distance as a geodesic on the WGS84 ellipsoid (computed with `terra`, which uses GeographicLib), and the **projected** distance in the Target Mapping CRS. The second is the one that answers "how does this compare with the variogram range", because lags, IDW separation distances, TPS coordinates, grid resolution and buffer radii are all lengths in that system; the first is the real distance over the ground, independent of the projection. Reporting both makes the projection's distance distortion visible instead of leaving the reader to assume there is none: inside a UTM zone the two agree to a few thousandths of a percent, and a wide gap means the selected CRS suits the area poorly, which affects every lag the variogram was fitted on. A path of three or more vertices closes into a ring: it reports the enclosed area on the same two bases, the ellipsoidal one through the same `terra::expanse` call the class-zone export and the Area Coverage table use, and its length becomes the **perimeter** of exactly that ring, closing segment included, so the two figures describe one shape instead of an area and the open path leading into it. A **geographic** Target Mapping CRS produces the ground figure only, for the same reason the app refuses to interpolate in degrees. The measure control computes on a sphere of radius 6371000 m (up to ~0.5% from the ellipsoid in length, and it knows nothing of the analysis CRS), so its finished text is **replaced** by the figures recomputed in R and stored with the shape: one set of numbers per measurement, still correct when a measurement made earlier is clicked again, where a single box in a corner could only ever hold the newest. The pop-up keeps Center on this / Delete links for its own shape. Read-only throughout: measurements are not stored, not exported and enter no model, and a measurement stays until it is deleted or the map is redrawn. Uses the measure plugin bundled with `leaflet` itself, so no new package and no external asset; its control is restyled to the size of the drawing toolbar above it (the plugin ships a button half again as wide), and its panel is trimmed to what the map cannot already show, dropping the heading that repeats the button's own tooltip and the running latitude/longitude readout, and reducing Cancel and Finish to the cross and tick icons the plugin already draws, with accessible names attached since hidden text is not one. The control is lifted clear of the tile attribution, whose height it measures on render and again on every resize or basemap change: a wordy credit line (Esri's imagery attribution) wraps to two or three lines along the foot of the map and otherwise hides the button and its panel behind it. Scientific Guide §3.5, User Guide 1.6.
- **GeoTIFF export for interpolation surfaces.** The Export Styler's format list gains **GeoTIFF (data)**, offered for every registry item that is a single raster surface: the Actual and Predicted maps, the residual Delta map, the Interpolated Point Errors map, the four variance and standard-error surfaces, and Quick Exports of those views. It writes the values, coordinate reference system and extent exactly as computed, in the run's projected analysis CRS, with kriging surfaces written as multi-band files (band 1 prediction, band 2 variance) keeping the layer names as band descriptions. Because a GeoTIFF is the data rather than a rendering of it, every styling control switches off while it is selected (typography, palette, DPI, dimensions and the preview), with a note saying why. Two map items are not single rasters and remain image-only, and the styler now says so instead of leaving the user to guess: the **Actual vs Predicted Comparison** (a pair of surfaces) and the **Point Error Map** (point geometry). In a batch export, raster items honour the GeoTIFF choice and anything else in the same batch falls back to PNG, with a Run Log line naming each item that did. The former "TIFF" entry is relabelled **TIFF (image)**, since an image TIFF carries no georeferencing and the two were easy to confuse. User Guide, Export Registry §4-5.
- **Class zones export as a GIS vector layer.** A new **Export Class Zones** button on the Map Viewer toolbar writes the classified surface currently displayed as Shapefile, GeoJSON, KML or GeoPackage, sharing the format dropdown with the drawn-polygon export. One dissolved polygon per class, carrying the class label, its lower and upper break limits, its area in hectares, and which surface, variable and method produced it; the comparison view exports Actual and Predicted together, distinguished by a `surface` attribute. The zones are built from the same `terra::classify` call the map and the Area Coverage table make and their hectares come from the same `expanse` call, so an exported layer cannot disagree with what is on screen: polygon boundaries are cell boundaries, inheriting the grid resolution rather than being smoothed. Shapefile and GeoPackage keep the projected analysis CRS so a GIS works in the projection the areas were computed in; GeoJSON and KML are reprojected to WGS84 as those formats require. KML stores only a name and a description per placemark, so there the class label goes to the name and the full attribute record to the description, which keeps the export lossless in a format that has no attribute table; Shapefile and GeoPackage carry the fields as ordinary queryable columns. The outer breaks are ±Inf by construction and are written as NULL rather than a fabricated finite limit. Requires Agronomical or Binned styling; the button greys out whenever the export cannot be produced (no run yet, continuous styling, residual view) and names the blocking state on hover. Scientific Guide §9.5, User Guide, Map Viewer toolbar. The drawn-polygon button is relabelled **Export Drawn Polygons** and both now share one writer, so their format support cannot drift apart.
- **Repeated cross-validation (opt-in).** A **Repeated CV** checkbox in the Spatial Engine panel (off by default, hidden under Standard LOOCV) re-runs each engine's cross-validation under 3, 5 or 10 different fold assignments and adds a **Fold-Realization Stability** table to the Scientific Analysis tab, reporting every displayed error metric as *mean ± SD* across realizations. A k-fold score is one realization of a random partition, and at moderate sample sizes the spread across alternative splits can be as large as the difference between two interpolation methods: the SD is the resolution of that comparison. **No existing number moves:** realization 1 keeps the fixed seed and *is* the reference run, so the Model Performance table, the residual maps and the interpolated surface are identical whether the option is on or off, and a repeat varies the fold assignment only (data, variogram policy, neighbourhood and all model-fitting seeds are held fixed). Deterministic leave-one-out plans (Standard LOOCV, Auto at n ≤ 50, Spatial Block below n = 30) contribute a single realization and say so in the Run Log; in the pooled Total (Combined) rows they are carried unchanged into every repeat. Costs one full extra cross-validation pass per realization (roughly 5× the CV time at 5 repeats for RK/RFK, which refit the variogram in every fold); the per-locality progress bar now moves through the repeats and a cancellation is honoured between them. The realization count is recorded in the run configuration and its JSON export. Works across all five engines and both surfaces. Scientific Guide §9.1, User Guide 1.b.
- **North arrow and metric scale bar on the Data Setup mini-map.** The validation mini-map now draws a north arrow (top-left) and a metric scale bar (bottom-left). Both are permanent rather than toggled: this map exists to be checked against reality before any modelling starts, and the Map Viewer's checkboxes are there because those maps are exported, which this one is not. - **Strict Measured boundaries now warn when the buffer is too narrow for the grid.** A raster cell is kept only when its **centre** falls inside the boundary, and under Strict Measured the boundary is the union of buffer circles around the samples, so a buffer below half a cell diagonal (resolution ÷ √2) discards the cell a sample sits in. - **The ruler labelled its projected figure with the sidebar's current CRS, not the one the displayed run was computed in.** Everything else in the Map Viewer reads the snapshot committed at dispatch, so reconfiguring the sidebar for the next run cannot alter what is on screen. The ruler alone read the live selection, so changing the Target Mapping CRS after a run relabelled every measurement on that run's surface with a system it was never computed in. The committed CRS now travels in the run snapshot and the ruler names that one, falling back to the live selection only before a first run has committed anything.
- **A measurement whose path crossed itself reported an area that was not the area drawn.** Both engines evaluate a ring's area as the shoelace sum, and on a figure-eight the two lobes carry opposite orientation, so the sum returns their *difference*: a symmetric bowtie reported approximately zero hectares for a visibly enclosed shape, and an asymmetric one reported the larger lobe minus the smaller. Such a ring now reports its perimeter, which the crossing does not affect and which stays exact, and the pop-up says why no area accompanies it. The crossing test is combinatorial on the clicked vertices, counting only proper crossings, so it is a property of the shape alone rather than of the analysis CRS or of the `s2` setting.
- **Both guides understated how far the ruler's two bases normally sit apart.** "A few thousandths of a percent" describes only the neighbourhood of the line where the point scale factor is 1. Measured across UTM zone 36N at 39°N, the projected length runs -0.040% against the ground figure on the central meridian, passes through zero about 1.6° from it and reaches +0.039% at the zone edge, approaching 0.1% where the zone is widest near the equator, with the area gap twice that because it scales as k². A perfectly ordinary central-meridian run therefore read as the "visible gap" the same paragraph tells the reader to treat as a CRS-fit problem. Corrected alongside it: the measure plugin's spherical area was given as departing from the ellipsoid "of order 0.1%", which holds near 35° latitude but follows R²/(MN) and so grows to about +0.45% at the equator and -0.9% towards the poles; and the User Guide promised a ruler on "every interactive map" when the Data Setup mini-map has none. Duncan's is now labelled **(liberal)**, since it controls the comparison-wise and not the family-wise error rate; Tukey's HSD remains the conservative default. Scientific Guide §8.6.
- **Cross-validation is not symmetric across engines, and the app now says so.** RK and RFK refit the trend and the residual variogram inside every fold, while OK, CK and IDW reuse a model fitted on the full point set, which makes their metrics mildly optimistic relative to RK/RFK on the same data. The Scientific Guide previously claimed all kriging engines refit; §5 is corrected and the Model Performance panel carries a footnote when an affected engine is displayed. Documentation only — no metric changed, and an opt-in strict-CV mode is left for a later version.
- **NRMSE is normalised by the absolute mean.** A negative-mean variable (centred anomalies, sub-zero temperatures, redox potentials) reported a *negative* NRMSE%, a meaningless sign for a normalised error, because the denominator kept the mean's sign. Every positive-mean variable — all typical soil data — is byte-identical; only the previously wrong-signed case moves. Scientific Guide §5 now defines the metric.
- **A boundary that encloses no grid node skips the locality with a named warning.** A coarse fixed resolution over a tight boundary (easiest to hit with a small Strict Point Buffer) used to interpolate the full bounding box and then mask every cell away — a blank locality with no message, after paying for the whole computation. The run now records the cause in the run warnings and log and skips that locality, matching the Classification Suite's existing loud failure in the same situation.
- **An interpolation run and an optimizer can no longer run concurrently.** Each dispatch spawns its own nested worker cluster sized to most of the machine's cores, so starting one while the other worked oversubscribed the CPU roughly two-fold; either direction now raises a notification asking to wait. Results were never affected (numerics are plan-independent) — this is resource protection for the single-user desktops the app targets.
- **Empty states in the Descriptive Suite's tables say why they are empty.** The group-statistics and correlation tables returned NULL when there was nothing to show (no rows in the active groups, fewer than two variables, controls that could not be partialled out, an uncomputable cross-correlogram), which both breaks the app-wide "never hand a widget output NULL" rule and hides the reason; each case now renders a one-row message naming it.

### Added
- **Spatial Cross-Correlogram** (Descriptive & Exploratory suite, Correlation Analysis tab): cross-correlation between two variables as a function of the **ground distance** separating sample points, binned exactly as the app's variograms are. With both variables standardised, the plotted value is `rho(h) = r - gamma12(h)` — the standardised cross-covariance derived from the empirical cross variogram — so a curve decaying from the ordinary correlation (drawn as a dashed reference) toward zero shows the scale over which the two variables genuinely co-vary, which is the co-regionalisation Co-Kriging exploits. Point size encodes pairs per bin and bins under 30 pairs are greyed as unreliable; `Spearman`/`Kendall` produce the rank-based version, labelled as such. Coordinates are projected to metres first, so the panel requires the confirmed X/Y mapping and shows an explanatory note until then. **Replaces the "Lagged CCF" panel** (see Fixed). - **Directional Variogram (Anisotropy Check) panel** (Tab 3, all engines): semivariance recomputed within four angular cones — 0°/45°/90°/135° clockwise from north, 22.5° half-angle — instead of pooling every point pair regardless of orientation, which is what the fitted variograms do. ### Fixed
- **Classification runs crashed with "numbers of columns of arguments do not match" whenever a fold's training rows lacked a class**: spatial cross-validation folds are geographic blocks and cannot be balanced by class, so a spatially clustered class can fall entirely inside one held-out block (class-stratified random folds have the same hole for a singleton class, which necessarily lands in exactly one fold). Fitted on data containing none of that class, `ranger` and `nnet::multinom` drop the unused outcome level and return one fewer probability column than the target has classes, so pooling the folds' predictions aborted and the whole run failed — the console showing the engine's "Dropped unused factor level(s) in dependent variable" warning just before. Absent classes are now padded with probability **0** — the fold model's genuine posterior for a class it never saw, not an imputed share — with the column order pinned to the trained level set, so the run completes and the pooled metrics cover every class. The affected classes are named in a warning when the run finishes, because their recall is pessimistic by construction: those held-out samples score as misses. Out-of-fold permutation importance is padded the same way (matching against a missing column previously turned every importance value `NA`). Scientific Guide §10.2.
- **Target classes containing no samples reached the model**: a binned target carries one level per interval, and an equal-interval or Jenks break on a skewed variable can enclose nothing (a level can also be emptied by discarding rows with missing covariate values). The empty class was carried into the fit, where it left yardstick's macro recall undefined — reporting **balanced accuracy as a silent `NA`** — added an all-zero row and column to the confusion matrix, collapsed class-stratified cross-validation to 2 folds (the smallest class count being zero), and, on runs that predict maps, aborted the surface stage with "Predicted probabilities are missing columns for class level(s)". Empty levels are now dropped once, before anything is fitted, so the modelled class set, the confusion matrix, the raster legend and the exported model bundle all agree. The class count behind the maps can therefore be lower than the "Number of classes" slider; the run summary reports how many classes were actually modelled.
- **Classification and Governing Factors runs warned about unsound random numbers on every run**: both background workers were dispatched without `future`'s `seed` argument, so each drew from a stream seeded by process entropy and `future` reported "UNRELIABLE VALUE: ... unexpectedly generated random numbers without specifying argument 'seed'". Both now receive a proper parallel-safe L'Ecuyer stream. No result changes: each worker's entry point re-seeds itself before drawing anything (the classification pipeline wraps every random step in its own two-sided sandbox, and the governing-factors routine opens with a fixed seed under the same convention) — confirmed for the latter by checking that its importance, ALE, PDP, SHAP and forest outputs are bit-identical under different starting random states. The interpolation pipeline already dispatched with a fixed seed and is unchanged. The classification run-progress poller also stopped emitting a "cannot open file ... stage_*.txt" warning on each tick before the worker writes its first stage line.
- **"Lagged CCF" measured lag in table rows, not in space** (the panel is replaced; see Added): the correlation suite's lagged cross-correlation called `stats::ccf`, where lag *k* means "*k* rows down the data frame". The rows of a soil point table are upload order, so the published curve changed if the file was sorted differently, and the ±1.96/√n bands it drew assume a stationary sequence — neither is defensible for cross-sectional spatial samples, while the Descriptive Guide advertised the panel for "spatial or sequential lag analysis". It is now a distance-binned **Spatial Cross-Correlogram**, which is invariant to row order by construction (pinned by a regression test that shuffles the input). Scientific Guide §8.4.
- **Spearman and Kendall partial correlations were not partial rank correlations** (changes the partial-correlation heatmap and table for those two methods; Pearson is unchanged): both the plot and the summary table residualised the **raw values** with a least-squares fit and then took a rank correlation of the residuals, while the p-values beside them were computed under `ppcor`'s conventions. A partial rank correlation is the product-moment partial correlation of **ranks**, so the ranks must be residualised, not the raw values. Spearman now rank-transforms every variable (targets and controls) before residualising, and Kendall — which has no residualisation analogue — takes its partial tau from the inverted Kendall tau matrix, reducing to the classical first-order partial tau for a single control. Both estimator and p-value now follow the same convention. The two code paths were also merged into one shared, tested routine, which incidentally fixes the heatmap failing outright when a variable's display label contained a space or bracket. Scientific Guide §8.3.
- **Variogram candidate screening compared ranges that are not comparable** (can change which model family wins in edge cases; most fits are unaffected): each fitted candidate must fall inside a sanity window before it is eligible, but the window was applied to gstat's range parameter *a*, which means a different ground distance in every family (the practical range is *a* for Spherical, 3*a* for Exponential, √3·*a* for Gaussian, ≈4.75·*a* for Matérn ν = 1.5). The window was therefore ~3× tighter at the low end for Exponential than for Spherical, and let an Exponential structure extending three times beyond the data pass at the top — so the pool of eligible candidates was shaped by family rather than by fit quality. The window is now applied to the practical range, i.e. to the same physical distance for every family. Scientific Guide §4.1.
- **PCA outlier panel now names its estimator**: the Mahalanobis distance plot is titled "Mahalanobis Distance (Classical Estimator)" and states that the classical mean/covariance is inflated by the outliers themselves, so a cluster of extreme observations can mask itself under the threshold. The mathematics is unchanged (and correct); the panel is a screening aid, and the caption now says so. Scientific Guide §8.2.
- **Out-of-fold feature importance leaked its shuffles into the cross-validation random stream** (changes reported metrics only for XGBoost at tuning depth **Full**; every other learner and depth is byte-identical): the permutation importance was computed inside the CV fold loop on the loop's own random stream, burning `reps x predictors` shuffle draws per fold, so every later fold's model was fitted from a different random state depending on whether importance had been requested. Learners that fit deterministically hid it (the multinomial model starts its weights at zero, Random Forest pins its engine seed, XGBoost does not subsample at depths None/Light), but at depth Full XGBoost tunes `sample_size` and `mtry` and therefore draws random row/column subsamples — so a purely diagnostic toggle could move accuracy, kappa, the confusion matrix and the per-class table. Each fold's importance now runs in its own seeded sandbox derived from the run seed and the fold index: the fold loop is identical either way for any learner, and each fold's importance is independently reproducible. Scientific Guide §10.8.
- **A hidden slider silently coarsened the Auto grid resolution** (changes the raster grid, exported GeoTIFFs and classified-area tables for Auto runs on datasets whose localities lie far apart): both resolution branches applied a floor of 10% of the manual `grid_res` slider. That slider is only shown in Fixed mode, and in Auto modes the app writes the **global** density recommendation into it, so a large bounding-box diagonal pushed the recommendation toward its 500 m ceiling and floored every compact locality's per-locality grid at ~50 m — a global-scale quantity overriding a per-locality one through a control the user could neither see nor set, with no message. Auto resolution is now self-contained (≈100,000 cells inside each locality's own boundary, clamped to [5, 1000] m) and the Fixed branch keeps an absolute 0.1 m sanity floor for values restored from a saved run configuration. Scientific Guide §2.5.
- **Failures while assembling results were reported as parallel modelling failures**: `promise %...>% success %...!% error` routes rejections from the success handler to the same error handler as the worker, so an error in raster merging, export registration, map fitting or the kappa tables opened the "Parallel Interpolation Failed" dialog, complete with troubleshooting advice about coordinate columns and collinear covariates — for a run whose models had all completed. The main-session assembly stage now has its own handler and its own **Results Assembly Failed** dialog, which states that the models finished and that maps/tables/exports may be incomplete, releases the run UI, and logs the cause. `%...!%` now genuinely means the parallel run itself failed.
- **Diagnostic panels went blank instead of naming the cause**: when RK or RFK falls back to Ordinary Kriging for a locality (a routine, already-logged event), that locality has no trend model, so the Trend Model Summary, RK coefficient table and RF Variable Importance panels rendered empty with the explanation available only in the run log. They now state that the locality's trend model was not fitted and point to the log. Two related honesty fixes ride along: after a fallback the stored per-locality variogram describes the **measured values**, not model residuals, so that panel is now titled "Variogram of Measured Values - Ordinary Kriging Fallback" instead of "Internal Residual Variogram"; and a Model Performance row whose cross-validation produced nothing is labelled "CV unavailable - see Run Log" instead of appearing as an unexplained row of blanks.
- **Constant covariates were reported to the user as a collinearity problem**: the multicollinearity engine drops zero-variance covariates and collinear ones into the same list, and every consumer labelled the whole list "High VIF (> 10)". A constant is not collinear with anything — it carries no information and is removed regardless of the user's Drop/Keep choice. The engine now returns the two causes separately, and the PCA collinearity table, the Classification Suite's covariate note and run-time modal, and the interpolation run log each name the actual reason.
- **Multicollinearity engine could not be called on an `sf` object** (latent; every in-app call site drops geometry first): `sf`'s geometry column is sticky under `[ , ]`, so the degenerate-covariate scan would have received an `sfc` (erroring in `is.finite()`) or, had it simplified instead, produced a mask one element longer than the covariate list and misaligned the pruning silently. The engine — which is worker-shared and publicly callable — now drops geometry itself.
- **Residual write-back guard could be satisfied by a stale global** (latent): the per-locality residual join tested `exists("res_a_list")` without `inherits = FALSE`, and since workers source the model code into their global environment the lookup walked up out of the function frame. The length check made real damage unlikely; the guard is now frame-local.

- **Co-Kriging cross-validation left the held-out point's covariates in the system** (changes CK's reported Model Performance metrics, honestly downward; the prediction surface and the LMC fit are untouched): `gstat.cv` defaults to removing only the primary variable per fold, so each held-out point was still supported by its own co-located covariate observations — an information regime the map never enjoys, since Monolith's covariates are co-sampled lab measurements that do not exist at grid prediction locations, and inconsistent with RK/RFK's leave-one-out, which removes full rows. CK cross-validation now removes the entire held-out row across all LMC variables (`remove.all = TRUE`). Scientific Guide §1.4.
- **IDW power and TPS lambda optimizers did not deduplicate co-located points** (changes the stored power / lambda only for datasets containing co-located samples; a no-op otherwise): the interpolation run fits on a coordinate-deduplicated point set (2-decimal precision in the projected CRS), and the variogram auto-fit preview deduplicates the same way, but the two optimizer buttons searched on the raw point set. A co-located twin predicts its held-out partner at distance zero — an exact hit for every candidate IDW power — inflating the power search, and exact replicates trigger `fields::Tps`'s pure-error handling, shifting the GCV curve. Both optimizers now deduplicate exactly as the run does, so the stored optimum comes from the same point set as the run that consumes it. Scientific Guide §4.2 / §4.3.
- **One failed locality dragged the global TPS lambda slider negative**: after "Optimize TPS Lambda", the slider is set to the mean of the per-locality optima, but a locality whose optimization failed contributed the internal −1 "Auto" sentinel to that mean — e.g. one success at 0.5 plus one failure yielded −0.25, silently flipping the global default to Auto. Failure sentinels are now excluded from the mean (per-locality stored values always took precedence at dispatch, so only the slider position and non-optimized localities were affected).
- **Maps could stay blank grey after the first run when the run finished on another tab** (display only, no numeric results affected): Leaflet refuses to draw into a zero-size container, stashing the layers in `pendingRenderData` and flushing them only when the widget is resized. Because the raster lists are cleared at dispatch, the view switcher offers only "View: Actual" during a run, so the comparison canvases are still hidden and have never been created; a run that produces predictions (typically CK/RK/RFK) then selects the comparison view at completion and those two widgets render for the very first time. If the Map Viewer tab was itself hidden at that moment (working in the Classification Suite while the run finished), both maps initialised at zero size and came up empty. The single 100 ms resize that was supposed to repair this raced the Bootstrap tab fade and the processing-overlay transition, and once missed it never fired again, so the maps stayed grey until a second run. Revealing the maps now pumps resize events until every visible canvas reports it has actually rendered (capped at ~3 s), and the same repair runs on returning to the Map Viewer tab and on switching view, so a canvas that initialised hidden recovers even without pressing Reveal Maps.
- **Moran's I duplicate-coordinate jitter could round away to nothing** (changes Moran's I only for datasets containing co-located points, far below the reported precision): duplicates are separated by a tiny seeded displacement before the k-nearest-neighbour graph is built, but the displacement was a fixed `1e-8` map units. At a UTM northing of ~4.5 × 10⁶ the gap between representable doubles is ~1 × 10⁻⁹, so `1e-8` is only about ten representable steps and demonstrably collides — six copies of one coordinate reduce to five distinct values. Surviving duplicates make `spdep` warn ("identical points found") and leave the neighbour definition ambiguous, and any further growth in coordinate magnitude would turn the jitter into a silent no-op. The displacement now scales with the data (1e-9 of the coordinate span, floored at 1e-12 of the coordinate magnitude and at the historical 1e-8), which stays orders of magnitude below any real sample spacing so the neighbour definition itself is unchanged. Scientific Guide §9.2.
- **Co-Kriging ignored the multicollinearity decision** (changes CK results when collinear covariates are present): the VIF threshold from the Auto-Drop / Keep All modal reached the run pipeline and was applied to RK/RFK, but `apply_CK()` had no gate at all — so "Auto-Drop and Continue" was a no-op for Co-Kriging and every collinear covariate was fed to `fit.lmc()`. Since near-singular coregionalization matrices are precisely what makes the LMC fit fail, this was a frequent (and silent) cause of the "LMC Fit Failed, falling back to Ordinary Kriging" path. CK now applies the same gate on the same point sets as RK/RFK, and the dropped covariates are named in the run log. CK is gated but builds no kriged covariate grids (it predicts the covariates jointly through the LMC), so no extra covariate surfaces are computed. Scientific Guide §8.1.
- **Classification final model was tuned under the wrong cross-validation** (changes Light/Full tuned results; **None** is byte-identical): the evaluation loop honoured the selected strategy (Spatial by default), but the final full-data fit hardcoded random class-stratified folds for its tuning search. The class map, the entropy surface, the permutation importance ranking and the exported `.rds` bundle were therefore all built from hyperparameters selected under exactly the near-neighbour leakage that spatial cross-validation exists to remove, while the metrics table reported a leakage-free estimate. The final fit now tunes under the run's own strategy. Scientific Guide §10.6.
- **Rank-deficient Regression Kriging returned silent `NA` metrics**: with more covariates than a fold's training rows can support, the per-fold `lm` aliased coefficients, predicted `NA`, and the NAs propagated through residual kriging into the reported metrics with nothing indicating a problem. Both the cross-validation folds and the main RK fit now check the rank requirement up front and report an explicit error naming the shortfall (points available vs. coefficients needed); a failing main fit routes the locality through the existing Ordinary Kriging fallback with the reason logged.
- **TPS crashed to the IDW fallback on a missing lambda**: the auto/manual lambda test read `tps_lam < 0` without an `is.na()` guard, so an `NA` lambda raised "missing value where TRUE/FALSE needed" inside the engine and silently sent the whole surface down the IDW fallback path. `NA` is now treated as unset, i.e. the documented Auto (GCV) default.
- **IDW power and TPS lambda optimizers searched in the upload's raw CRS** (changes the stored power / lambda only for datasets uploaded in a geographic, degree-based CRS; projected uploads are unaffected): the "Optimize IDW Factors" and "Optimize TPS Lambda" buttons built their point set directly in the mapping CRS and never projected, while the interpolation run they feed always works in a projected metre CRS. For a geographic upload the power search therefore selected neighbours and weighted distances in degrees, and the TPS unit-box normalization inherited a distorted longitude-versus-latitude aspect ratio, so the stored per-locality optimum disagreed with the run that consumed it (the app's own sibling variogram auto-fit already projected). Both optimizers now project to the local UTM zone first, so the optimum is invariant to whether the same points arrive in a geographic or a projected CRS. Scientific Guide §4.2 / §4.3.
- **Fixed grid resolution had no cell-count ceiling** (memory-safety guard; only fires in a pathological case, otherwise no change): in Fixed resolution mode the slider value was used verbatim, and the grid builder materializes every bounding-box cell before clipping to the boundary, so a very fine resolution over a large extent could allocate hundreds of millions of nodes and exhaust memory. Fixed mode now caps the candidate grid at roughly 4 million cells (matching the Classification Suite's grid guard), coarsening the resolution and recording a warning in the run log when the cap is reached; ordinary resolutions are used exactly as set, and the Auto modes were already bounded.
- **Residual (Delta) raster carried a meaningless variance band**: the Actual − Predicted difference was taken over the full raster stack, so when both surfaces carried a kriging-variance layer the exported residual GeoTIFF included a "difference of two kriging variances" band — not a quantity that exists. The difference is now taken on the prediction layers only. The in-app viewer was never affected (it selects the prediction layer explicitly); only the exported GeoTIFF changes, losing the spurious second band.
- **Run-time estimator could fit its ETA model on a partially filtered history**: the run-history error handler assigned `history_data <- NULL` *inside the handler's own frame*, leaving the outer variable untouched, so a throw partway through the filter chain (e.g. an older `run_history.csv` without a `cores_used` column) left the half-filtered frame in place and the ETA regression was fitted on it. The whole block is now the `tryCatch` value.
- **Two different metrics were both labelled "Bias"** with opposite signs: the interpolation Model Performance table reports **Bias (ME)** as *observed − predicted*, while the uploaded-ML-prediction tables report **MBE** as *predicted − observed*. Both read "Bias", so the same over-prediction appeared with opposite signs in two tables a reader would naturally compare. The second is now labelled **"MBE (ML pred - observed)"** in all three tables that show it. Label only, no values changed; the sign convention is spelled out in Scientific Guide §5.
- **Undefined validation metrics reported as infinity**: `augment_metrics()` had no zero-denominator guards, so constant observations gave `NSE = -Inf`, a zero-mean (centred / anomaly) variable gave `NRMSE = Inf`, and a perfect prediction gave `RPD = Inf` and `RPIQ = Inf`. Those values flowed straight into the Model Performance table, the exported metrics CSV, and the pooled Total (Combined) diagnostics, where an infinity reads as a real and spectacular score. All four now return NA, matching the convention CCC already followed; RPIQ's guard is also consistent with RPD's (it previously checked only the IQR term, not RMSE).
- **sMAPE was averaged over a different sample count than every other metric**: rows where the observation and prediction are both exactly zero produce 0/0, and `na.rm` silently dropped them. Harmless for concentration data, wrong for any variable that legitimately reaches zero (residual and anomaly surfaces). The 0/0 term is now defined as 0, the usual convention, so n is consistent across the table.
- **Global Performance Metrics export table could report infinity for a constant variable**: the pooled uploaded-ML-prediction table (Actual vs. ML-Predicted, exported as *Global Performance Metrics*) computed its R² (correlation) and R² (traditional / NSE) inline without a zero-variance guard, so a constant observed vector gave `NSE = 1 − x/0 = -Inf` and an undefined squared correlation, and an infinity reads as a real score. Both now return NA, matching the NA-not-Inf convention `augment_metrics()` / `calc_ccc()` already follow (the per-locality Model Performance and uploaded-metrics tables were already safe, computing through yardstick). Numerically identical for all non-degenerate data.
- **Small-unit covariates were silently dropped as "constant"**: the multicollinearity engine's variance floor was absolute (`var > 1e-6`), so any covariate whose natural units put its variance below that threshold — clay as a 0–1 fraction, normalized indices, ratios, values in km or Mg — was treated as a constant and pruned before the VIF loop ran, silently changing the RK/RFK trend model. Because constants are dropped even under "Keep All", the user's explicit override could not rescue them. Degeneracy is now judged relative to each covariate's own magnitude, so genuinely constant columns are still pruned while small-magnitude ones are modelled normally.
- **Cross-validation coordinate detection used prefix matching**: `perform_cv()` still matched `^lon` / `^lat` by prefix and took the first match in *column* order, so a Co-Kriging CV object carrying a covariate named e.g. `Longitude_deg` could win over the guaranteed `x`/`y` columns and put residual Moran's I on the wrong coordinates. Exact-name matching now takes precedence, consistent with the `is_coord_col()` rule adopted everywhere else.
- **Unrecognised CV strategy crashed the run**: a stale or hand-edited run-configuration upload carrying an old `cv_strategy` key raised `match.arg`'s error inside a parallel worker, surfacing as the generic "Parallel Interpolation Failed" modal. Unknown values now degrade to Auto.
- **Covariate engines without covariates reported "Unknown interpolation method"**: calling RK, RFK, or CK with no auxiliary variables fell through the dispatcher to the unknown-method error, telling the user that RK is not a recognised method. The dispatcher now names the real cause. The UI path was already guarded; the engine is publicly callable.
- **Only the last failing locality's error dialog was visible**: a multi-locality run that failed in several regions opened one modal per failure, each replacing the previous one, so the user saw a single region and had no indication the others had failed (the stacked notifications expire after 15 s). Failures are now collected into one dialog listing every failed region with its full error text.
- **Missing classification predictor trained a smaller model in silence**: a predictor column absent from the training frame was routed to the categorical branch (`is.numeric(NULL)` is `FALSE`), became an all-NA column, was mode-imputed to a constant and then dropped by `step_zv` — so the model trained on fewer predictors than selected, with no message anywhere. It now fails with the missing column names.
- **Jenks styling silently rendered continuous maps**: `classInt`'s Jenks implementation emits a stray `message()` condition ("Use fisher instead...") that `suppressWarnings()` does not muffle; several stats-table consumers wrapped the shared class-break reactive in a blanket `tryCatch(condition = ...)`, which intercepted that message mid-evaluation, aborted the reactive, and poisoned its cached state — the map renderer then swallowed the resulting error into its continuous-palette fallback, and the area tables reported "Awaiting Classification Params" forever. Messages are now suppressed at the source and all consumers catch errors only. K-Means and Supervised were unaffected (they emit no message). Break values are unchanged.
- **Per-locality resolution table was stale in Fixed mode**: with Resolution Logic set to Fixed, adding or changing the selected localities did not refresh the sidebar's per-locality summary table (or the map resolution overlay) — they kept showing the previous selection. Both now track the current locality list in Fixed mode too, showing the chosen fixed value per locality, and the overlay follows subsequent slider changes. Display-only: interpolation always read the fixed value directly and was unaffected.
- **Interpolated Point Errors map was meaningless for geographic (lat/lon) uploads** (behavior change in the already-broken case, user-approved): the error-surface IDW stamped the raw uploaded coordinates with the locality's UTM CRS instead of projecting them, so degree values were read as metres — every grid cell saw all samples at essentially equal distance and the exported surface was near-constant. The points are now projected (input CRS → locality UTM) before the IDW; projected uploads were and remain correct.
- **"Keep All (Not Recommended)" in the RK/RFK multicollinearity modal was silently ignored**: the chosen threshold reached the run pipeline but was never passed into the interpolation engines, so covariates the user explicitly kept were still auto-dropped at the default VIF 10 ("Auto-Drop" only worked by coincidence). The threshold now flows end-to-end, and an infinite threshold (Keep All) disables iterative pruning entirely — including the singular-matrix fallback path — matching the Classification Suite's already-correct behavior.
- **Zero-variance covariate crashed the VIF engine**: a constant covariate (common after subsetting to one locality) produced NA correlation rows, failed `solve()`, and then crashed the fallback ("subscript out of bounds") — misreported as "RK failed … Falling back to OK", or a silently missing collinearity advisory in the Classification Suite. Constants are now pruned (and reported as dropped) before the VIF iteration, and the fallback is NA-hardened.
- **CV residuals could be written back to the wrong points**: the per-point residual write-back used positional assignment against a differently filtered point set; with co-located points whose first occurrence has a missing target, R's silent recycling shifted residuals onto the wrong points, feeding the Internal Residual Variogram (Total view) and residual exports with shuffled values. The write-back now joins on the rounded-coordinate key both dedup passes share, and skips (leaving NA) on any length mismatch.
- **Pooled "Total (Combined)" CV object could silently degrade to one locality**: if combining the per-locality CV objects failed structurally, the pooling helper returned only the first locality labelled as the combined result; it now returns the empty state instead.
- **Governing-factors scatter panel no longer follows live inputs**: after a run, changing the Target dropdown (without re-running) silently swapped the "Target vs Top Factor" panel's y-axis and title while the importance/SHAP/ALE panels still described the completed run. The panel now uses the run's committed target and data (same display-decoupling convention as the main Map Viewer).
- **Coordinate-column filter swallowed legitimate variables**: any column merely *containing* "lat"/"lon" (`Precipitation_cumulative`, `correlation_index`, `latent_heat`, `along_slope`, …) was excluded from variable auto-mapping, popup variables, mapping targets, and the Descriptive Suite's grouping/plot choices. A shared `is_coord_col()` helper now matches whole names only (x, y, lon/long/lng, lat, longitude, latitude, easting, northing) across all six call sites.
- **Descriptive statistics described the wrong prediction column for Single-Split runs**: the Total/locality summary tables preferred the `_cve` column even when the displayed run mapped `_ss` predictions; they now summarise exactly the column the displayed run's value type uses.
- **CRS auto-suggestion no longer guesses a specific projected system**: metre-scale coordinates previously auto-filled EPSG:32635 (or EPSG:5514 for negative values) — a Bulgaria/Türkiye (resp. Czech) system applied to data from anywhere. Since a zone cannot be inferred from bare projected coordinates, the app now prompts for the correct CRS instead (the geographic ±180/±90 → EPSG:4326 suggestion is unchanged).
- **Classification scope could silently expand to the full bounding box**: when a fixed grid resolution was too coarse for a small polygon scope (no grid cell inside the boundary), the grid fell back to the entire bbox — the opposite of what scoping promises. It now stops with a clear message ("reduce the grid resolution or widen the scope").
- **Binned classification targets crashed on tightly clustered values**: distinct break values that rounded to identical 2-dp interval labels made `factor()` fail on duplicated levels; label precision now widens automatically until the interval labels are unique.
- **CCC is now NA when either vector is constant** (stricter convention, user-approved): the previous code returned 1.0 for two equal-mean zero-variance vectors, asserting perfect agreement where Lin's coefficient is mathematically undefined (the correlation term is 0/0).
- **Partial-correlation heatmap NaN row**: selecting a variable both as an analysis variable and a control residualized it against itself (~zero residuals). Control variables are now excluded from the analysis set per standard partial-correlation practice.
- **PCA 3D biplot transient error**: switching straight to the 3-D biplot before its axis controls rendered threw a temporary red error; the 3-D branch now carries the same `req()` guard as the 2-D biplot.
- **Theme readability**: "Midnight Neon" set its body text color identical to the content background (plain text and inactive tab labels were literally invisible); "Slate & Gold" paired dark brown text with the dark slate background (~2:1 contrast). Both now use light body text with proper contrast.
- **Manual variogram tuning restored.** Switching Fitting Mode to Manual after "OPTIMIZE ALL VARIOGRAMS" showed no variogram (before the first run) or an unresponsive plot (after a run): the panels hard-required a completed run's display context, and the tuning overlay only draws when the Scientific Analysis locality filter happens to equal the tuned locality. The panels now fall back to the live sidebar variable before the first run, the analysis filter follows the *Locality to Tune* automatically while Manual mode is active, and a locality with no fitted variogram shows an instruction placeholder instead of a blank. The tuning-locality dropdowns also no longer reset to the first locality on unrelated data refreshes. Follow-up: the Tab 3 panel *visibility* was still keyed to the completed run's method, so before the first run the variogram cards stayed hidden behind the "Diagnostic Mode Active" placeholder even after auto-fit; the diagnostic panel gating now falls back to the live sidebar method pre-run (any kriging-family selection shows the Data Structure variogram cards, and the Predicted card appears once auto-fit has fitted predicted-side variograms), while post-run gating still follows the displayed run.

All break/area computations now go through a packed-safe accessor, and if class breaks are ever unavailable the viewer falls back to the continuous palette rather than rendering an empty map.
- **Oversized worker exports ("globals exceed maximum allowed size") and slow optimizer clicks.** The auto-fit and IDW/TPS optimizer buttons passed inline lambdas to `furrr`; a lambda defined inside an observer drags the observer -> server environment chain (the entire session state) into the future export, which grew with every completed run until dispatch failed at ~1 GiB. Pooling now reprojects to the auto-UTM zone of the combined centroid (the same zone rule used for geographic inputs). Displayed pooled numbers shift accordingly; per-locality results are unchanged. ### Performance
- **Classification prediction surfaces are built in one model pass instead of two** (roughly halves the longest stage of a classification run): every grid block was predicted twice — once for the hard class and once for the class probabilities — which is two full recipe bakes and two model passes over a grid that can reach a million cells, on the stage the progress bar itself marks as the longest (covariates → surface). Every shipped learner is a probability model, so the hard class *is* the argmax of the probabilities the run already computed, and it is now derived from them. Output is identical except at exact probability ties, where the winner is now fixed deterministically on the trained class order instead of being left to the engine; agreement with a direct class prediction is pinned by a test across all three learners.
- **SHAP dependence values extracted in one pass**: the Governing Factors module rescanned the entire SHAP frame (sample size × permutations × predictors rows) once per sampled observation, with three full-length comparisons each. The rows are now filtered once and grouped by observation. Identical values.
- **Classification rasterisation builds its coordinate matrix once**: the surface rasteriser rebuilt the full `n × 2` grid coordinate matrix inside the loop over class-probability layers, i.e. once per class on a grid that can reach a million cells. It is now built once and reused for the class, probability and entropy layers. Identical rasters.

- **Interpolation runs are cancellable during covariate kriging**: the covariate stage of an RK/RFK run interpolates every retained covariate over the full prediction grid and had no cancel checkpoint anywhere inside it — the run polled the cancel flag only before and after the whole block, so on a multi-covariate run pressing Cancel did nothing until every covariate had finished. A per-covariate checkpoint (the same hook the Classification Suite already used) now bounds cancel latency to one covariate's kriging.
- **Grid coordinates extracted once instead of twice**: building the prediction grid and de-duplicating the sample points each called `st_coordinates()` twice on the same object to fill the `x` and `y` columns, materializing the full coordinate matrix a second time on a grid that can reach ~1,000,000 nodes. Numerically neutral.
- **Collinear covariates are no longer kriged before being dropped**: the RK/RFK multicollinearity gate ran *inside* the engine, after every selected covariate had already been interpolated onto the full prediction grid — so each covariate the gate discarded had cost one global kriging plus its own variogram candidate search (4 models × 4 starting ranges), on the critical path of a run the user is watching a progress bar for. With, say, six collinear covariates reduced to two, that was four wasted global krigings per locality. The gate is now resolved before the covariate surfaces are built, and the retained set is passed down to the engine rather than recomputed. Numerically neutral by construction: the gate is evaluated on exactly the point set each engine fits (the Actual and Predicted surfaces are screened separately, since they can retain different samples), and the grid carries the union of the two retained sets.
- **Interpolation grid pre-filtered to the boundary**: grid nodes outside the run boundary (previously interpolated and then masked away) are now excluded before the engines run. All engines predict pointwise, so within-boundary values are bit-identical; kriging cost drops substantially for concave/multi-part boundaries whose bounding box far exceeds their area.
- **Descriptive summary table computes its five group statistics in one `aggregate()` pass** instead of five (identical numbers).
- **Startup auto-install now warns about reproducibility**: installing missing packages pulls latest CRAN versions, which can drift from the pinned `renv.lock`; the console message points to `renv::restore()` as the reproducible path.
- **Map styling is responsive again** (Continuous/Binned/Agronomical switches, algorithm/class-count changes, Match Scales): raster display values are unwrapped once per run and cached instead of on every styling tick; the class-count slider and supervised limit inputs are debounced so dragging/typing triggers one re-render instead of one per step; area tables check their cache before deserializing rasters; and the Leaflet viewer shows a mean-aggregated preview above ~500,000 cells (display-only - exports, GeoTIFFs, and area/classification statistics always use the full-resolution rasters).
- **Styling ticks no longer re-resample raster layers** (biggest win on multi-locality runs, where the per-tick cost scaled with locality count): the display projection is now computed once per layer per run straight to the Leaflet map CRS (EPSG:3857) and cached, and `addRasterImage` is called with `project = FALSE` — previously its internal, uncached reprojection re-resampled every locality layer on the main thread at every styling change. Classified (Binned/Agronomical) draws also skip the per-locality cell-value extraction that only the continuous legend needs. Display-only: exports, GeoTIFFs, and area/classification statistics still use the full-resolution rasters; the displayed surface is now single-resampled (native → 3857) instead of double-resampled through an EPSG:4326 intermediate, so the continuous legend's min/max may shift imperceptibly.
- **Jenks / K-Means class breaks are seeded and sample-based** (`calc_class_breaks`): exact Jenks is O(n^2) and took 4-10 blocking seconds on raster-sized vectors while both classInt styles drew unseeded random numbers (irreproducible class limits). Breaks are now computed under the app's standard seed sandbox, with Jenks estimated on a seeded subsample capped at 5,000 cells; class areas are still measured on the full-resolution raster. Class limits may shift marginally versus the previous (already sample-based, unseeded) values and are now bit-reproducible. See scientific guide 9.4.
- **Scientific Analysis plots are now cached per run and locality** (`renderCachedPlot`, session cache): variogram, internal residual variogram, cross-variogram, RF importance, TPS GCV, observed-vs-predicted, and CV residual-variogram panels no longer recompute (including `robust_vgm_fit` refits on the residual variograms) when switching the analysis locality filter back and forth. Cache keys embed the run revision and the underlying fit objects, so manual variogram edits and re-runs still refresh immediately.
- **Observer hygiene**: the Export Styler persist, mapping sync, variable-category cascade, point-styling choice rebuild, run-history rebuild, panel toggles, and log notifier are now event-driven (`observeEvent`) with explicit dependency sets; the variogram slider bounds and the Map Viewer sampling-point overlay reuse cached projections (`projected_max_dist`, `pts_view_4326`) instead of re-transforming all coordinates on every styling tick or run completion.
