# User Guide

## Workflow at a Glance

Monolith is organised as six tabs. Four of them are the interpolation workflow, worked left to right:

1. **Data Setup** loads the table, maps coordinates and variables, and confirms the CRS. Nothing else unlocks until this is confirmed.
2. **Map Viewer** shows the interpolated surfaces and carries the drawing and export toolbar.
3. **Scientific Analysis** holds the variograms, performance tables, residual diagnostics and the run log for the last run.
4. **Export** collects every map, table and figure the session produced.

**Exploratory** and **Classification** sit apart from that sequence, behind a divider on the right of the tab bar: both branch straight off Data Setup, read the confirmed table directly, and ignore the interpolation configuration entirely.

In Exploratory → Governing Factors, the importance bars and table report the increase in RMSE when each predictor is shuffled, relative to the unshuffled forest. A value near zero means the shuffle barely changed this model's error; the separate OOB variance-explained row describes model quality. The table gives each row its own **Unit**, because the importance rows (RMSE increase, in the target's units) and the model-quality row (% of variance) are different kinds of number.

In Exploratory → Descriptive Suite, the **Group Statistics** table under the plot reports, per group and for the TOTAL row, Count, Mean and SD beside their robust counterparts, **Median, Q1, Q3, IQR and MAD** (the MAD is scaled by 1.4826 so it reads on the same scale as the SD). Where the mean and SD disagree with the median and MAD, a few extreme values are pulling the moments. On the boxplot, violin and sina plots, the **normality verdict** is printed as a sentence beside its icon (test, statistic, p, n and the conclusion at alpha = 0.05), so it can be read and copied without hovering. Details: the Descriptive and Exploratory Suite guide, Section 2.

The sidebar (Context, Spatial Engine, Domain & Grid, Map Styling, Session) configures interpolation runs. On the Exploratory and Classification tabs the whole of it is replaced by a short notice naming the active suite: both read the confirmed table directly and pick their own variables, so neither uses any of those selections.

## In-App Documentation

The header's **info (i) button** opens this documentation in a slide-in drawer with three tabs (User Guide, Scientific Guide, Descriptive and Exploratory Suite). While the drawer is open:
  - Click anywhere **outside the drawer**, or the ✕ button, to close it.
  - A **floating button column** in the lower-right corner navigates the open document: jump to the top or end, or step to the previous or next section heading.

## The Header

The header carries the session's context and its controls. Beside the wordmark, a strip states what everything on screen is computed from - the loaded dataset, its number of points, the Input Data CRS the coordinates were recorded in, the Target Mapping CRS every metric quantity is measured in (each appears as it is set) and how many localities the table contains - so those facts stay visible from every tab. On the right sit the run-status chip (grey *Idle*, amber *Running* with a live percentage, green *Run ready* with the method, grey *Cancelled* with the run number after a cancelled run), the light/dark button, the **(i)** button that opens this documentation, and the **(?)** button, whose About panel carries the session information and a download of it for reproducibility.

## Light and Dark

The **sun / moon button** in the header switches the interface between its light and dark variant. The choice is remembered in your browser and applied on the next visit; on a first visit the interface follows whatever your operating system asks for. Switching is immediate and never interrupts a run: it changes nothing on the server, so you can flip it while an interpolation is in progress.

The variant governs the interface only. Map basemaps are chosen separately in the Map Viewer toolbar, and exported figures are unaffected: their appearance comes from the Export Styler, so a figure exported in the dark variant is identical to the same figure exported in the light one.

## Data Ingestion & Configuration

The Data Setup tab presents the configuration as four numbered cards; the later ones appear once a dataset is loaded. The steps below follow those cards, with the second one (*Spatial Mapping*) split into variable assignment and coordinate reference system, because each carries rules worth stating on its own.

The application requires cleanly structured, georeferenced tabular data. Column headings (the first row) hold parameter titles (`tn`, `p`, `k`, `ph`, `som`, `clay`), categorical or grouping factors (`subset`, `texture_class`, `locality`), and coordinate labels (`x`, `y`, `lat`, `long`). Rows hold the data values.

**Step 1. Upload dataset**
   - Click `Browse...` to upload a `.csv`, `.xls` or `.xlsx` file of up to 30 MB. It must contain distinct columns for X coordinates, Y coordinates and at least one variable of interest.
   - **Variable List (Optional)** sits beside it, so both files are chosen in one pass. It is a second `.xlsx`, `.xls` or `.csv` table (for example `samp_var_list.xlsx`) defining your columns: the column naming your variables is the one whose header contains `actual`, `column` or `variable` (the first column when none does), headers containing `label`, `name`, `display` or `ID` supply the readable labels used on every map and report, and headers containing `cat`, `group` or `type` file the variables into folders such as "Physicochemistry", "Remote Sensing" or "Terrain". Upload the dataset first: the list is matched against its column names, and a list uploaded on its own is rejected with a note saying so. What it produces is listed for review and editing under *Variable Mapping & Verification*, at the foot of the tab.
   - Under both sits an optional **Boundary shapefile** row with an **Upload .shp set** button. Most analyses never need it: the built-in hulls (convex, concave, strict, wrapped) are configured in the sidebar once the dataset is loaded. To supply your own boundary, select the `.shp`, `.shx`, `.dbf` and `.prj` files together (up to 200 MB in total).
   - A sample dataset ships in the app directory.

      **Using the sample data?** It arrives ready to run: **Locality** preset to Kale and Yorga (the two the accompanying manuscript examines in detail, so the first run is the one the publication describes rather than all seven at once), and both **Input Data CRS** and **Target Mapping CRS** preset to `EPSG:32635` (UTM 35N), the zone those localities are on. One notification lists what was set; clearing the Locality box restores the full set, and either CRS can be changed like any other. The presets are keyed on the sample file's own name, never on its contents, so they never apply to a dataset of your own; loading any other file clears them.

      The zone is worth a word, because the app otherwise refuses to guess one. It cannot be recovered from this file: the coordinates are bare eastings and northings, and UTM zones 34N, 35N and 36N each place these same numbers inside their own span (22.9°E, 28.9°E and 34.9°E respectively). What settles it is the locality names: Acipayam, Beyagac, Kale, Karacasu and Tavas are districts of Denizli, and only 35N puts them there. So the preset is a documented fact about one shipped file, not an inference from its numbers.

      `samp_data_1.xlsx` (paired with the variable list `samp_var_list.xlsx`) is a dataset with an associated manuscript submitted for peer review. It is provided strictly for demonstration, evaluation and testing of Monolith, and is **not** licensed for third-party use until that manuscript is formally published. On publication these datasets will be released under the [Creative Commons Attribution 4.0 International (CC BY 4.0)](https://creativecommons.org/licenses/by/4.0/) license. Until then all rights are reserved and the restrictions apply to all third parties. Full terms: [sample_data/DATA_LICENSE](https://github.com/rserdarkara-hash/monolith/blob/main/sample_data/DATA_LICENSE).

**Step 2. Assign variables**
   - **X/Y coordinates:** select the columns holding longitude/latitude or easting/northing. A column is pre-selected only when its **whole** heading is a recognised coordinate name: `x`, `lon`, `long`, `lng`, `longitude`, `easting` for X, and `y`, `lat`, `latitude`, `northing` for Y (case and surrounding spaces ignored). Partial matching is deliberately not used, so names merely containing a coordinate fragment (`Longevity_index`, `Lateral_flow`) stay available as analysable variables. If nothing matches, the first column stays selected and you pick the right ones. The same rule decides everywhere else in the app which columns are coordinates rather than variables.
   - **Locality / grouping:** headers containing `locality`, `loc`, `site`, `farm`, `id` or `group` are offered for the "Locality" or a "Grouping Factor" selector, which filters analysis subsets later.

**Step 3. Coordinate reference system (CRS)**
   - **Neither CRS dropdown has a default.** Monolith identifies your CRS when the file carries the evidence to prove it, narrows it down when it does not, and never assumes a zone. The one exception is the dataset shipped in `sample_data/`, recognised by its own file name: its zone is documented rather than inferred, so both selectors arrive on `EPSG:32635` (UTM 35N) and a notification says so. That is the only preset in the app; every other file takes the route described here, whatever it contains. A projected easting/northing pair is equally valid in all 60 UTM zones (the same numbers read one zone east move every point 6° of longitude), so a guessed default would place a whole survey in the wrong country without raising a single error.
   - **How identification works.** Coordinates inside ±180/±90 *could* be degrees, but a local grid in metres (a field plot with X = 2–48 and Y = 5–60) fits those ranges too. So `EPSG:4326` (WGS 84) is set automatically only when the X and Y columns are named as longitude and latitude (`lon`, `long`, `lng`, `longitude` and `lat`, `latitude`), or when an uploaded boundary shapefile contains at least half of the points read as degrees. Otherwise a panel under the dropdowns asks **Are these coordinates longitude/latitude?** with a **Use EPSG:4326** button; if they are metres or another system, set the CRS they were recorded in instead. Either way the notification names the WGS 84 assumption: coordinates recorded on an older geographic datum (for example ED50) need that CRS chosen explicitly. For projected coordinates the app looks for proof: a companion `lon`/`lat` (or `long`/`lng`/`longitude`/`latitude`) column pair in the same table, or an uploaded boundary shapefile with a `.prj`. When one candidate reproduces that evidence and the alternatives are decisively worse, the CRS is set and reported with the numbers behind it: how closely the chosen CRS reproduces the `lon`/`lat` columns and how far off the next candidate is, or, from a boundary, the share of points that fall inside it. Nothing is plotted until a CRS is set. **Uploading a dataset empties the Input Data CRS and starts identification over.** An input CRS is established for a particular file; it is not a session setting, and leaving one standing over a different file's coordinates is how a survey ends up silently in the wrong country. That reset applies to a CRS you typed yourself as well, because it was your answer for the previous table, not for this one. The **Target Mapping CRS** is different: it names the system your outputs are produced in, not a property of the file. A target you chose yourself is kept, a notification says so, and the panel under the selectors judges it against the new data at once; a target the app filled in is cleared and identified again. Within a dataset the rule is unchanged: once an Input Data CRS is set here, uploading a boundary shapefile or remapping the X/Y columns re-runs identification but never overrides it; a deliberate choice stands, and the position printed under the mini-map is where to check it.
   - **No evidence in the file? Locate the study area instead.** A **Locate your study area** panel appears under the CRS dropdowns. Click roughly where the data was collected on the world map, or type a country or region (`Germany`, `Kansas`), and press **Find matching projections**. Monolith searches the full EPSG catalogue of projected coordinate systems that PROJ ships (over 5,000 codes, worldwide, no curated list), keeps those whose declared area of use covers that place, and reports each surviving **position** the coordinates would land on, nearest first, with a numbered marker on the map. Codes that land within 250 m of each other are grouped on one row, and the row says how far apart they actually are (*"Same place to within 209 m: EPSG:3045, EPSG:25833, ..."*). That covers a WGS 84 UTM zone, its ETRS89 twin and its older datum siblings such as WGS 72 or ED50: a map click cannot separate them, so they are offered as one place led by the modern code rather than as competing rows. Press **Use this CRS** on the row whose position is your study area: you confirm a place, which you know, instead of an EPSG code, which you may not. The search runs in the background and the tab stays usable while it works. If nothing lands near the point you indicated, the list says so rather than offering a best guess, which usually means X and Y are mapped to the wrong columns or are swapped. Country text can only ever be a secondary filter, so if it matches more projections than can be searched at once the panel says the search was capped; combined with a map click, text that matches nothing inside that area returns an empty list rather than widening the search again.
   - **The Input Data CRS is the only control that moves points on a map.** Every map layer is reprojected to `EPSG:4326` for display no matter what the Target Mapping CRS says, so cycling the target will never correct a misplaced survey. The Input Data CRS also decides where the models are computed: metre-based projected input is used as supplied; geographic or non-metre projected input is transformed to the WGS 84 UTM zone of each locality. Data Setup warns above 1% input-projection distance distortion. To reduce that distortion, reproject the coordinates before upload; changing their CRS label alone changes their interpreted location. The **Target Mapping CRS** governs the georeferencing of exported GeoTIFFs and shapefiles, the final resampling of the surface, the sidebar resolution suggestion, and the ruler's projected reading.
   - **Check the position printed under the mini-map.** It states in degrees where your points currently land, for example `Currently plotting at 12.958°E, 52.466°N`. Compare it against the study area you know: a wrong zone shows up immediately as a longitude in the wrong country. The Map Viewer in tab 2 is a snapshot of the last completed run, so a CRS change only reaches it after you press **Run Interpolation** again; until then the Map Viewer carries a banner naming the mapping its layers were computed under and what has changed since. The existing results are never discarded, because the run archive and the Export Registry refer to them.
   - Both CRS dropdowns list **every WGS 84 / UTM zone** (1N–60N, 1S–60S) alongside WGS 84, S-JTSK / Krovak and (Input only) Pseudo-Mercator; type a zone or code to search. Once the data's position is known (from the Input Data CRS, or the point clicked in *Locate your study area*), its UTM zone and the two adjacent zones are listed first under *Near your data*.
   - Both CRS dropdowns accept **free-typed entries**: any EPSG code (`EPSG:25832`, or the bare number `25832`), PROJ string or WKT. Typed values are validated before a run starts.
   - **A standing panel under the two dropdowns judges the Target Mapping CRS and names the one that is right for your data.** It appears once the dataset, the X/Y columns and the Input Data CRS are set, and it states its verdict in one line. When the target is not set, not recognised, not metric, or questionable, and the recommended CRS measures better than your selection, it offers that CRS by name with a **Use this CRS** button. The recommendation is the WGS 84 UTM zone your data falls in, derived from the data itself: it exists for every longitude and its distortion stays below 0.1% inside its own zone. If you prefer your national grid, type it in and the panel judges it on the same two rules as anything else.
   - The panel has five states. **Green** means the CRS suits the area, and states its point scale factor (`k = 0.999836`, so distances are -0.016% off). **Blue** covers a target that is not set yet, and a geographic target such as `EPSG:4326`: that one is a legitimate choice, and the panel says so rather than staying silent, because maps and exports simply come out in degrees while the models are still computed in the projection described above. **Amber** means a run is allowed but the CRS is questionable. **Red** means a run is refused, or the entry is not a recognised CRS. The information icon next to the verdict explains what reads from this CRS.
   - The **Target Mapping CRS** must be metric if it is projected. A CRS in feet would make exported rasters, the resolution suggestion and the ruler's projected reading report feet as metres (a factor of 3.28). That is a red verdict and both interpolation and classification refuse a run with it.
   - **The Input Data CRS is not checked for units or distortion.** Grid resolution, buffer distance and variogram ranges are applied in the Input Data CRS when it is projected, so it should be a metric projection suited to the study area (its UTM zone, for example). A geographic Input Data CRS needs no such choice, because the pipeline projects it to the local UTM zone itself.
   - **Recommended setting for projected data:** choose the same UTM zone that suits your study area for both the Input Data CRS and the Target Mapping CRS. The models, the exports, the resolution suggestion and the ruler then share one metric system, and the unit and suitability checks on the Target Mapping CRS cover the models as well.
   - **The Target Mapping CRS must also suit the area.** Being metric is not enough: Web Mercator's axis unit is the metre and at 52°N it reports every distance 64% too long. Monolith measures the point scale factor at your data (the centroid and the four corners of the data extent, worst case) and states the number. Beyond 0.1% off is amber; beyond 1% is red, and the interpolation gate then offers **Use Anyway (Not Recommended)**, recorded in the run configuration and summary. Classification refuses this red suitability verdict without an override.
   - The selected input CRS is cross-checked against the mapped X/Y columns. A geographic (degree) CRS with coordinates outside ±180/±90 raises an error notification; a projected (metric) CRS with degree-like coordinates raises a caution; X values that stay inside ±90 while Y values run past it flag a swapped longitude/latitude mapping. If the mapped X/Y columns hold no numbers at all, which happens when the file's coordinate columns are named so that the app cannot recognise them and the mapping falls back to the first column, the guard says so and names the two columns it read. Fix the CRS or the mapping before running. The guard never blocks or alters a computation itself.
   - A boundary shapefile may be stored in any CRS: it is reprojected onto the data at run time. Its `.prj` fills the **Target Mapping CRS** only when that selector is empty and never replaces a CRS already set. A shapefile without a `.prj` is read in the **Input Data CRS**. In a multi-locality run, an unnamed feature covering samples from several localities is skipped; those localities use their selected sidebar boundaries and the Run Log explains why. To assign uploaded features explicitly, include an attribute column containing their locality names.
   - A note under the upload reports how many samples fall inside the boundary. A boundary that encloses none of them is not applied: each locality uses the boundary type set in the sidebar, and the note gives the distance between the boundary and the samples. A layer of points or lines is used through its convex hull.
   - The confirmed X/Y mapping and CRS are also what the **Spatial Cross-Correlogram** in tab 5 uses to bin point pairs by ground distance. Until the mapping is confirmed that panel shows a "Coordinates are not mapped yet" note; every other correlation panel is unaffected.

**Step 4. Mini-map validation**
   - The validation mini-map colours points **by locality**, one colour per geographic group, with a permanent name label over each group and a locality legend. A point far from its named group, or a group plotted in the wrong part of the world, reveals a swapped X/Y pair or a wrong CRS before any modelling starts. Custom point styling set in the Variable Mapping step takes precedence here. The mini-map always carries a north arrow (top-left) and a metric scale bar (bottom-left); unlike the Map Viewer's equivalents these are not optional, because this map exists to be checked against reality. Returning to this tab after a run re-frames the mini-map on the samples, so it always opens showing the full data extent.

**Step 5. Variable mapping and verification**

The pairs below are filled in from the variable list uploaded in Step 1 when one was supplied, and detected from the column names otherwise. This is the fourth and last card on the tab.

  - **Target isolation:** non-numeric columns and the coordinates identified in Step 2 are filtered out; the remainder become target variables. A column counts as a coordinate only when its **entire name** is a coordinate label, so `Precipitation_cumulative` and `correlation_index` remain mappable variables.
  - **Smart pairing:** a name search links observed data with model outputs, ignoring case. For cross-validated predictions it accepts `<target>_cve`, `<target>_pred`, `<target>_predicted`, `<target>Pred`, `<target>Predicted`, `pred_<target>` and `predicted_<target>`, in that order of preference; for single-split predictions `<target>_ss`, `<target>_split`, `<target>_test`, `<target>Split` and `<target>Test`. A successful match creates a triad (Actual, Pred_cve, Pred_ss) so you can toggle between ground-truth and residual maps without re-linking.
  - **Review mapping:** check the table to verify labels, units and prediction pairs, and edit any the app got wrong.
  - **Confirm:** press **Confirm Variable Mapping** at the end of the page, then proceed to the Spatial Engine.

## Mapping: Context

**Sidebar layout**
* The **Context**, **Spatial Engine**, **Domain & Grid**, **Map Styling** and **Session** sections are collapsible: click a section title to fold it away. Each remembers its state in the browser between sessions.
* **Spatial Engine** holds the choices that define the model: method, its parameters, and the cross-validation design. **Domain & Grid** holds the choices that define where and at what cell size it is evaluated: boundary, buffer and resolution, with the resolved per-locality table beneath them.
* **Session** holds **Save config** and **Load config**. The first writes the active coordinate mapping, variable list and categories, palette and engine settings to a JSON file; the second reads one back in a later session. That file is the session's setup, not the record of a finished run, which is the Export tab's *Download Run Configuration*.
* The **Run Interpolation** button stays pinned to the bottom of the sidebar while you scroll, and a **status chip** in the header shows the run state from any tab: grey *Idle*, amber *Running* with a live percentage, green *Run ready* with the method.
* The **Variable** dropdown supports live search: start typing to filter long lists.

**1.1 Locality (spatial grouping)**
* The designated grouping column partitions the dataset. Select a single field, or "ALL" to run a batch-parallelized interpolation across multiple spatial domains at once. Clearing the selection is treated as "ALL": every analysis path (runs, optimizers, auto-fit, resolution suggestions) resolves it to all localities. Rows with a missing locality value are excluded from "ALL"-type selections.
* This selection seeds the **Spatial Scope** of the Classification Suite, whose locality picker can then be adjusted independently.

**1.2 Variable selection and category**
* **Variable category:** variables are organised into folders ("Soil Physicochemistry", "Terrain", "Satellite Indices") from your metadata file or automated detection. A new variable list opens on the first folder holding a variable with an uploaded prediction column (`_cve` or `_ss`), and on that variable, rather than on a folder of covariates; with no prediction column anywhere it opens on the first folder.
* **Variable:** selects the target "Actual" column. Suffix and label matching links a target such as `Total N (%)` to the column `tn` and to its prediction columns `tn_cve` and `tn_ss` where those exist.

**1.3 Primary view and comparison mode**
* **Actual Values:** the interpolated surface of your raw measured data.
* **Best ML Predictions (_cve):** the interpolated surface of the machine-learning model's cross-validated estimates.
* **Single Split ML Predictions (_ss):** the surface for a specific data-split prediction.
* **Residuals (v - pv) of ML Predictions:** the localized difference between what you measured and what your uploaded model predicted. These residuals diagnose the ML model, not Monolith's interpolation.
* ML prediction and residual views are offered only when the selected variable has the corresponding prediction column (`_cve` for Best ML Predictions and Residuals, `_ss` for Single Split). Without prediction columns the Primary View is limited to Actual Values.
* **Actual vs Predicted** is the group of three boxes under the Primary View buttons, shown whenever a prediction or residual view is selected. **Comparison Mode** splits the display into a synchronized dual-map view for a side-by-side audit of actual data against predictions. **Fit Actual/Predicted Separately** (on by default, recommended) gives the predicted surface its own model: its own variogram under Ordinary Kriging, its own power under IDW, its own lambda under TPS. Unticked, the predicted surface reuses the model fitted to the measured values: the Actual variogram (the run's own Actual fit under Auto-Fit, the applied Actual model under Manual), the Actual IDW power, and the Actual TPS lambda, which on Auto (GCV) is the one GCV selects for the measured values. Manual tuning, **OPTIMIZE IDW FACTORS** and **OPTIMIZE TPS LAMBDA** then offer or search the Actual target only. Under Auto-Fit and Auto (GCV), cross-validation refits the shared variogram, or reselects the shared lambda, inside every fold from the measured values of that fold's training samples. RK, RFK and CK always fit each surface on its own. **Match Scales** appears once Comparison Mode is on, and whenever the Map Viewer shows a comparison view of a run that has a predicted surface, and gives both maps one colour range (the surfaces, and their standard-error or variance maps alike).
* **Sidebar selections configure the NEXT run.** Once a map exists, changing the Variable, Primary View, Interpolation method or Comparison Mode does not alter the displayed map or its Scientific Analysis results; they update when you press **Run Interpolation** again. Styling controls (Continuous/Binned/Agronomical, class limits, palette) stay live and restyle the displayed map immediately. To switch between surfaces the last run already computed, use the **View** dropdown in the Map Viewer toolbar, which is instant and needs no re-run. For a kriging run it also holds the uncertainty maps of those surfaces (see *Uncertainty maps* under Mapping: Spatial Engine).

**1.4 Data subset (Single Split view only)**
* With the Primary View set to **Single Split ML Predictions (_ss)**, a **Data Subset** dropdown appears beneath it and restricts the mapped data to one modelling partition ("Train", "Test", "Validation") before interpolation. The whole run works on those rows: the variogram, IDW and TPS optimizers and their previews, the manual slider bounds, the collinearity check, the run-time estimate and the Descriptive Statistics card all describe the same subset as the maps and the metrics, and a value tuned on it is stored against that subset alone.
* Choices are read from a `subset` column in the uploaded dataset, matched case-insensitively. Without such a column only "All" is offered.
* The filter applies to the Single Split view only; all other views use the full dataset.

**1.5 Drawing on the map: custom groups and exports**

The interactive maps carry a **drawing toolbar** on their left edge for sketching polygons, rectangles and point markers. This supports two workflows.

* **Assigning a custom locality or analysis group:**
    1. Draw a shape around the points you want to group.
    2. An **"Assign Locality / Analysis Group"** dialog opens when the shape is finished. Enter a group name and click **Save Group**.
    3. All points inside the shape are written to an `Assigned_Locality` column, and the app reports how many were captured. Select that column as the Locality/Grouping column in Data Setup to analyse your custom zones.
* **Map overlays** are toggled from the **Overlays** menu at the left end of the Map Viewer toolbar, with the basemap selector beside it. The view switcher, locality pan and the utility buttons (Refresh, Pop-up, Quick export, Point styling) follow along the same row. The menu holds three groups:
    * **Additions**, all off by default: sample points, the resolution box (the pixel size each locality of the displayed run was built at), the north arrow, locality borders and the scale bar.
    * **Leaflet's own controls**, both on by default: **Drawing Tools** (the polygon/rectangle/marker/edit/delete stack at the top-left of the map) and **Ruler** (bottom-left). Turn them off for a clean surface (before a Quick export, or when the map is small enough that the controls cover the data). Shapes already drawn stay on the map; only the toolbar is hidden.
    * **Variable Label in Legend**, off by default. The map legend shows its colour ramp and its break values only, because the variable label and unit are already printed as the heading directly above the map, and a long label made the legend box wide enough to cover a useful part of the surface. Turn it on for a legend that has to stand on its own: a screenshot or an exported panel separated from its heading.
* **Exporting your work:** the **Downloads** menu at the right end of the Map Viewer toolbar holds three downloads and the vector format they share. It writes files straight to your disk, which is what separates it from **Quick export** on the same row: that one sends the map you are looking at to the Export Registry instead. The menu holds (Shapefile ZIP, GeoJSON, KML, GPKG). The first two grey out whenever the export cannot be produced, and hovering a greyed-out entry names the blocking state, so the requirement is visible before you click.
    * **Drawn polygons:** active once at least one polygon has been drawn. Downloads *all* drawn polygons for reuse in a GIS. It exports the shapes **you** drew; the app's own classified zones have their own button.
    * **Class zones:** downloads the class zones of the surface **currently displayed** as a GIS vector layer, one dissolved polygon per class, carrying the class label, its lower and upper break limits, its area in hectares, and which surface, variable and method produced it. It follows the view switcher, so Actual, Predicted, or both under the comparison view. It requires Agronomical or Binned styling (Agronomical also needs **Apply to maps and statistics** pressed first), so it stays inactive until a run has produced a surface, while the map uses the continuous colour ramp, and while the residual (Delta) view or a standard-error or variance view is showing, none of which is classified into zones. The polygons are classified raster cells dissolved per class, so their boundaries are cell boundaries and are not smoothed, and their hectares are the numbers the Area Coverage table reports. Shapefile and GeoPackage keep the run's Target Mapping CRS; GeoJSON and KML are reprojected to WGS84 as those formats require.
        * **Which format to pick:** GeoPackage and Shapefile carry the attributes as queryable fields, so choose one of those to filter, join or symbolise by class in a GIS. KML stores only a name and a description per shape, so the export puts the class label in the name and the full attribute record in the description. Everything is there, but as text rather than columns.
    * **Updated dataset:** downloads the current dataset as `.xlsx` including the `Assigned_Locality` column, so group assignments survive the session. Use it after saving drawn groups.
* Shapes can be edited or deleted with the toolbar's tools, and the polygon export always reflects the current set. Deleting a shape does **not** undo a group assignment already saved from it.

**1.6 Measuring distances and areas on the map**

A **ruler** sits in the bottom-left corner of every Map Viewer map, including both panels of the comparison and residual views, so the same feature can be measured on the Actual and the Predicted surface without switching views. (The Data Setup mini-map is a preview and has no ruler.)

1. Click the ruler icon, then **Create a new measurement**.
2. Click each point along the path. The panel keeps a running path distance, and two icons sit beneath it: a cross to abandon the measurement and a tick to finish it.
3. Click the last point again, or the tick, to finish. Three or more points close the shape, which is reported as an enclosed area together with its perimeter.

The result appears in the measurement's own pop-up, on the shape itself. Click any measurement to reopen it: each one carries its own figures, so several can sit on the map at once without their numbers being confused, and the pop-up holds **Center on this** and **Delete** links for that shape alone. Every figure is reported on two bases:

* **Ground (WGS84):** the geodesic distance on the WGS84 ellipsoid. This is the real distance over the ground and does not depend on the projection you chose.
* **Projected (your Target Mapping CRS):** the same path measured flat in the Target Mapping CRS of the run **on screen**, so changing the sidebar CRS for your next run does not relabel a measurement taken on this one. The models are computed in the Input Data CRS (or, for geographic or non-metre input, the local UTM zone), so this figure is in the models' own system, and directly comparable with a variogram range, grid resolution or buffer radius, when the Target Mapping CRS is that same system.

The two normally agree to within a few hundredths of a percent, and up to about 0.1% near the edge of a UTM zone. That much is ordinary and means nothing is wrong. A gap far beyond it means the Target Mapping CRS distorts distances over your area: check that the CRS suits the region (Scientific Guide Sections 3.5 and 3.7). When the Target Mapping CRS is geographic, only the ground figure is shown, because a length in degrees is not a length.

A path that crosses itself reports its perimeter but no area, because the enclosed area of a figure-eight is not well defined. Redraw it without the crossing to get one.

These figures replace the text the measure control writes for itself, which is a quicker spherical approximation, so a shape carries one set of numbers rather than two. An open two-point line reports a **Length**; from the third point the shape closes and reports a **Perimeter**, the boundary of the same ring the area is measured over. Measurements are for reading the map only: they are not stored, not exported, and change nothing about a run. A measurement stays on the map until you delete it or the map is redrawn by a new run or a view change.

## Mapping: Spatial Engine

**Uncertainty maps.** Once a kriging map (OK, RK, RFK, CK) is displayed, the Map Viewer's **View** dropdown lists two more groups under the surfaces: **Uncertainty: standard error** (*SE: Actual*, *SE: ML Predicted*, *SE: Actual vs Predicted*) and **Uncertainty: variance** (the same three). The predicted and comparison entries appear only when the run mapped a prediction column. Choosing one redraws the surface as its SE or variance map in place, keeping the zoom and position, without a re-run; the map title and legend name the metric. SE shares the variable's unit, variance is in its squared units (Scientific Guide Section 7.2). For OK and CK the band is the kriging variance; for RK and RFK it is the hybrid trend-plus-residual variance, which is approximate and optimistic away from the samples (Section 7.3), so read those maps as a relative reliability map rather than a calibrated interval. IDW and TPS runs have no uncertainty entries, and the sidebar's **Uncertainty Mapping** note in Map Styling says so until a kriging map has been generated.
* Uncertainty maps always use a continuous sequential palette: a diverging palette choice (RdYlBu, BrBG, Spectral) is shown as Viridis on these maps, because uncertainty has no midpoint for a diverging palette to mark. Binned and Agronomical classes apply to the concentration maps only, and the class limits and class areas do not change while an uncertainty map is on screen.
* **Quick export** sends the uncertainty map on screen to the Export Registry, and a single map exports as a GeoTIFF of that SE or variance band. The **Class zones** download is inactive on these views.
* A new run keeps the SE or variance choice when the new run offers it, as it keeps a palette.

**1. Select the interpolation method**
   - **Deterministic (fast):** **IDW** weights by distance (Shepard 1968), **TPS** fits a smooth surface by minimizing bending energy (Duchon 1977). Both are ideal for rapid visualization and neither produces a prediction variance.
   - **Geostatistical (standard):** **Ordinary Kriging (OK)** models spatial autocorrelation through a variogram, giving the best linear unbiased predictor (Matheron 1963).
   - **Multivariate:** **Co-Kriging (CK)** exploits cross-correlation between the target and a densely sampled auxiliary variable (Wackernagel 2003), for example using sensor conductivity to improve a clay map. Selecting CK reveals a **CK Max Neighbors** slider (5 to 60, default 15) setting how many nearest samples of each variable enter every prediction. This is a modelling decision, not a speed setting: smaller values assume the field's mean and covariance are stable only locally, larger ones approach a global system and suit sparse, stationary data. If your sampling is unusually sparse or the fitted cross-variogram range is long, try raising it and compare the Model Performance metrics. The value used is recorded in the run-configuration summary. Scientific Guide Section 1.4.
   - **Hybrid / ML:** **Regression Kriging (RK)** and **Random Forest Kriging (RFK)** combine environmental trends (topography, satellite data) with kriging of the residuals (Hengl et al. 2007, 2015).
   - Selecting RFK reveals an **RFK Uncertainty Method** radio, which governs the variance band behind that run's SE and variance maps and nothing else: not the prediction surface, not the reported metrics. *Infinitesimal Jackknife (calibrated)*, the default, is the random-forest analogue of a regression standard error and a better-calibrated variance of the ensemble mean, at a small computational cost; *Ensemble spread (fast)* is the between-tree variance, a stability heuristic that understates true predictive uncertainty. The choice is recorded in the run-configuration summary. Scientific Guide Section 7.3.

**1.b. Choose the cross-validation strategy**
   - The **Cross-Validation Strategy** selector sits directly beneath the Spatial Engine dropdown. It changes the reported diagnostics only, **never the interpolated map**, with one exception: *Optimize IDW Factors* tunes the power under this same strategy, so the power it stores (and the IDW surface built from it) can differ between strategies. Re-run the optimizer after changing the selector.
     - **Auto (default):** leave-one-out CV at 50 or fewer points, seeded random 10-fold above 50.
     - **Standard LOOCV:** full leave-one-out at any size. The most rigorous choice and the slowest, because every kriging engine rebuilds its model in every fold: on a 355-sample locality with two covariates, about 50 s for OK, 100 s for CK, 110 s for RK and 135 s for RFK. At ten folds the refit adds roughly half a second per locality for OK, 1.3 s for CK and 0.4 s for RK and RFK.
     - **Spatial Block CV:** holds out ten spatially contiguous k-means clusters, curbing the optimistic bias random folds show under spatial autocorrelation (Roberts et al. 2017; Ploton et al. 2020). Recommended for spatial validation; below 30 points it reverts to LOOCV.
   - The strategy actually applied is shown in the badge beside the **Model Performance** table and inside each row's *Source* cell; the exported sheet carries it as a *CV Design* column.
   - **Every kriging fold rebuilds its model.** OK, CK, RK, RFK and the OK fallback all re-estimate, from each fold's training samples alone, everything they estimated for the map: the variogram (or the co-kriging model), the covariate screen, the interpolated covariates, the trend. A held-out sample contributes its coordinates and nothing else. The note under the Model Performance table states what the engine on screen re-estimated. The exception is a variogram you saved with **Apply manual model**: it cannot be re-fitted without scoring a different model than the one that drew the map, so it is reused unchanged and that locality is labelled *conditional on applied variogram*. IDW's power exponent and a fixed TPS lambda are still chosen once on all the points; Auto (GCV) TPS is not. Scientific Guide Section 5.
   - **Comparing engines on the same data: the CV Population switch.** RK, RFK and CK can only use samples that carry every selected covariate, while OK by default uses every sample with a measured target. Scoring them against each other then compares two different experiments. With Ordinary Kriging selected, the **CV Population** control offers **Native** (default: every measured sample) and **Comparable** (only the samples that also carry every selected covariate, deduplicated and folded exactly as RK, RFK and CK use them). Under Comparable, OK is trained *and* scored on those samples; the OK map still uses every sample. Choosing Comparable reveals the Auxiliary Variables panel for OK, which is there only to select the samples: OK does not model with them.
   - **The CV population ID** is eight characters shown when you hover the *Source* cell of the Model Performance table, and written to the exported metrics. Two runs on the same uploaded table whose ids match cross-validated the same rows under the same partition, so their scores are directly comparable; different ids mean they did not. Note that Spatial Block folds are built from the population's own coordinates, so Native and Comparable fold differently by design.
   - **Sample accounting.** Each row reads *n = predicted of expected*. If a fold could not be evaluated, its samples carry no prediction, the row is marked **INCOMPLETE**, and the metrics describe only the samples that were predicted; a cross-validation that failed as a whole reads *n = 0 of* its expected count, and the Total (Combined) row counts those samples as expected. Nothing is ever filled in from another engine; the Run Log names the fold and the reason.
   - **Repeated CV (fold-realization stability):** a checkbox under the strategy selector, off by default and hidden under Standard LOOCV. Left off, the metrics come from a single fold assignment, which is reproducible and keeps method comparisons paired. Tick it, pick 3, 5 or 10 realizations, and the cross-validation re-runs under that many fold assignments; the Scientific Analysis tab then shows a **Fold-Realization Stability** table where every metric reads *mean ± SD*. Use the SD as the resolution of your comparison: **if two methods' RMSE values differ by less than it, the ranking is fold luck, not skill.** Three practical points: the map and the Model Performance table are identical either way, because realization 1 is the reference run; it costs one full extra cross-validation per realization, and every kriging engine rebuilds its model in each fold, so five realizations is roughly five times the cross-validation time; and leave-one-out folds are deterministic, so localities validated by LOOCV contribute a single realization and the Run Log says so. The realization count is recorded in the run configuration and its downloadable JSON.
   - The summary tables on the Scientific Analysis tab (variogram parameters, model performance, prediction and classification metrics, area coverage, descriptive statistics) are sortable by column header. Hovering a **Model Performance** header shows a plain-language definition of that metric.
   - **Reading the Moran columns.** The table reports Moran's I of the cross-validation residuals (Moran 1950) and, beside it, a two-sided **Moran p**. Hover an I value to see that row's expected value under no spatial autocorrelation, which is −1/(n − 1) and therefore slightly *negative*, not zero: at 30 points a reading of +0.01 sits essentially on the null expectation. A clearly higher value is *consistent with* spatial structure the procedure did not capture; it is a lead to follow, not an instruction to switch to RK or RFK. A value near the expectation is not a clean bill of health either, because random folds leave a held-out point's neighbours in the training set and can mask the very structure the statistic looks for. An `NA*` in either column means the statistic **could not be computed** for that point set (too few cross-validated points, missing coordinates, or a failed neighbour search) and never that no structure was found; the Run Log states which. The p column is also `NA*` on the rare fallback weighting, which has no significance test attached.
   - **Under Spatial Block CV the column changes its name and drops its p-value.** Whole withheld blocks share one extrapolation condition, so their errors move together for reasons of the fold design rather than the model, and the usual significance test does not apply. Rows scored that way are headed **Block-CV residual clustering**, marked `†`, and their p reads `NA†`; the footnote under the table says why. A locality too small for blocks was scored by LOOCV and keeps the ordinary reading, as does a pooled row that mixes fold designs. Scientific Guide Section 5.
   - **`n/a¹` means the metric does not apply here.** For a target whose observed values span zero (an anomaly or a centred variable), NRMSE (mean) and SMAPE have no interpretation, so the table prints `n/a¹` with a footnote instead of a number, and **NRMSE (SD)** is reported in their place: the error as a multiple of the observed spread, which does not depend on where the variable's zero sits. Distinguish it from `NA*`, which means the value could not be computed.
   - **No metric prints 0 unless it is 0.** Every statistic is computed and exported at full precision and displayed to four significant digits (every integer digit from 1000 up, so a large area keeps its whole hectares), dropping to scientific notation below 1e-4, so a near-constant variable reports its real error rather than a row of zeros.
   - **Pooled rows are summaries, not scores.** With *Filter Analysis View* set to **Total (Combined)**, a note under the cross-validation badge reminds you that the pooled R² and NSE are computed against the pooled mean of all localities. Where localities sit at different levels that between-locality spread inflates both numbers, and the pooled row can look better than every individual locality. Judge model skill on the per-locality rows; pooled RMSE, MAE and Bias are unaffected.
   - **Run Warnings.** Conditions the interpolation reported for individual localities used to appear only in the progress overlay, which is gone once the maps are revealed. They now open the tab as their own card, named by locality and surface, and they are written into the Run Log, so they travel into the exported log as well. A blank metric cell usually has its explanation here.
   - **The uploaded-prediction card can score a different sample than the model.** *Prediction Performance (Uploaded Data)* is computed on the displayed points that carry both a measured and a predicted value; the model's cross-validation population drops rows with no measured value **before** removing co-located duplicates. Where one member of a co-located pair holds the measurement and the other the prediction, the two counts differ and neither is wrong. When they do differ, a note under the card states both. The card and the classification-agreement table beside it appear only for a run that mapped a prediction side: an Actual-values run reads no prediction column, so it also registers no ML-prediction maps or exports.
   - **Single-locality runs:** the analysis filter selects that locality directly. **Total (Combined)** and combined descriptive/area summaries appear only when the displayed run covers multiple localities.
   - A **Variable naming** radio next to *Filter Analysis View* switches every diagnostic on the tab (variogram titles, RF importance panels, cross-variogram headers, RK coefficient tables) between the human-readable **labels** from your metadata mapping (default) and the raw **column names**. The toggle is cosmetic; no computed value changes.
   - Every diagnostic plot sits in a card with two header buttons: **download** saves a 300-dpi PNG of exactly what is shown, on a 9 x 7 in page at the type sizes on screen, and **expand** opens a large modal with a *Static (High-Res)* / *Interactive (Hover/Zoom)* toggle. Interactive mode adds per-point hover readouts: lag distance, semivariance and pair counts on variograms; observed, predicted and residual on scatter plots.

**1.c. Covariate helpers (RK / RFK / CK)**
   - **Predictor correlations:** **Rank by correlation** opens a category-filtered table ordered by absolute Pearson correlation, with signed **r**, raw two-sided **p** and finite paired sample count **n**. The target column, selected localities, subset and scoped row count appear above it. After the first calculation, changing this context refreshes the table automatically. Candidates with fewer than three finite pairs or constant values are listed as unavailable. The screened target column is excluded from the ranks. A **Maximum p (raw)** selector above the button (All, 0.05, 0.01, 0.001) drops candidates whose raw p exceeds the value chosen.
   - **Correlation target:** Actual view uses measured values and shows no source switch. ML Predictions, Single Split and Residuals views default to uploaded predictions; **Actual values** switches this screen to measurements. CVE uses all rows in the selected localities. Single Split adds a **Correlation data subset** switch initialized from Context's **Data Subset**, allowing an independent All/Train/Test/Validation comparison wherever those partitions exist. Changing Context's subset resets the correlation subset to match it. These switches affect this screen only.
   - **Interpretation:** raw p-values are an exploratory filter, without adjustment for multiple screening or spatial dependence (Scientific Guide Section 8.7). Across-locality correlations can reflect differences between localities; check the intended locality separately. Pearson screens linear association, so weak correlation does not exclude a useful nonlinear RFK predictor.
   - **Multicollinearity gate:** launching RK, RFK or CK with several covariates triggers an iterative VIF screen (threshold 10) **on the same selected-locality data**, with an Auto-Drop / Keep All choice. Your answer is remembered until the method, the covariate set or the locality selection changes, so each new spatial context is re-screened, and it applies to Co-Kriging as well. Choosing **Keep All** genuinely keeps every collinear covariate; the only exception is constant covariates, which are always excluded because they carry no information and would break the regression fit. "Constant" is judged relative to each covariate's own scale, so covariates that are simply small in magnitude (clay as a 0-1 fraction, normalized indices, values in km or Mg) are kept and modelled normally. The screen needs at least two covariates; a run whose **single** covariate turns out to be constant within a locality still proceeds, with the trend simply carrying no covariate information there, and the run warnings name the covariate. **Your answer sets the rule, not a one-off covariate list.** The map applies it to all samples of each locality, and cross-validation applies it again inside every fold using only that fold's training samples, so a fold can legitimately keep a different set than the map. When that happens the Run Log names the covariates and the fold count, and the note under Model Performance says so.

**2.a. Variogram optimization (geostatistical engines only)**
   - Selecting a kriging method reveals the Variogram Panel.
   - **Auto-Fit (default Fitting Mode):** **OPTIMIZE ALL VARIOGRAMS** fits four model families (spherical, exponential, Gaussian, Matérn) from four starting ranges by weighted least squares and keeps the best eligible fit per locality. Zero-nugget Gaussian and Matérn models are mathematically valid, but Monolith does not auto-select them because they have produced unstable or extreme predictions in this workflow. Review the plotted curve against the scatter points. The button is a **preview**: an Auto-Fit run always fits its own variogram for the variable, data subset and localities it is about to map, whether or not you pressed it.
   - **The optimizer runs in the background.** **OPTIMIZE ALL VARIOGRAMS** greys out and reads *Optimizing…* while the search runs on parallel workers, and the rest of the app stays usable: you can switch tabs, inspect data, read the guides or open the descriptive panels. The fitted variograms and the diagnostics dialog appear when it finishes; SSE retains small nonzero values, and an unavailable fit SSE reads `N/A`. The button restores itself even if the run fails. Only one optimizer runs at a time, and an optimizer and an interpolation run cannot overlap: each parallelizes across most of your machine's cores, so starting one while the other works raises a notification asking you to wait.
   - **Manual override:** if the auto-fit misses the short-range variability (the points closest to the Y axis), switch to `Manual Tuning`. Raise **Nugget** for very noisy data, set **Partial Sill** to the upper plateau of the points, and set **Range** where the curve flattens. The sliders are scaled to the variance and extent of the locality and target you are tuning, so small-valued variables such as total nitrogen can be tuned too; applying a model does not narrow them. If a variable's variance is below about 0.0001 the sliders cannot represent its steps, and a notification asks you to rescale it in the uploaded file (for example % to g/kg). **Apply manual model** refuses a model whose nugget and partial sill are both zero. In Manual mode a run uses **only** models you saved with that button, for the variable and data subset you tuned them on; a locality with no applied model fits its own variogram, exactly as under Auto-Fit. An applied model stays applied until you apply another, press **OPTIMIZE ALL VARIOGRAMS**, or change the data: interpolation runs, Auto-Fit runs included, do not replace it. Stored models are cleared when you upload data, reassign localities, or change the X, Y, locality or Input CRS mapping, because a value tuned on other rows no longer describes these. A Gaussian or Matérn model with a nugget below 5% of its sill is applied, but flagged at Apply, in the variogram subtitle and on the map: kriging with it can put predictions far outside the observed range, or return an empty locality. Add a nugget if that happens.
   - Switching to Manual Tuning, or changing the *Locality to Tune*, moves the Scientific Analysis locality filter with it, so the variogram you are tuning is the one on screen: the fitted curve carries your manual model as a red dashed overlay with its weighted SSE in the subtitle, using the same criterion as Auto-Fit. Manual "Mat" uses Matérn smoothness 1.5, and the stored model family prefills alongside its numeric parameters. This works straight after **OPTIMIZE ALL VARIOGRAMS**, before any interpolation has run.
   - **While you are tuning, the Scientific Analysis tab is arranged around the variogram.** The *Actual* and *Predicted Data Structure* cards move to the top of the tab, directly under the locality filter, so a slider and the curve it moves are visible together. The panels are shown whatever engine produced the run currently on the Map Viewer, so tuning after an IDW or TPS run no longer leaves them behind the "Diagnostic Mode Active" placeholder. Because that run's engine fits no variogram, its result cards (parameters, performance, summaries, validation diagnostics) are held back for as long as tuning is active, with a note saying so - the maps, exports and run history from that run are untouched, and its cards return the moment you run the analysis again.
   - **A locality that produces no surface says so.** If a fitted model leaves the kriging system unsolvable, the engine returns an undefined value at every grid cell rather than raising an error. Such a locality is skipped instead of being stored and drawn as a blank completed map, and the Run Log carries a `[WARN]` line naming it and pointing at its variogram panel. The model is never altered to force a solution: a nugget small enough to leave the model unchanged leaves the system unstable too, and the surface it returns can sit far outside the observed range. For Ordinary Kriging the Run Log adds a line whenever the undefined surface came from a Gaussian or Matérn variogram with a nugget below 5% of its sill, which is the usual cause; add a nugget and run again.
   - **Manual fits apply to Ordinary Kriging only.** A hand-tuned model describes the variogram of the *measured values*, which is what OK kriges. RK and RFK remove a trend first and model the variogram of the **residuals**, and CK fits a linear model of coregionalization across the target and its covariates; imposing a value-scale model on either would be scientifically wrong, so both refit their own variogram automatically. The panel says so while RK, RFK or CK is selected, and starting such a run with stored manual fits raises a one-time notification and a Run Log line rather than ignoring your tuning silently.

**2.b. IDW optimization**
   - Selecting IDW reveals the related panel, which calculates optimal parameters per locality. When optimized, a table details the power factor chosen for each spatial domain. It carries a *Predicted* column only when the run also optimized a predicted target; with actual values alone the column is omitted rather than filled with `N/A`.
   - Adjust the **Max Neighbors** slider (4 to 50, default 12) *before* optimizing, to keep distant, unrelated points from distorting local predictions.
   - The search uses the same fold scheme as the reported metrics, so it follows the **Cross-Validation Strategy** you selected in the sidebar: leave-one-out, a seeded random 10-fold, or ten spatial blocks. Fold assignment is deterministic, so repeated optimizations under the same strategy give identical results, but changing the strategy can change the power.
   - The chosen power is then evaluated on the same cross-validation data it was selected on, with no nested loop, so an optimized IDW model's reported metrics are mildly optimistic. Keep that in mind when comparing IDW against methods that were not tuned this way.
   - **A stored power belongs to the variable and data subset it was tuned on** and is used only for that combination; any other target falls back to the sidebar value. The search itself runs on the rows the run uses, the Data Subset included. The Actual/Predicted target switch on the manual panel appears in every view that computes a predicted surface, not only in Comparison Mode, so a predictions-only view can set the power its map actually uses.
   - The search runs on projected metric coordinates. A geographic upload is transformed to its local UTM zone first, so the chosen power reflects true ground distances and matches the surface the run produces.
   - **OPTIMIZE IDW FACTORS runs in the background** (see 2.a): the dashboard stays responsive, the button reads *Optimizing…* until the per-locality powers are stored, and only one optimizer runs at a time.
   - Manual override is available.

**2.c. TPS optimization**

Regional Parameters shows the lambda actually fitted and its effective degrees of freedom for each surface. A warning identifies a near-planar surface (effective df below 3.5), including whether GCV or fixed smoothing produced it. The Model Parameters export has numeric Lambda and Effective df columns, with Mode and Surface stated separately. Very small positive lambdas retain scientific notation.
   - Selecting TPS reveals the related panel. The lambda slider defaults to `< 0` (Auto GCV), so generalized cross-validation (Craven & Wahba 1978) determines the smoothing parameter natively during interpolation.
   - Click **Optimize TPS Lambda** to extract locality-specific lambda values explicitly and generate a table of them. As with IDW, the table's *Predicted* column appears only when a predicted target was optimized.

Auto (GCV) has no such issue, because each fold re-optimizes lambda on its own training points. If the metrics are what you intend to report, prefer Auto and use the optimizer to inspect the GCV curve.
   - As with IDW, the search runs on projected coordinates, so a geographic upload is transformed to metres first and the extracted lambda agrees with the run.
   - **A stored lambda and its GCV curve belong to the variable and data subset they were computed for** and are offered only for that combination. As with IDW, the target switch appears in every view that computes a predicted surface.
   - **OPTIMIZE TPS LAMBDA runs in the background** (see 2.a), with the same responsiveness and one-at-a-time rules.
   - Manual override is available. Setting `Lambda = 0` forces exact interpolation with no smoothing.

## Mapping: Domain & Grid

Where the surface is predicted and at what cell size. These are separate decisions from the model itself: the same engine can be evaluated over a tight hull or a buffered one, on a coarse grid or a fine one.

**1. Define the grid resolution**
  Resolution is the pixel size of the final map. Resolutions and their suggestions are always in **metres**, even under a geographic mapping CRS, because interpolation always runs in a projected CRS.
* **Auto (Per Locality):** each locality's grid is sized from that locality's **own mapped area**, about 100,000 pixels inside its boundary, clamped to 5-1000 m before the candidate-cell guard below. Small fields get fine grids and large ones coarser grids.
* **Auto (Global):** every locality gets **one pixel size**, the size the largest locality would get under Auto (Per Locality), and the grids are aligned to one shared lattice. Example: a 2 km² field and a 200 km² field get 5 m and 45 m under Per Locality; under Global both get 45 m. Use it when the localities' maps must be compared or merged cell for cell. The alignment holds when the localities share a working CRS and the Target Mapping CRS is that same system; reprojection into another CRS resamples the surfaces. The 4-million-cell guard below applies here too: a locality whose extent would need more than that at the shared size is coarsened, and the size used instead is reported in the progress panel, as a notification and in the run log. If the shared size is too coarse to put a single pixel centre inside a small locality, that locality is skipped and the run log says so.
* **The pixel size is set when the run starts**, because it follows the boundaries the run builds, so the per-locality table under the selector reads *set at run* in the Auto modes. After a run, the **resolution overlay** in the Map Viewer (Overlays menu) lists the pixel size each locality was built at, and the run configuration records it. The table's buffer column shows the dynamic buffer: in the Auto modes it follows each locality's own point spacing, and under Fixed resolution it is computed from the cell size you set. Auto resolution ignores the **Fixed** slider entirely.
* Pixels are always square and exactly the stated size: the grid grows by whole pixels until it covers the boundary.
* **Fixed:** manual control, 1 to 500 m. It arrives pre-filled with a value derived from your samples - half their mean nearest-neighbour distance, or the data extent divided by 300, whichever is larger - which you are free to overwrite.
    * **Low values (near the 1 m minimum):** high detail, high RAM use, longer processing.
    * **High values (50-300 m):** faster, but local variation may be lost.
    * As a guard, a resolution that would produce more than roughly 4 million grid cells across the map extent is coarsened automatically, and the locality and the size used instead are named in the progress panel, as a notification and in the run log. This applies in all three modes; ordinary resolutions are used exactly as set.
    * The opposite extreme is also caught: a resolution so coarse that no grid node lands inside a locality's boundary, easy to hit with a tight Strict Point Buffer, skips that locality with a run-log warning naming the cause instead of producing an empty map.

In every mode the per-locality summary table under the slider, and the on-map resolution overlay, follow the current locality selection.

**2. Borders and polygoning logic**
   Define the analysis envelope so the model does not interpolate indefinitely:
* **Concave hull:** shrink-wraps the boundary to the outer perimeter of the points. Best for irregularly shaped fields.
* **Convex hull:** a rubber-band boundary. Best for simple, rectangular fields.
* **Buffered:** a smoothed buffer around the concave hull, so the map covers the field edges.
* **Point buffer:** individual buffers around every point.
* **Buffer Logic (Buffered only):** *Auto (Dynamic)* scales the buffer with the resolution and the method (1x for TPS, 2x for IDW, 3x for the kriging engines, kept between 5 and 2000 m); *Fixed (Manual)* uses the Buffer Distance below.
* **Buffer Distance (m):** how far the map extends beyond the outermost samples, and the circle radius in Point buffer mode (default 250 m).

**Match the buffer to the cell size in Point buffer mode.** A grid cell is drawn only when its centre lies inside the boundary, and in Point buffer mode the boundary is just the circles around your points. A sample can sit up to half a cell diagonal from its own cell's centre, so keep the buffer at or above **resolution ÷ 1.41** (equivalently, resolution at or below **buffer × 1.41**). A 175 m buffer on a 350 m grid falls short, and roughly a fifth of isolated samples then appear as points sitting on blank map. The sidebar flags the mismatch under the resolution table when resolution is Fixed, and every run re-checks it against the resolution actually used, raising a notification and writing the corrective numbers to the run log. An uploaded boundary shapefile takes over wherever it matches a locality, so the advisory then concerns only the localities it does not cover. Lowering the resolution is usually the better fix, since widening the buffer enlarges the area the map claims to cover.

*The Boundary Type, Buffer Logic and Resolution Logic configured here apply to **interpolation runs only**. The Classification Suite has its own boundary, buffer and resolution controls in its Spatial Scope panel.*

## Running a Model

**Execution and run estimation**
   - **Run estimate:** the line directly above the **Run Interpolation** button states what the next run will cost before you start it - the estimated duration, how many locality models it will fit, how many points they cover, and the method it will use. It follows every change to the sidebar, and the confirmation dialog reads the same estimator, so the two never disagree.
     - **History-aware:** with enough prior runs logged for the chosen method, a linear model predicts runtime from sample counts.
     - **Cold start:** without history, base multipliers are used. RFK (1.0x), RK (1.0x) and CK (1.3x) are calibrated from real measurements; OK (0.5x), IDW (0.5x) and TPS (0.3x) are unverified estimates based on theoretical complexity.
   - Click **Run Interpolation** and move to the **Map Viewer** tab. The app cross-validates under the strategy selected in 1.b, generates the surface, and populates the performance table with RMSE, R², Moran's I and the rest. Both the cross-validation seed and the Moran neighbour count are hardcoded; see Scientific Guide Sections 9.1 and 9.2 to change them.
   - **What the Map Viewer shows while a run works:** a panel naming the method being interpolated, a progress bar, and a four-entry phase strip - *Validate*, *Fit variogram* (*Fit model* for IDW and TPS), *Predict grid*, *Cross-validate*. The entry in progress is highlighted and finished ones turn green. The strip reads the same per-locality checkpoints as the bar, so it advances with the slowest locality rather than the first. IDW and TPS cross-validate before writing their surface, so for those two the last two entries light in the reverse order to the work. The panel stays on screen until the run finishes and you press **Reveal Maps & Enable Analysis**; the rest of the app is usable throughout. When the run completes the button reads *Interpolated* and stays disabled until you reveal the results, so a second run cannot overwrite surfaces you have not looked at yet; revealing them hands the button back as **Run Interpolation**.
   - **Cancelling a run:** the cancel takes effect at the next checkpoint. Checkpoints sit before each locality's Actual and Predicted surfaces and, for RK and RFK, between covariates as they are interpolated onto the prediction grid. The covariate stage is often the longest stretch of a multi-covariate run, so a cancel there is picked up after the current covariate finishes. Starting a new run before the cancelled one has reached its next checkpoint does not revive it: each run carries its own cancellation flag, so the cancelled workers still stop and free their cores for the new run.
     - **A cancelled run is labelled as one.** The results that were on screen were archived or discarded when the run started, so there is nothing to fall back to. The configuration panels read **Run #N - CANCELLED**, with a note that the settings shown are what was requested and that no surface, metrics or exports were produced; the Model Performance table carries the same note instead of empty rows, the header chip reads *Cancelled*, and the Run Log ends with the cancellation. A cancelled run is never archived. To bring back an earlier result, restore it from the Run History Archive.
   - **Too many covariates for the sample size:** Regression Kriging fits one coefficient per covariate plus an intercept, so both the main fit and each cross-validation fold need more points than that. If a locality or a held-out fold falls short, the run says so explicitly, naming how many points are needed against how many exist, instead of returning blank `NA` metrics. Reduce the covariate count, add samples, or pick a strategy with smaller held-out folds.
   - **Failed regions:** if one or more localities error out, a single summary dialog lists **every** failed region with its full error text. Per-region error notifications appear alongside it, and the full text is retained in the run log.
   - **Results assembly errors are reported separately from model errors:** once the parallel workers finish, the app still has to merge rasters, build tables and register export items in the main session. A failure in *that* stage opens a **Results Assembly Failed** dialog stating that the models themselves completed and that maps, tables or exports may be incomplete.
   - **Automatic fallbacks:** if an engine cannot be fitted for a locality (TPS on a degenerate point layout, or a CK/RK/RFK model failure), the app falls back to a simpler engine and reports this in the run log and as a warning notification. Check the log if a map looks different from the method you selected.
     - **The affected diagnostic panels say so in place.** A fallback leaves a locality without the diagnostics belonging to the method you chose: a fallen-back RK locality has no trend model, an RFK one has no forest. The Trend Model Summary, RK coefficient table and RF Variable Importance panels state that the locality's trend model was not fitted and point you at the log. The per-locality residual variogram is titled *Variogram of Measured Values - Ordinary Kriging Fallback*, because after a fallback the fitted variogram describes the measured values, not model residuals. A cross-validation row that could not be computed is labelled "CV unavailable" rather than shown as blanks. Likewise, if an uploaded boundary shapefile cannot be applied to a locality (projection failure or no spatial overlap), the run proceeds with the point-derived boundary and says so in the progress warnings.
   - **Copying a table:** every result table carries a copy button in its title row, the counterpart to the download button on each figure. One click puts the table on the clipboard as both a formatted HTML table and tab-separated text, so pasting into Word or Google Docs gives a table and pasting into a spreadsheet fills cells. What is copied is what is displayed, at the displayed rounding, headers included, and every page of a paginated table rather than only the page on screen. The button turns into a tick when the copy succeeds; a table that holds only a status message ("No data for this selection.") is reported rather than copied. It works on every table on this tab and in the Classification, Exploratory and Governing-Factors suites.
   - **Responsive diagnostic views:** validation diagnostics that do not apply to the active engine or the current view (RF Variable Importance, internal residual variogram, TPS GCV plot) are hidden rather than rendered blank.
   - **Directional Variogram (anisotropy check):** a panel in the Scientific Analysis tab, shown for **every** engine including IDW and TPS, which fit no variogram of their own. It recomputes semivariance separately in four compass directions (N-S, NE-SW, E-W, NW-SE) instead of pooling all pairs regardless of orientation. Two switches above the plot choose what it is computed on. **Data** picks the measured values or, when the run mapped an uploaded prediction column, those predictions (the second choice appears only for such a run). **Computed on** picks the values themselves or the cross-validation residuals of that surface; residuals are the more informative view for RK and RFK. Reading the measured and the prediction side against each other shows whether your ML model kept the field's directional structure. The two *Computed on* choices do not have the same precondition: values are read straight from the uploaded table and plot whenever that column is filled, while residuals exist only where that surface's interpolation **and** its cross-validation both completed. So a surface whose run failed can still show its values and correctly report no residuals; the panel says so, and the Run Log on the same tab carries the cause. If the four curves reach their plateau at clearly different distances, the field's structure is directional and a single range under-describes it. This is a diagnostic only: all engines remain omnidirectional, so nothing on the map changes because of what you see here. Treat a strong split as a caveat to report, not a setting to adjust. Select a locality to compare directions within one field, or "Total (Combined)" to pool every locality in the run.
   - **RK linear trend panel:** for Regression Kriging runs, the Scientific Analysis tab shows the trend model as fit-statistic chips (R², adjusted R², residual standard error, F statistic with p-value, sample size) followed by a sortable coefficient table with each covariate's estimate, standard error, 95% confidence interval, t value, p-value and significance code. Select a specific locality in the analysis filter to view it, since trend models are fitted per locality. The R console summary sits under the collapsible *Raw R model summary* link. The export registry holds this same coefficient table, plus a second sheet with the fit statistics from the chips. **Read the p-values with care:** they come from OLS and assume independent residuals, while RK kriges those residuals precisely because they are spatially autocorrelated, so the standard errors are biased low and covariate significance is overstated. The panel repeats this note in place. The estimates themselves are unbiased; gauge the severity from the residual Moran's I in the Model Performance table.

## Mapping: Map Styling

**Colour palette configuration**
- The **Color Palette** picker holds fourteen scales: Viridis, ten sequential Brewer ramps (Greens, Blues, Oranges, YlOrRd, PuBuGn, Purples, GnBu, YlGn, YlOrBr, Greys) and three diverging ones (RdYlBu, BrBG, Spectral). A variable whose name or label reads as a nutrient (TN, P, K, Ca, Mg, Fe, Mn, Cu, Zn) opens on a ramp of its own; other variables open on the ramp their data category implies, or YlOrRd.
- Styling can be changed before or after generating the interpolation models. Switching between Continuous and Binned, changing the palette, or moving between a surface and its SE or variance view in the View dropdown restyles the displayed maps **in place**: the base map, zoom level and overlays stay put and only the coloured surface layers and the legend are re-encoded. A pulse bar at the top of the page and spinners on the statistics tables show when the app is working.
- The **basemap dropdown** on the Map Viewer toolbar (Satellite, Topographic, Standard Street, Dark Matter, Light) swaps the imagery under the interpolated surface without redrawing the map: the surface, the overlays, the zoom level and the pan position all stay where they were. All five basemaps cover the same zoom range, so a switch changes only the imagery; the shallower providers (Topographic in particular) upscale their deepest tiles rather than dropping out when you are zoomed in past what they publish. **Satellite (Esri)** is the default here and on the Data Setup validation map, and it is what the app opens on.
- A variogram warning banner on the Map Viewer describes only fits used by the displayed run. Tuning another locality or preparing the next run does not change that banner; IDW and TPS maps have no variogram-fit banner. It carries one band per condition, and each asks for something different:
    * **Variogram fit failed** (red): no candidate model could be fitted and a default spherical model was used, so the map's spatial structure was not estimated from your data. Treat the surface as indicative and look for the cause in the Run Warnings card on the Scientific Analysis tab.
    * **Auto-fit selected a non-converged or singular variogram** (amber): a model was fitted but the solver did not settle. The map is usable; the variogram parameters are imprecise. Compare families in **Manual Tuning**.
    * **Variogram range not resolved within the empirical lag window** (amber): the fit converged, but its range falls outside the distances your empirical lags can resolve. *Practical range extends beyond sampled lag support* means the sill is extrapolated past the observed spatial support. *Practical range is below sampled-distance resolution* means it falls below the application's effective short-range resolution threshold and behaves as near-pure nugget; this threshold is not a claim about the actual minimum point separation. The map is the best available description of the data - what is limited is what may be read off the model. A wider survey extent addresses the first, denser short-range sampling the second.
    * **Sill not observed; possible large-scale trend** (amber): the empirical variogram is still climbing at the cutoff. This can mean long-range dependence or non-stationarity, and the variogram alone cannot separate them. Consider **Regression Kriging** with covariates that capture the systematic trend, which fits the variogram to the residuals instead.
    * **Gaussian or Matérn model with a nugget below 5% of the sill** (amber): predictions can land far outside the observed range. Check the map against the data or add a nugget.
- **Structural Dependency can read "Not reliably identified."** The percentage is derived from the fitted sill, and where the model reaches that sill beyond the longest lag your samples cover, the sill was never observed. The cell then says so and carries the model-extrapolated figure on hover; the Practical Range cell is qualified the same way. The exported sheet keeps the number and adds `Max Lag` and `Sill Resolved` so a reader can see which rows are supported. Both are blank for a model you applied by hand: there the parameters are your choice, not a fit.
- **Hollow map points carry no measured value.** The sampling-point overlay shows every point of the displayed run, and a point whose measured value is missing was not used to fit the surface. Those points render as an open grey outline with no fill, they are named in the point legend, and their pop-up says so. The count of points on the map can therefore exceed the *n* the Model Performance table reports.
- The last two entries, **Dark Matter (key)** and **Light / Positron (key)**, come from CARTO, which now requires a free API key for them. Selecting either opens a **CARTO API key** box beside the dropdown; paste your key there (request one at carto.com/basemaps/apikey) and the map reloads with it. Without a key the tiles still draw, but CARTO stamps an "API key required" watermark across them. The key is used only to request tiles for the current session: it is not saved into a run configuration, an export or the run history, so re-enter it after restarting the app. The other three basemaps need no key and ignore the box.
- Choose a classification method:
    * **Continuous:** best for raw gradients.
    * **Binned (5):** splits the displayed value range into five equal-interval bands. Applies immediately.
    * **Agronomical:** class-based management zoning. Selecting it reveals the algorithm picker (Supervised thresholds, Jenks, or K-Means; Jenks 1967; Hartigan & Wong 1979), the class-count slider, and for Supervised the limit boxes with a hint showing the displayed surface's value range. All are editable freely, because nothing recomputes while you adjust them. Press **Apply to maps and statistics** to commit: the maps restyle and the class-area and classification-performance tables recompute in one pass. The button greys out and reads "Applying..." until that pass finishes. An amber note appears whenever the staged settings differ from what the maps show. Applying re-encodes every visible map layer and recomputes class areas, so expect a few seconds of work, longer for multi-locality or comparison views.
        * Jenks and K-Means breaks are computed with a fixed internal seed (Jenks on a seeded subsample for large rasters), so re-applying the same settings reproduces the same class limits. Above roughly 500,000 cells the interactive viewer shows a resampled preview for responsiveness; exports, GeoTIFFs and all area and classification statistics always use the full-resolution raster.
        * Applying the agronomical classification enables the **Agronomical Classes** setting of the *Classification Performance (Uploaded Predictions)* table in the Scientific Analysis section; that table's other setting, **Quartiles**, bins observed and predicted values into quartiles and needs no map classification at all. Applying also registers the class-area and classification-performance tables for export, for both surfaces and every locality of the run, so the styling can be chosen after the run without losing them; re-applying different class limits replaces those sheets rather than adding a second set.

## Finalizing & The Export Registry

The Export Registry standardizes outputs for reports and presentations.

- Open the export styler for individual downloads after choosing a single result, or select several results for a batch download.
- All tabular results selected are written into a single `.xlsx` file with one sheet per table, named after its locality and table. Sheets carry a bold, frozen header row and columns sized to their content, and every statistic is written as a full-precision number, so the values sort, chart and compute without retyping. The cards round for reading; the sheets do not.
- **File names say which run a file came from:** `Export_<item>_<method>_<timestamp>` for a single download and `Batch_<item>_<method>_<timestamp>` inside a batch zip, where the item names the locality for a per-locality result. Exported map figures are titled with the variable, the product and the method (for example *Total N - Actual Map - Ordinary Kriging*), and their legend names the variable and its unit, as the Map Viewer's does; an uncertainty or residual map's legend says so (*SE: ...*, *Variance: ...*, *Resid: ...*). The two ML-prediction error maps carry no method: they are interpolated with a fixed IDW power, whatever engine the run used.
- **Combined area totals require disjoint locality domains.** If locality boundaries overlap by more than 0.5 m², the table explains why no combined total is reported. Use the per-locality area tables; the unavailable total is omitted from exports.
- **The registry holds every table the Scientific Analysis tab shows.** Per locality: descriptive statistics (actual and predicted side by side), prediction performance, classification agreement, model CV metrics (actual and predicted), fold-realization stability where repeated CV was used, class-area coverage for both surfaces, the empirical variogram points, the fitted variogram parameters, the TPS GCV grid, the RF importance table with every importance measure the forest recorded, and the RK coefficient table with its fit statistics. For the run as a whole: pooled CV metrics for both targets, pooled fold-realization stability, the fitted variogram parameters of every locality in one sheet, the IDW power / TPS lambda listing, total descriptive statistics, total prediction performance, total classification performance, and total class-area coverage for both surfaces. Each is the table its card shows, with the same labels. Three add what the screen shows another way: the CV metrics sheet adds the fold plan, the cross-validation population with its ID, what the folds re-estimated, the expected and predicted sample counts with coverage, and Moran's E[I], all as columns; the fold-realization sheet splits mean and SD into two columns and carries the expected count with the minimum and maximum predicted; and the RK coefficient sheet gives the p-value as a number and the confidence interval as two columns.
- Class-area and classification-agreement sheets follow the map classification: Binned styling adds the class-area sheets as soon as it is selected, Agronomical adds them, and the agreement sheets with them, when you press **Apply to maps and statistics**, and changing the classification or switching to Continuous replaces or removes them, so an export never mixes two classifications.
- **Variogram Parameters** reports the range parameter *a* and the **practical range**, the distance at which the model reaches 95% of its sill. Compare localities on the practical range: *a* means a different distance for each model family (an exponential reaches its sill at 3*a*, a spherical at *a*). A Matérn model shows its smoothness beside the model name.
- **Download Run Configuration (.json)** writes a machine-readable record of the run currently in the registry: every model setting (method, localities, view, the **Input Data CRS** the coordinates were read in and the **Target Mapping CRS** the surface and exports were produced in, boundary and resolution logic, cross-validation strategy, the cross-validation population, the per-fold model refit and covariate screen, the variogram fitting mode and, when a Predicted surface is mapped, the Actual/Predicted sharing choice (Ordinary Kriging, IDW and TPS), the resolved collinearity gate including a "Keep All" override, the covariates you selected and, per locality and surface, the ones the model used and the ones the collinearity screen removed, and the method-specific parameters: IDW power and neighbours, TPS lambda, CK neighbourhood, RFK trees and uncertainty method), the per-locality tuning values the run consumed (the IDW powers of an IDW run, the TPS lambdas with their effective df of a TPS run), and the software provenance (app version, R version and platform, and the versions of sf, gstat, fields, randomForest and terra). Keep it beside the exported maps: it is what lets you reproduce a surface months later, and it supplies the parameter list a methods section has to state. The file always describes the **current** run, so download it before starting the next one, or restore an archived run from the Run History Archive first. It is a record, not a setup: **Load config** refuses it by name and reads only the session configuration that **Save config** writes.
- **Run History Archive.** When a run starts while results are on screen, a dialog asks whether to archive or discard them (tick *Remember my choice* to stop being asked). Up to three runs are kept, the oldest dropped first with a notification: an archived run holds its full-resolution surfaces, which can take several hundred megabytes of memory for a large multi-locality run. **Restore** puts an archived run back as a whole: its maps, the Scientific Analysis tables and plots, its run log and warnings, the configuration panels and the export registry all describe that run again, and the run on screen goes into the archive in its place. A restore is refused while a run is in progress. A cancelled run is never archived.

**1. Accessibility and themes**
   - In the export styler's **Advanced** tab, under **Publication Modifiers**, tick **High Contrast Palette (Colorblind Safe)** for colourblind compliance.
   - Residual and error maps use a zero-centered diverging palette selectable under **Residual / Error Maps** in the Basic tab (default Red-Blue). With the high-contrast option on, a non-colourblind-safe choice is replaced automatically by Purple-Orange.
   - Two error-map assets are registered per run with uploaded predictions: the **Point Error Map** (discrete errors at the exact sample locations, matching the Map Viewer's Point Residuals panel) and the **Interpolated Point Errors Map** (the IDW surface of those errors).
   - **Uncertainty products (Variance and SE maps) are registered for the kriging engines only:** OK, RK, RFK and CK. IDW and TPS are deterministic weighting and smoothing interpolators with no prediction-variance model, so a run using either has no uncertainty item in the registry and no uncertainty band in its GeoTIFF. This matches the Map Viewer, whose View dropdown offers SE and variance maps only for a kriging run.

**2. Typographical scaling and advanced options**
   - Advanced options give individual size and orientation control over every figure element, and the configuration can be saved for future sessions.
   - Sizes are **points** and margins are **millimetres**, both physical: a 16 pt title is 16 pt on the page. Nothing is rescaled at export time, so the size you set is the size you get at any DPI and any export dimensions.
   - The **preview is the export figure**, drawn at the width and height you set and then scaled as a whole to fit the preview pane. Nothing is cropped: if an axis label is crowded or clipped in the preview it will be crowded or clipped in the file, so widen the figure, shrink the type, or angle the labels until the preview looks right.
   - **Legend placement follows the item.** An Actual vs Predicted comparison opens with a horizontal legend beneath its two panels, where a right-hand legend has no room; every other item opens with the legend on the right. This is applied on top of the remembered styling each time the styler opens, so a legend position set by hand holds for that session but is not carried onto a differently shaped item. A configuration you load with **Load Config** overrides it.

**3. DPI configuration**
   - Set **Export DPI** under **Output Quality** (72 to 600, default 300): 72 for quick sharing, 300 for internal reports and printing, 600 for journal submission.
   - DPI changes the pixel count only. Layout, type size and margins are identical at 72, 300 and 600 DPI.

**4. Download**
   - Select the format (`PNG`, `TIFF (image)`, `PDF`, `JPEG`, or `GeoTIFF (data)`) and click **Finalize & Download**.

**5. GeoTIFF: the data rather than a picture of it**
   - **GeoTIFF (data)** appears in the format list only for registry items that are a single raster surface: the Actual and Predicted maps, the residual Delta map, the Interpolated Point Errors map, the variance and standard-error surfaces (kriging runs only), and any Quick Export of those views. It writes the raster values, CRS and extent of the surface as displayed, in the run's Target Mapping CRS, ready for QGIS or ArcGIS.
   - **Each band carries its real statistics** (minimum, maximum, mean, standard deviation and the share of cells with a value), which GIS software reads for its default stretch, and the file names its run in metadata tags: `MONOLITH_VARIABLE`, `MONOLITH_UNIT`, `MONOLITH_PRODUCT`, `MONOLITH_METHOD`, `MONOLITH_LOCALITY`, `MONOLITH_RUN_ID`, `MONOLITH_APP_VERSION`, `MONOLITH_TARGET_CRS` and `MONOLITH_CREATED` (a tag with no value, such as a unit the variable list does not give, is left out). Both are stored inside the `.tif`; no `.aux.xml` sidecar is needed. QGIS lists them under *Layer Properties > Information*, and `gdalinfo` prints them. If a GDAL build cannot write them, the file is still written with its values, and a notification and the Run Log say the tags are missing.
   - Because it carries values rather than a rendering of them, **no styling applies**: typography, palette, DPI, dimensions and the preview all switch off while it is selected. Symbolise the layer in your GIS instead. **Kriging** surfaces are written as multi-band files, band 1 the prediction (`var1.pred`) and band 2 the variance (`var1.var`), with layer names kept as band descriptions; a standard-error export is a single band named `var1.se`. **IDW and TPS** surfaces are single-band prediction rasters, since neither engine produces a variance.
   - Two map items are **not** single rasters and stay image-only: the **Actual vs Predicted Comparison** (a pair of surfaces) and the **Point Error Map** (point geometry). The styler says so when one is selected. Export the Actual and Predicted maps separately for the first; for vector geometry use **Class zones** and **Drawn polygons** in the Map Viewer's Downloads menu.
   - In a batch export, GeoTIFF applies to every raster item selected; anything else in the same batch is written as PNG, and the Run Log records which items that happened to. Tables continue to be merged into the single Excel workbook, and a table that cannot be written costs only that worksheet: the Run Log names it and the rest of the batch, figures included, still downloads.

## Classification Suite

Tab 6 trains a supervised multiclass classifier from co-sampled covariates, either on an existing categorical column or on a continuous variable binned into ordered classes (quantile, equal-interval or Jenks breaks). Method details: Scientific Guide Section 10.

The suite is self-contained: while this tab is active the interpolation sidebar is hidden and replaced by a short notice. Everything a classification run needs (target, predictors, localities, boundary, buffer, grid resolution) lives in the suite's own left-hand panel and never interacts with the interpolation configuration.

**Setup**
- The **Target** selector opens on *Bin a continuous variable*, because most soil datasets carry no text or factor column to classify. Switch to *Categorical column* if yours does.
- Choose the target, one or more covariates, and a method (Multinomial Logistic Regression, Random Forest, or Extreme Gradient Boosting / XGBoost; Venables & Ripley 2002; Wright & Ziegler 2017; Chen & Guestrin 2016). Random Forest is the default. For two-class targets the multinomial option automatically fits the statistically equivalent binomial logistic regression.
- Only text and factor columns are offered as categorical targets. Numeric columns are always treated as continuous, even when they carry few distinct values, as coarse climate-raster covariates often do. If your classes are stored as numeric codes, recode them to text or use the binned-target mode.
- **Collinearity guardrail:** an amber note under the covariate picker warns when the selected covariates are redundant *within the current spatial scope*, and at run time the same Auto-Drop / Keep All / Cancel dialog appears that the kriging engines use. The screen is method-aware: iterative VIF > 10 for most learners, but a stricter VIF > 5 when **Random Forest** is selected (James et al. 2013; O'Brien 2007), because moderate collinearity that barely hurts RF predictions still splits the permutation importance between the correlated covariates and makes the true drivers look weak. *Tip: five flavours of the same elevation layer add no information and only smear the importance chart across near-duplicates. Prefer dropping.*
  - **What Auto-Drop does:** the screen runs again on the training rows of every cross-validation fold and tuning resample, so the reported accuracy includes the screening step, and once more on all rows for the final model. The map, the importance of the final model and the downloadable model use the covariates that last screen keeps. Out-of-fold importance follows the same rule per fold: a covariate a fold dropped is not scored on that fold, and one no fold kept is absent from the importance chart rather than shown as a zero bar. The run summary names them and says how many folds dropped each covariate, which can differ from the list in the dialog: the dialog screens the scoped data before the run, while the models screen complete rows only.
- **Balance classes (inverse-frequency weights):** when rare classes matter (100 "healthy" against 5 "diseased"), tick this so each class contributes equally to the fit instead of the model defaulting to the majority. Metrics stay unweighted; expect slightly lower overall accuracy in exchange for better rare-class recall. Not supported by the multinomial learner, which then fits unweighted and says so in the run badge. Every fit, including each cross-validation fold and each tuning resample, computes its weights from its own training rows. *Tip: weighting is a stopgap, not new information. The real fix for a 5-sample class is more field samples.*
- **Cross-validation:** Spatial (blocked) clusters nearby points into folds so reported accuracy reflects prediction into unsampled areas. Standard (random k-fold) is usually optimistic under spatial autocorrelation. Each fold reconstructs its held-out covariates from training points, just as the map reconstructs grid covariates, so the reported metrics validate the map task even when **Predict maps** is off. The extra kriging can lengthen runs, especially with many covariates or folds.
- **Hyperparameter tuning:** None fits fixed defaults (fast, deterministic); Light and Full search a grid over the folds. The search uses whichever cross-validation strategy you picked, for the scored folds *and* for the final model behind the maps and the exported bundle, so a Spatial CV run tunes under spatial folds throughout.
- **Use nested CV (slower):** appears once tuning is enabled. By default the same folds both choose and score the hyperparameters, which is mildly optimistic; nested CV instead re-runs the grid search inside every fold, on 5 inner folds built from that fold's training rows only, so the reported metrics honestly include the tuning step (Varma & Simon 2006; Cawley & Talbot 2010). Expect roughly 5x the tuning runtime, and the badge then shows "(nested CV)". *Tip: use it for the run you intend to report or publish; the quick estimate is fine while exploring.*
- **Feature importance scored on:** choose whether permutation importance is measured **Out-of-fold** (default) or on **Training rows**. Out-of-fold reuses each fold's own model and shuffles predictors only in the rows that fold never saw, so importance is measured under the same honest design as the reported accuracy. Training-row scoring is the conventional default but rewards a flexible model for memorising its training data. Both cost the same, and the design in force is written on the importance plot's axis and into the exported metrics CSV. Switching this control cannot change the reported performance: the shuffles run in their own isolated random stream, so accuracy, kappa, the confusion matrix and the per-class table come out identical either way. *Tip: the two designs are not comparable numbers, so do not read an out-of-fold importance against a training-row one.*
- If the scoped data are thin, the run warns, naming which classes have fewer than 3 samples and their counts, but still proceeds. Results for those classes will be unreliable: widen the scope, merge or exclude rare classes, or use fewer classes for a binned target.
- A second warning can appear when the run finishes, naming classes that **some cross-validation fold had no training samples of**. This is normal with Spatial (blocked) CV, whose folds are geographic blocks and cannot be balanced by class: a class confined to one part of the area ends up wholly inside one block, and the model trained without that block cannot predict it. Those samples count as errors, so the reported accuracy for that class reads worse than the model deserves. The run is still valid; read the per-class table with the warning in mind. To avoid it, use fewer classes, prefer quantile over equal-interval breaks (equal-interval bins can be nearly empty on a skewed variable), switch to Standard CV if an in-domain estimate is what you want, or widen the scope.
- Jenks target breaks are reproducible, including the internal sampling used above 3,000 points.
- Binned targets can produce an interval containing no samples at all, most often with equal-interval or Jenks breaks on a skewed variable. Empty classes are dropped automatically, so the class count behind the maps and tables can be lower than the "Number of classes" slider. The run summary always reports how many classes were actually modelled.
- **Predict maps** additionally predicts class, per-class probability and uncertainty (entropy) surfaces on a grid. Boundary type, buffer logic and grid resolution are set in the suite's own **Spatial Scope** panel. If a fixed resolution is too coarse for a small scope, so that no grid cell lands inside the boundary, the run stops with a clear message instead of predicting over the whole bounding box. Reduce the resolution or widen the scope.
- **Run progress and cancellation:** the running panel shows a live progress bar captioned with the stage actually running: interpolating held-out covariates, hyperparameter tuning, cross-validation fold *k* of *n*, the final model fit, permutation importance, building the prediction grid, interpolating covariates onto the grid, and classifying the grid cells. Covariate interpolation can dominate either validation or a large map, and the bar advances through both stages.
  - *First run of a session:* before any stage appears the caption reads "Starting (loading modelling libraries, first run ~30s)". The classifier runs in a background process that must load the modelling libraries from scratch the first time it is used, roughly 30 seconds; later runs in the same session reuse the warmed process and start almost immediately. The rest of the app stays open during this wait, though other on-screen analyses may respond sluggishly while the libraries load.
- The **Cancel Run** button takes effect at the next checkpoint. Checkpoints sit between cross-validation folds, between covariates during grid interpolation, and between blocks of grid cells during classification, so a cancel is usually picked up within a few seconds. The exceptions are the two black-box search steps, a tuning grid search and a single covariate's kriging, which must finish first. Once cancelled the run stops and no partial results are kept: the Run Classification button becomes available again and the previous run's results stay on screen.

**Spatial Scope**
- The **Localities** picker restricts the run (training, cross-validation, binning breaks and the predicted maps) to the chosen localities. It is specific to this suite: it starts with all localities selected and is never overwritten by the sidebar Context panel, so the scope you set here is the scope the run uses. Leaving it empty means all localities.
- **Boundary Type / Buffer Logic / Grid Resolution** live in this panel and apply to classification maps only: Concave Hull (default), Convex Hull, Wrapped (Buffered, with dynamic or fixed buffer distance), or Strict Point Buffer, applied per locality in scope. The grid is either Auto, a cell size derived from the boundary area targeting about 50,000 cells, or a Fixed cell size in metres.
- **A very fine cell size over a wide scope is coarsened.** The grid is laid over the bounding box of the whole scope before it is trimmed to the boundary, and that box is far larger than the mapped area when the selected localities sit far apart. If the cell size you ask for would need more than 4 million cells to cover the box, the run enlarges it to the smallest size that fits and tells you the value it used, both in the live scope note and as a notification when the run finishes. The mapped area is unchanged; only the cell size is.
- Once at least one polygon exists, drawn with the map toolbar or uploaded as a shapefile, a **Polygon scope** control appears: *Ignore polygons*, *Within localities* (points must lie inside both the selected localities and a polygon), or *Polygons only* (the locality filter is ignored).
- The live "In scope: x of y georeferenced points" note shows exactly what the run will use, and turns red below 20 points. Under Strict Point Buffer it is joined by a warning whenever the buffer is narrower than half a cell diagonal (**resolution ÷ 1.41**), which leaves isolated samples with no mapped cell beneath them; the note reads the effective cell size in both Auto and Fixed modes, and the finished run repeats it as a notification. It stays silent under *Polygons only*, where the domain is your polygons and the Boundary Type setting has no effect.
- The predicted maps cover the union of per-locality boundaries, or the polygons, so the classifier does not predict across unsampled gaps between distant localities.
- **Classification maps are always drawn in a metric projection.** Boundary buffers, grid resolution, cross-validation block sizes and class areas are all metres, so if your Target Mapping CRS is geographic (WGS 84, degrees) the run is computed and mapped in the WGS 84 UTM zone your data falls in, and the scope note says which one. The maps, rasters and exports then carry that projection. Nothing else about the run changes, and a metric Target Mapping CRS is used as chosen if it passes the suitability gate. A non-metre projected target or red suitability verdict is refused.

**Results**
- The results panel is a 2 x 2 plot grid: Predicted Class Map and Prediction Uncertainty (normalised Shannon entropy; Shannon 1948) on top, Class Probability Map and Feature Importance below. All four sit in identical cards with the title and an expand control in a header row above the figure, so the frames line up and nothing is drawn over a map. Below the grid, a **Results table** dropdown switches between the tables (Model performance metrics first, then Confusion matrix, Per-class accuracy, Covariate lift, Performance by area, and Class area coverage). Options that do not apply to the run are absent from the dropdown; the CSV export always contains the full metric set regardless.
- **Click any map**, or the expand icon in its card header, to open it full-size at higher display resolution. The Feature Importance plot has the same control, which is the easiest way to read long covariate names. Three default-off **map display options** sit above the maps, beside the run badge: *Scale bar & north arrow*, *Show sample points* (the scoped training samples as white circles, useful for judging where the map is supported by data and where it extrapolates), and *Stretch colour scale*. All three apply to the on-screen maps, the expanded views and the styled PNG exports, and never alter the exported data rasters.
- **Reading a flat-looking map.** The entropy and probability maps are drawn on the absolute 0-1 scale, so the per-class probability maps are comparable with each other and entropy is comparable between runs. A model with little skill keeps every probability near 1 / (number of classes) and every entropy near 1, and that narrow field renders as a single flat colour. Each map's subtitle states its observed range, and *Stretch colour scale* rescales the colours to that range to reveal the structure inside it (at the cost of comparability). The Predicted Class Map's subtitle reports how many of the modelled classes actually appear on the map and the share of cells taken by the largest one; the legend lists the classes present. One class covering the whole grid is the expected output of a model with no skill, so check Overall accuracy against the no-information rate in Covariate Lift, and Cohen's kappa, before reading anything into the pattern.
- **Model Performance** reports pooled cross-validated metrics with plain-language names: Overall accuracy, Cohen's kappa (Cohen 1960), Balanced accuracy, Precision / Recall / F1 (macro averages), ROC AUC (multiclass, Hand & Till 2001), Log loss, and Brier score (Brier 1950). The Estimator column states how each metric extends to the multiclass case, including the denominator a macro average was taken over (*Macro average (K = 3)*) or, for a two-class run, which class counts as the event. Precision, recall and F1 are averaged over **every** class present in the target: a class the model never predicts scores 0 rather than dropping out of the average, so all three share one denominator and a model that ignores a rare class cannot outscore one that finds some of it. The blue badge states the CV design, the scope, the number of rows used for fitting and CV, whether tuning was nested, and whether class weights were applied. Rows with missing targets or selected covariates are excluded from that count; a run without covariates excludes rows with missing targets.
- **Per-class Accuracy** lists the reference and predicted counts with producer accuracy (recall) and user accuracy (precision) per class. A class the model never assigned reads **no predictions** in the user-accuracy column rather than a blank cell, and the run summary under the results names it. The confusion matrix and class area coverage in hectares are their own dropdown entries. Class areas are true ground (ellipsoidal) hectares, the same basis the interpolation Area Coverage table and the class-zone export use, so re-measuring a class in a GIS on the flat map plane will differ by roughly a tenth of a percent.
- **Feature Importance** shows which covariates drove the map: permutation importance (Breiman 2001; Fisher et al. 2019), how much the model's log-loss worsens when one covariate is shuffled, with each bar's share of the total in percent. *Tip: read it together with the collinearity note, since correlated covariates split their importance. A bar near zero or negative is a covariate the model ignores; a covariate the Auto-Drop screen removed has no bar at all.*
- **Covariate Lift** benchmarks the model against two no-covariate baselines on the same CV folds: always-predict-the-majority-class (the no-information rate, with an info icon for the interpretation), and a spatial-only nearest-neighbour classifier. It states the accuracy difference in points and reads McNemar's test (McNemar 1947) for you: no significant difference, significantly more accurate, or significantly less accurate than spatial position alone. When the covariate model is significantly less accurate, the note points to the alternative: for a binned target, interpolate the continuous variable in the Spatial Engine and classify that surface; for a categorical target, switch the maps to *Spatial 1-NN*. Under random k-fold CV it also reminds you that random folds favour the 1-NN baseline, so re-check under spatial blocked CV. *Tip: if the lift is not significant your covariates add little beyond spatial position, and the map may look plausible while the covariates do no real work.*
- **Running without covariates (categorical targets only).** Leave *Covariates* empty and run: the classifier is then the spatial 1-NN assignment itself. You get its cross-validated metrics (class metrics only, no ROC AUC / log-loss / Brier), confusion matrix, per-class accuracy, per-area table, a *Majority-class baseline* table in place of Covariate Lift, and the 1-NN map with its class-area table and Class GeoTIFF. The method, tuning, class-weight and importance settings do not apply; there is no Feature Importance panel and no model download. A binned target still needs at least one covariate: without covariates, interpolate the continuous variable in the Spatial Engine and classify that surface.
- **Spatial 1-NN map (categorical targets only).** A *Maps show* switch above the maps selects the *Covariate model* or *Spatial 1-NN (no covariates)*, which gives every cell the class of its nearest sample. Its accuracy is the *Spatial baseline (1-NN)* row of Covariate Lift. It has hard classes only, so the entropy and probability panels show a notice, the confidence threshold is hidden, and the probability/entropy GeoTIFF downloads are hidden. The class-area table (captioned with the surface), the Class GeoTIFF download (`predicted_class_nn.zip`) and the Styled Maps PNG follow the selection. Each new run resets the switch to the covariate model.
- **Performance by Area**, shown when the scope spans multiple localities or polygons in polygons-only mode, splits the same out-of-fold predictions per area: n, Overall accuracy, Cohen's kappa, Balanced accuracy, macro F1 and **Classes (K)**, plus a Total row matching the headline metrics. An area's macro F1 is averaged over the classes that area actually holds, which is why K is printed per row: two areas' F1 scores are not necessarily over the same class set. NA appears where a metric is undefined for an area, and small-n areas deserve caution.
- **Confidence threshold (abstain below):** a slider above the maps, beside the probability-class picker. Cells whose best class probability falls below the threshold turn grey ("Unclassified") instead of receiving a weak guess, because a 34/33/33% cell is ignorance, not a prediction. The map, area table and class GeoTIFF update instantly with no re-run, and a note reports how many validation points would survive the threshold and how accurate the survivors are. *Tips: values at or below 1/(number of classes) can never trigger; 0.5 is a sensible start for 3+ classes; treat the grey cells as your next field-sampling plan.*
- Maps render once per run and are cached. They redraw only when a new run completes, another probability class is selected, the confidence threshold changes, or a map display option is toggled.

**Exports**
- **Class GeoTIFF + legend (.zip):** `predicted_class.zip` holds three files: `predicted_class.tif`, the class raster with the map's colour palette embedded, so it opens coloured in QGIS, ArcGIS and most image viewers; `predicted_class.tif.aux.xml`, where GDAL keeps the class names, so GIS software shows each code's class when the two files sit side by side; and `predicted_class_legend.csv`, the `ID,class` table that names the codes on its own. Keep the `.tif` and `.aux.xml` together when you move them. Honours the current confidence threshold.
- **Probabilities / Entropy GeoTIFF:** full-precision floating-point *data* rasters (values 0-1), never masked by the threshold. Like the interpolation GeoTIFFs, each band stores its real statistics and the file carries `MONOLITH_*` tags naming the target, the product, the method, the run and the app version. Generic image viewers show single-band float data in grayscale, so load them in GIS software and apply a colour ramp, or use the styled export below.
- **Styled Maps (PNG):** a zip of publication-style renders (300 DPI, 9 x 7 in) of the class, entropy and currently selected probability maps, with projected coordinate axes in metres. The scale bar, north arrow and sample-point options are honoured as toggled.
- **Metrics CSV:** every result table of the run in one file, with both the display name and the yardstick metric id per row, and a `scope` column separating the sections: the pooled metrics, the per-area rows, the baseline comparison (spatial baseline, majority class, covariate lift, McNemar p), the permutation importances, the **per-class block** (producer and user accuracy with the reference and predicted counts, marked *no predictions* where the model assigned a class to nothing), the **confusion matrix** cell by cell with its orientation written into each row's label, and the **class areas** of the surface on screen, named with the confidence threshold in force. The per-class block is what lets a reader recompute the macro averages and check them.
- **Download Model (.rds):** saves the trained workflow with its metadata, so an hour of tuning is not lost when the app closes. Reuse it on new data in any R session with the same package versions: `b <- readRDS(file); predict(b$workflow, new_data, type = "prob")`. `new_data` needs the covariate columns listed in `b$predictors`, and all preprocessing replays automatically. When Auto-Drop removed covariates, `b$predictors` is the shorter kept list and `b$screened_out` / `b$vif_threshold` say which ones went and at which threshold. *Tip: keep the bundle next to a note of your app version, since .rds files from different xgboost versions may not interchange.*
