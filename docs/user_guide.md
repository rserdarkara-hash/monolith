# User Guide

## Workflow at a Glance

Monolith is organised as six tabs. Four of them are the interpolation workflow, worked left to right:

1. **Data Setup** loads the table, maps coordinates and variables, and sets the CRS. No map is drawn and no run starts until the coordinates and the Input Data CRS are set.
2. **Map Viewer** shows the interpolated surfaces and carries the drawing and export toolbar.
3. **Scientific Analysis** holds the variograms, performance tables, residual diagnostics and the run log for the last run.
4. **Export** collects every map, table and figure the session produced.

**Exploratory** and **Classification** sit apart from that sequence, behind a divider on the right of the tab bar: both branch straight off Data Setup, read the loaded table directly, and ignore the interpolation configuration entirely. The Exploratory tab (descriptive statistics, correlation, PCA and Governing Factors) has its own guide, *Descriptive and Exploratory Suite*; the Classification tab is described under *Classification Suite* below.

The sidebar (Context, Spatial Engine, Domain & Grid, Map Styling, Session) configures interpolation runs. On the Exploratory and Classification tabs it is replaced by a short notice naming the active suite.

On narrow windows, the header's dataset status and action controls wrap onto additional lines.

Click an info icon (ⓘ) beside a control or card title to read what it does and how its choices differ; click anywhere else to close it.

## Data Ingestion & Configuration

The Data Setup tab presents the configuration as four numbered cards; the later ones appear once a dataset is loaded. The steps below follow those cards.

The application requires cleanly structured, georeferenced tabular data. Column headings (the first row) hold parameter titles (`tn`, `p`, `k`, `ph`, `som`, `clay`), categorical or grouping factors (`subset`, `texture_class`, `locality`), and coordinate labels (`x`, `y`, `lat`, `long`). Rows hold the data values.

**Step 1. Upload dataset**
   - Click `Browse...` to upload a `.csv`, `.xls` or `.xlsx` file of up to 30 MB. It must contain distinct columns for X coordinates, Y coordinates and at least one variable of interest.
   - **Variable List (Optional)** is a second `.xlsx`, `.xls` or `.csv` table (for example `samp_var_list.xlsx`) defining your columns: the column naming your variables is the one whose header contains `actual`, `column` or `variable` (the first column when none does), headers containing `label`, `name`, `display` or `ID` supply the readable labels used on every map and report, and headers containing `cat`, `group` or `type` file the variables into folders such as "Physicochemistry", "Remote Sensing" or "Terrain". Upload the dataset first (a list uploaded on its own is rejected): each row of the list goes to the column of the same name. A notification counts the variables matched and names the rows that found no column. What it produces is listed for review and editing under *Variable Mapping & Verification*, at the foot of the tab.
   - Under both sits an optional **Boundary shapefile** row with an **Upload .shp set** button. Most analyses never need it: the built-in boundary types (Concave hull, Convex hull, Buffered, Point buffer) are set in the sidebar once the dataset is loaded. To supply your own boundary, select the `.shp`, `.shx`, `.dbf` and `.prj` files together (up to 200 MB in total).
   - **A sample dataset ships in the app directory.**

      It arrives ready to run: **Locality** preset to Kale and Yorga (the two localities that the accompanying manuscript examines in detail), and both **Input Data CRS** and **Target Mapping CRS** preset to `EPSG:32635` (UTM 35N). One notification lists what was set; clearing the Locality box restores the full set, and either CRS can be changed like any other.

      `samp_data_1.xlsx` (paired with the variable list `samp_var_list.xlsx`) is a dataset with an associated manuscript submitted for peer review. It is provided strictly for demonstration, evaluation and testing of Monolith, and is **not** licensed for third-party use until that manuscript is formally published. On publication, these datasets will be released under the [Creative Commons Attribution 4.0 International (CC BY 4.0)](https://creativecommons.org/licenses/by/4.0/) license. Until then all rights are reserved and the restrictions apply to all third parties. Full terms: [sample_data/DATA_LICENSE](https://github.com/rserdarkara-hash/monolith/blob/main/sample_data/DATA_LICENSE).

**Step 2. Assign variables**
   - **X/Y coordinates:** select the columns holding longitude/latitude or easting/northing. A column is pre-selected only when its **whole** heading is a recognised coordinate name: `x`, `lon`, `long`, `lng`, `longitude`, `easting` for X, and `y`, `lat`, `latitude`, `northing` for Y (case and surrounding spaces ignored). If nothing matches, the first column stays selected and you pick the right ones. A row whose X or Y cell is empty, not a number or infinite has no position: it is left out of the maps, the spatial models and the Classification Suite, and the rest of its table is read as usual.
   - **Samples at the same location** (projected coordinates agreeing to the centimetre) are one sample location in every spatial model, the Classification Suite included, and on the map: each numeric value is the average of the rows that carry it. In the Classification Suite a text (class) column takes the location's most frequent class, and a location where two classes tie for most frequent has no class and is left out. The run log counts the merged locations, and a merged point's pop-up says how many samples it holds. Descriptive statistics and Governing Factors read the rows as uploaded.
   - **Locality/Grouping Column:** lists every column and pre-selects the first whose heading contains `loc`, `site`, `farm`, `id` or `group` (the first column when none does). Its values are the localities the sidebar's **Locality** selector offers, and each locality is modelled separately.

**Step 3. Coordinate reference system (CRS)**
   - **Neither CRS dropdown has a default.** Monolith identifies your CRS when the file carries the evidence to prove it, narrows it down when it does not, and never assumes a zone. The shipped sample dataset (Step 1) is the only exception.
   - **How identification works.** Coordinates inside ±180/±90 *could* be degrees, but a local grid in metres (a field plot with X = 2–48 and Y = 5–60) fits those ranges too. So `EPSG:4326` (WGS 84) is set automatically only when the X and Y columns are named as longitude and latitude (`lon`, `long`, `lng`, `longitude` and `lat`, `latitude`), or when an uploaded boundary shapefile contains at least half of the points read as degrees. Otherwise a panel under the dropdowns asks **Are these coordinates longitude/latitude?** with a **Use EPSG:4326** button; if they are metres or another system, set the CRS they were recorded in instead. Either way the notification names the WGS 84 assumption: coordinates recorded on an older geographic datum (for example ED50) need that CRS chosen explicitly. For projected coordinates the app looks for proof: a companion `lon`/`lat` (or `long`/`lng`/`longitude`/`latitude`) column pair in the same table, or an uploaded boundary shapefile with a `.prj`. When one candidate reproduces that evidence and the alternatives are decisively worse, the CRS is set and reported with the numbers behind it: how closely the chosen CRS reproduces the `lon`/`lat` columns and how far off the next candidate is, or, from a boundary, the share of points that fall inside it. Nothing is plotted until a CRS is set. **Uploading a dataset empties the Input Data CRS and starts identification over**, a CRS you typed yourself included. The **Target Mapping CRS** names the system your outputs are produced in, not a property of the file: a target you chose yourself is kept (a notification says so, and the panel under the selectors judges it against the new data), while one the app filled in is cleared and identified again. Within a dataset, once an Input Data CRS is set, uploading a boundary shapefile or remapping the X/Y columns re-runs identification but never overrides it; check it against the position printed under the mini-map.
   - **No evidence in the file? Locate the study area instead.** A **Locate your study area** panel appears under the CRS dropdowns. Click roughly where the data was collected on the world map, or type a country or region (`Germany`, `Kansas`), and press **Find matching projections**. Monolith searches the full EPSG catalogue of projected coordinate systems that PROJ ships, keeps those whose declared area of use covers that place, and lists each **position** the coordinates would land on, nearest first, with a numbered marker on the map. Codes that land within 250 m of each other, such as a WGS 84 UTM zone, its ETRS89 twin and older datum siblings, share one row led by the modern code, and the row says how far apart they are (*"Same place to within 209 m: EPSG:3045, EPSG:25833, ..."*): a map click cannot separate them. Press **Use this CRS** on the row whose position is your study area, so you confirm a place you know rather than a code you may not. The search runs in the background. If nothing lands near the point you indicated, the list says so rather than offering a best guess, which usually means X and Y are mapped to the wrong columns or are swapped. Typed text is a secondary filter.
   - **The Input Data CRS is the only control that moves points on a map.** Every map layer is reprojected to `EPSG:4326` for display whatever the Target Mapping CRS, so changing the target never corrects a misplaced survey. The Input Data CRS also decides where the models are computed: metre-based projected input is used as supplied, so grid resolution, buffer distance and variogram ranges are measured in it and it should suit the study area (its UTM zone, for example); geographic or non-metre input is transformed to the WGS 84 UTM zone of each locality. It never blocks a run: Data Setup only warns when it distorts distances by more than 1% at your data. The remedy is to reproject the coordinates before upload; changing their CRS label alone only changes where they are read to be. The **Target Mapping CRS** governs the georeferencing of exported GeoTIFFs and shapefiles, the final resampling of the surface (none when it is the working CRS; another projected Target Mapping CRS keeps the run's cell size), the sidebar resolution suggestion, and the ruler's projected reading.
   - **Check the position printed under the mini-map.** It states in degrees where your points currently land, for example `Currently plotting at 12.958°E, 52.466°N`. Compare it against the study area you know: a wrong zone shows up immediately as a longitude in the wrong country. The Map Viewer is a snapshot of the last completed run, so a CRS change only reaches it after you press **Run Interpolation** again; until then the Map Viewer carries a banner naming the mapping its layers were computed under and what has changed since. The existing results are never discarded, because the run archive and the Export Registry refer to them.
   - Both CRS dropdowns list **every WGS 84 / UTM zone** (1N–60N, 1S–60S) alongside WGS 84, S-JTSK / Krovak and (Input only) Pseudo-Mercator; type a zone or code to search. Once the data's position is known (from the Input Data CRS, or the point clicked in *Locate your study area*), its UTM zone and the two adjacent zones are listed first under *Near your data*.
   - Both CRS dropdowns accept **free-typed entries**: any EPSG code (`EPSG:25832`, or the bare number `25832`), PROJ string or WKT. Typed values are validated before a run starts.
   - **A standing panel under the two dropdowns judges the Target Mapping CRS and names the one that is right for your data.** It appears once the dataset, the X/Y columns and the Input Data CRS are set, and it states its verdict in one line. When the target is not set, not recognised, not metric, or questionable, and the recommended CRS measures better than your selection, it offers that CRS by name with a **Use this CRS** button. The recommendation is the WGS 84 UTM zone your data falls in, derived from the data itself: it exists for every longitude and its distortion stays below 0.1% inside its own zone. If you prefer your national grid, type it in and the panel judges it on the same two rules as anything else.
   - The panel's colour gives the verdict. **Green** means the CRS suits the area, with its point scale factor (`k = 0.999836`, so distances are -0.016% off). **Blue** covers a target not set yet, and a geographic target such as `EPSG:4326`, which is a legitimate choice: maps and exports come out in degrees while the models are still computed in the projection described above. **Amber** means a run is allowed but the CRS is questionable. **Red** means a run is refused, or the entry is not a recognised CRS. The information icon next to the verdict explains what reads from this CRS.
   - The **Target Mapping CRS** must be metric if it is projected. A CRS in feet would make exported rasters, the resolution suggestion and the ruler's projected reading report feet as metres (a factor of 3.28). That is a red verdict and both interpolation and classification refuse a run with it.
   - **Recommended setting for projected data:** choose the same UTM zone that suits your study area for both the Input Data CRS and the Target Mapping CRS. The models, the exports, the resolution suggestion and the ruler then share one metric system, and the unit and suitability checks on the Target Mapping CRS cover the models as well.
   - **The Target Mapping CRS must also suit the area.** Being metric is not enough: Web Mercator's axis unit is the metre and at 52°N it reports every distance 64% too long. Monolith measures the point scale factor at your data (the centroid and the four corners of the data extent, worst case) and states the number. Beyond 0.1% off is amber; beyond 1% is red, and the interpolation gate then offers **Use Anyway (Not Recommended)**, recorded in the run configuration and summary. Classification refuses this red suitability verdict without an override.
   - The selected input CRS is cross-checked against the mapped X/Y columns. A geographic (degree) CRS with coordinates outside ±180/±90 raises an error notification; a projected (metric) CRS with degree-like coordinates raises a caution; X values that stay inside ±90 while Y values run past it flag a swapped longitude/latitude mapping. If the mapped X/Y columns hold no numbers at all (the mapping falls back to the first column when the coordinate headings are not recognised), the guard says so and names the two columns it read. Fix the CRS or the mapping before running; the guard itself never blocks or alters a computation.
   - A boundary shapefile may be stored in any CRS: it is reprojected onto the data at run time. Its `.prj` fills the **Target Mapping CRS** only when that selector is empty and never replaces a CRS already set. A shapefile without a `.prj` is read in the **Input Data CRS**. In a multi-locality run, an unnamed feature covering samples from several localities is skipped; those localities use their selected sidebar boundaries and the Run Log explains why. To assign uploaded features explicitly, include an attribute column containing their locality names.
   - A note under the upload reports how many samples fall inside the boundary. A boundary that encloses none of them is not applied: each locality uses the boundary type set in the sidebar, and the note gives the distance between the boundary and the samples. A layer of points or lines is used through its convex hull.
   - The X/Y mapping and the Input Data CRS are also what the **Spatial Cross-Correlogram** (Exploratory → Correlation Analysis) uses to bin point pairs by ground distance. Until both are set that panel shows a "Coordinates are not mapped yet" note; every other correlation panel is unaffected.

**Step 4. Mini-map validation**
   - The validation mini-map shows rows with finite coordinates and a locality, and colours points **by locality**, one colour per geographic group, with a permanent name label over each group and a locality legend. A point far from its named group, or a group plotted in the wrong part of the world, reveals a swapped X/Y pair or a wrong CRS before any modelling starts. A colour set chosen in the Map Viewer's **Point styling** toolbar replaces the locality colours here when its *Apply Colour Set to Mini Map* box is ticked. Returning to this tab after a run re-frames the mini-map on the samples, so it always opens showing the full data extent.

**Step 5. Variable mapping and verification**

The variables below, with their labels, categories and units, come from the variable list uploaded in Step 1 when one was supplied, and from the numeric columns otherwise. Their prediction columns are found by name either way (Smart pairing).

  - **Target isolation:** non-numeric columns and the coordinates identified in Step 2 are filtered out; the remainder become target variables.
  - **Smart pairing:** a name search links observed data with model outputs, ignoring case. For cross-validated predictions it accepts `<target>_cve`, `<target>_pred`, `<target>_predicted`, `<target>Pred`, `<target>Predicted`, `pred_<target>` and `predicted_<target>`, in that order of preference; for single-split predictions `<target>_ss`, `<target>_split`, `<target>_test`, `<target>Split` and `<target>Test`. A successful match creates a triad (Actual, Pred_cve, Pred_ss) so you can toggle between ground-truth and residual maps without re-linking.
  - **Review mapping:** check the table to verify labels, units and prediction pairs, and edit any the app got wrong. A **Unit** column in the variable list (a header named, or containing the word, *Unit* or *Units*) fills the unit boxes; a unit you enter appears in the map legends, on screen and in exported figures, and in the unit tag of exported GeoTIFFs, and decides whether a nutrient's published class limits apply (Map Styling).
  - **Finding a variable:** type part of a column name, label or category in the filter box above the list to show only the matching rows. The filter only hides rows: confirming saves every row.
  - **Confirm:** press **Confirm Variable Mapping** under the list, then proceed to the Spatial Engine.

## Mapping: Context

**Sidebar layout**
* The **Context**, **Spatial Engine**, **Domain & Grid**, **Map Styling** and **Session** sections are collapsible: click a section title to fold it away.
* **Spatial Engine** holds the choices that define the model: method, its parameters, and the cross-validation design. **Domain & Grid** holds the choices that define where and at what cell size it is evaluated: boundary, buffer and resolution, with the resolved per-locality table beneath them.
* **Session** holds **Save config** and **Load config**. The first writes every setting that defines a run to a JSON file: the column mapping and both CRSs, the variable list with its labels, categories and units, the context (localities, variable, view, data subset, comparison settings), the spatial engine with its cross-validation design, covariates and parameters, the manual variogram models and per-locality IDW powers and TPS lambdas you applied, the domain and grid, and the map styling with the palette picked for each variable. **Load config** restores them in a later session once the same data is loaded, and one notification lists anything it could not restore, such as a column, locality or covariate missing from the loaded table. An uploaded boundary shapefile is not part of the file. The file is the session's setup, not the record of a finished run, which is the Export tab's *Download Run Configuration*.
* The **Run Interpolation** button stays pinned to the bottom of the sidebar while you scroll; the header's status chip shows the run state from any tab.
* The **Variable** dropdown supports live search: start typing to filter long lists.

**1.1 Locality (spatial grouping)**
* The Locality/Grouping Column set on Data Setup partitions the dataset. Select one or more localities, or "ALL", to interpolate several localities in one run. Clearing the selection is treated as "ALL". Rows with a missing locality value are left out.
* This selection applies to interpolation runs only. The Classification Suite has its own **Localities** picker in its Spatial Scope panel, which starts with every locality selected and is never changed by this one.

**1.2 Variable selection and category**
* **Variable category:** variables are organised into folders ("Soil Physicochemistry", "Terrain", "Satellite Indices") from your metadata file or automated detection.
* **Variable:** selects the target ("Actual") column, listed by its label (`Total N (%)` for the column `tn`); the prediction columns paired with it in the variable mapping (`tn_cve`, `tn_ss`) come with it.

**1.3 Primary view and comparison mode**
* **Actual values:** the interpolated surface of your raw measured data.
* **ML predictions:** the interpolated surface of your machine-learning model's cross-validated estimates (the `_cve` column).
* **Single split:** the surface of a single train/test split prediction (the `_ss` column).
* **Residuals:** the localized difference between what you measured and what your uploaded model predicted (observed minus predicted). These residuals diagnose the ML model, not Monolith's interpolation; a **Residual Diagnostics** note in the Spatial Engine section explains the three residual products.
* ML prediction and residual views are offered only when the selected variable has the corresponding prediction column (`_cve` for ML predictions and Residuals, `_ss` for Single split). Without prediction columns the Primary View is limited to Actual values.
* **Actual vs Predicted** is the group of boxes under the Primary View buttons, shown whenever a prediction or residual view is selected.
    * **Comparison Mode** splits the display into synchronized side-by-side maps of the measured data and the predictions.
    * **Fit Actual/Predicted Separately** (on by default, recommended) gives the predicted surface its own model: its own variogram under Ordinary Kriging, its own power under IDW, its own lambda under TPS. Unticked, the predicted surface reuses the model of the measured values (their variogram, IDW power or TPS lambda, as fitted, selected or applied for them), and manual variogram tuning, per-locality IDW and TPS values and **OPTIMIZE ALL VARIOGRAMS** address the Actual target only. RK, RFK and CK always fit each surface on its own.
    * **Match Scales** gives both maps one colour range (the surfaces and their standard-error or variance maps alike) and, under Binned or Agronomical Jenks / K-Means styling, one set of class breaks computed from the two surfaces together. It appears once Comparison Mode is on under the ML predictions or Single split view, and whenever the Map Viewer shows a comparison view of a run with a predicted surface, and takes effect only while it is shown.
* **Sidebar selections configure the NEXT run.** Once a map exists, changing the Variable, Primary View, Interpolation method or Comparison Mode does not alter the displayed map or its Scientific Analysis results; they update when you press **Run Interpolation** again. Styling controls (Continuous/Binned/Agronomical, class limits, palette) restyle the displayed map without a re-run, Agronomical classes once you press **Apply to maps and statistics**. To switch between surfaces the last run already computed, use the **View** dropdown in the Map Viewer toolbar, which is instant and needs no re-run. For a kriging run it also holds uncertainty maps for each surface that has a reported variance (see *Uncertainty maps* under Mapping: Spatial Engine).

**1.4 Data subset (Single Split view only)**
* With the Primary View set to **Single split**, a **Data Subset** dropdown appears beneath it and restricts the mapped data to one modelling partition ("Train", "Test", "Validation") before interpolation. All tuning, previews, checks and results then use only those rows, and a value tuned on a subset is stored for that subset alone.
* Choices are read from a `subset` column in the uploaded dataset, matched case-insensitively. Without such a column only "All" is offered.
* The filter applies to the Single Split view only; all other views use the full dataset.

**1.5 Drawing on the map: custom groups and exports**

The interactive maps carry a **drawing toolbar** on their left edge for sketching polygons, rectangles and point markers. This supports two workflows.

* **Assigning a custom locality or analysis group:**
    1. Draw a polygon or rectangle around the points you want to group (a marker only annotates the map).
    2. An **"Assign Locality / Analysis Group"** dialog opens when the shape is finished. Enter a group name and click **Save Group**.
    3. All points inside the shape are written to an `Assigned_Locality` column, and the app reports how many were captured. Select that column as the Locality/Grouping column in Data Setup to analyse your custom zones.
* **Map overlays** are toggled from the **Overlays** menu at the left end of the Map Viewer toolbar, with the basemap selector beside it. The locality pan, the view switcher and the utility buttons (Refresh, Quick export, Point styling, Downloads) follow along the same row. The menu holds:
    * **Map additions**, all off by default: **Show Points** (sample points), **Cell Sizes** (the box listing the pixel size each locality of the displayed run was built at), **North Arrow**, **Borders** (locality borders) and **Map Scale**.
    * **Drawing Tools** (the polygon/rectangle/marker/edit/delete stack at the top-left of the map) and **Ruler** (bottom-left), both on by default. Turn them off for a clean surface (before a Quick export, or when the map is small enough that the controls cover the data). Shapes already drawn stay on the map; only the toolbar is hidden.
    * **Variable Label in Legend**, off by default: the legend shows its colour ramp and break values only (a surface with one value throughout, such as a pure-nugget locality's mean or standard error, shows that value), and the variable label and unit are printed above the map. Turn it on for a legend that has to stand on its own: a screenshot or an exported panel separated from its heading.
* **Sample points:** with **Show Points** on, **Point styling** colours the points by a grouping column (**Color By**, **Palette**, **Custom Colors...**), labels them with any column (**Show Labels**, **Label Field**, **Label Size**) and sets their size (**Point Size**). A point whose Color By cell is empty is grey and not listed in the legend, and custom colours stay with their column and palette. *Apply Colour Set to Mini Map* gives the Data Setup mini-map the same colours. Click a point to open its pop-up; **Pop-up Content** sets what it lists: the variables in the mapped variable's category (the default), one category of your variable list, all variables, or *Variables I choose*, the ones you tick in the list below it (none leaves only the point's notes). A new dataset starts again from the default.
* **Exporting your work:** the **Downloads** menu at the right end of the Map Viewer toolbar holds a **Vector format** selector (Shapefile ZIP, GeoJSON, KML, GPKG) and three downloads; the first two are written in that format. The menu writes files straight to your disk; **Quick export**, on the same row, sends the map on screen to the Export Registry instead. The first two downloads grey out whenever the export cannot be produced, and hovering a greyed-out entry names the reason.
    * **Drawn polygons:** active once at least one polygon has been drawn. Downloads *all* drawn polygons for reuse in a GIS. It exports the shapes **you** drew; the app's own classified zones have their own button.
    * **Class zones:** downloads the class zones of the surface **currently displayed** as a GIS vector layer, one dissolved polygon per class and locality, carrying the class label, its lower and upper break limits, its area in hectares, and the locality, surface, variable and method that produced it. It follows the view switcher, so Actual, Predicted, or both under the comparison view, each with its own classes as the maps draw them. It requires Agronomical or Binned styling (Agronomical also needs **Apply to maps and statistics** pressed first) and is inactive on the residual (Delta), standard-error and variance views, which are not classified into zones. Zone edges follow the grid cells and are not smoothed, and their hectares are the numbers the Area Coverage table reports. Zones of overlapping localities overlap, as their maps do. Shapefile and GeoPackage keep the run's Target Mapping CRS; GeoJSON and KML are reprojected to WGS84 as those formats require.
        * **Which format to pick:** GeoPackage and Shapefile carry the attributes as queryable fields, so choose one of those to filter, join or symbolise by class in a GIS. KML stores only a name and a description per shape, so the export puts the class label in the name and the full attribute record in the description.
    * **Updated dataset:** downloads the current dataset as `.xlsx` including the `Assigned_Locality` column, so group assignments survive the session. Use it after saving drawn groups.
* Shapes can be edited or deleted with the toolbar's tools, and the polygon export always reflects the current set. Deleting a shape does **not** undo a group assignment already saved from it.

**1.6 Measuring distances and areas on the map**

A **ruler** sits in the bottom-left corner of every Map Viewer map, including both panels of the comparison and residual views, so the same feature can be measured on the Actual and the Predicted surface without switching views.

1. Click the ruler icon, then **Create a new measurement**.
2. Click each point along the path. The panel keeps a running path distance, and two icons sit beneath it: a cross to abandon the measurement and a tick to finish it.
3. Click the last point again, or the tick, to finish. Two points report a **Length**; three or more close the shape, which reports a **Perimeter** with its enclosed area.

The result appears in the measurement's own pop-up, on the shape itself. Click any measurement to reopen its pop-up, which also holds **Center on this** and **Delete** links for that shape. Every figure is reported on two bases:

* **Ground (WGS84):** the geodesic distance on the WGS84 ellipsoid. This is the real distance over the ground and does not depend on the projection you chose.
* **Projected (your Target Mapping CRS):** the same path measured flat in the Target Mapping CRS of the run **on screen**. When that CRS is also the one the models were computed in (the Input Data CRS, or the local UTM zone for geographic or non-metre input), this figure is directly comparable with a variogram range, grid resolution or buffer radius.

The two normally agree to within a few hundredths of a percent, and up to about 0.1% near the edge of a UTM zone. A gap far beyond that means the Target Mapping CRS distorts distances over your area: check that the CRS suits the region (Scientific Guide Sections 3.6 and 3.7). When the Target Mapping CRS is geographic, only the ground figure is shown.

A path that crosses itself reports its perimeter but no area; redraw it without the crossing to get one.

Measurements are for reading the map only: they are not stored or exported and change nothing about a run, and each stays on the map until you delete it or the map is redrawn by a new run or a view change.

## Mapping: Spatial Engine

**1. Select the interpolation method**
   - **Deterministic (fast):** **IDW** weights by distance (Shepard 1968), **TPS** fits a smooth surface by minimizing bending energy (Duchon 1977). Both are ideal for rapid visualization and neither produces a prediction variance.
   - **Geostatistical (standard):** **Ordinary Kriging (OK)** models spatial autocorrelation through a variogram, giving the best linear unbiased predictor (Matheron 1963).
   - **Multivariate:** **Co-Kriging (CK)** predicts the target jointly with auxiliary variables through their cross-correlation (Wackernagel 2003). It uses every sample location: one that carries a covariate but no target value, such as a point of a dense conductivity survey beside fewer laboratory samples, still enters that covariate's part of the model, and this is where co-kriging improves a map. When the covariates are measured only where the target is, it gains little over Ordinary Kriging. A covariate needs to be measured together with the target at 10 or more locations, or it is left out and the Run Log says so; the Run Log also states whether each surface was fitted as a heterotopic (extra covariate locations) or isotopic design. CK is scored on every sample with a measured target, the same samples Ordinary Kriging's default *Native* population scores. Selecting CK reveals a **CK Max Neighbors** slider (5 to 60, default 15) setting how many nearest samples of each variable enter every prediction. This is a modelling decision, not a speed setting: smaller values assume the field's mean and covariance are stable only locally, larger ones approach a global system and suit sparse, stationary data. If your sampling is unusually sparse or the fitted cross-variogram range is long, try raising it and compare the Model Performance metrics. Scientific Guide Section 1.4.
   - **Hybrid / ML:** **Regression Kriging (RK)** and **Random Forest Kriging (RFK)** combine environmental trends (topography, satellite data) with kriging of the residuals (Hengl et al. 2007, 2015).
   - Selecting RFK reveals an **RFK Uncertainty Method** radio, which governs the variance band behind that run's SE and variance maps and nothing else: not the prediction surface, not the reported metrics. *Infinitesimal Jackknife*, the default, is the random-forest analogue of a regression standard error: an estimate of the variance of the forest's ensemble-mean prediction, at a small computational cost. *Ensemble spread (fast)* is the between-tree variance, a measure of where the model is least stable rather than a predictive variance. Neither is a calibrated interval. Scientific Guide Section 7.3.

**1.a. Uncertainty maps (kriging engines)**
   - Once a kriging map (OK, RK, RFK, CK) is displayed, the Map Viewer's **View** dropdown lists two more groups under the surfaces: **Uncertainty: standard error** (*SE: Actual*, *SE: ML Predicted*, *SE: Actual vs Predicted*) and **Uncertainty: variance** (the same three). A surface is listed only where at least one of its localities reports a variance, and the comparison entries need both surfaces to. Choosing one redraws the surface as its SE or variance map in place, keeping the zoom and position, without a re-run; the map title and legend name the metric. SE shares the variable's unit, variance is in its squared units (Scientific Guide Section 7.2). For OK and CK the band is the kriging variance; for RK and RFK it is the hybrid trend-plus-residual variance, which is approximate and optimistic away from the samples (Section 7.3), so read those maps as a relative reliability map rather than a calibrated interval. IDW and TPS runs have no uncertainty entries, and the sidebar's **Uncertainty Mapping** note in Map Styling says so until a kriging map has been generated.
   - Uncertainty maps always use a continuous sequential palette: a diverging palette choice (RdYlBu, BrBG, Spectral) is shown as Viridis on these maps. Binned and Agronomical classes apply to the concentration maps only, and the class limits and class areas do not change while an uncertainty map is on screen.
   - **A locality whose variogram could not be estimated has no SE or variance.** Either its fit failed and a default model was used (the red *Variogram fit failed* band), or the values it models are the same everywhere up to rounding: a target with no usable variance (named under Run Warnings) or, under RK and RFK, residuals that the trend reduces to rounding. Its predictions are kept but its uncertainty is not reported: it is blank on the uncertainty maps and in their exports, never shown as zero, while the other localities keep theirs. Under Co-Kriging the same applies to the target's own variogram. The Run Log names each such locality and surface. Scientific Guide Section 7.4.
   - **Quick export** sends the uncertainty map on screen to the Export Registry, and a single map exports as a GeoTIFF of that SE or variance band, laid out like the map's own GeoTIFF (one file per locality where the localities are gridded separately). The **Class zones** download is inactive on these views.
   - A new run keeps the SE or variance choice when the new run offers it.

**1.b. Choose the cross-validation strategy**
   - The **Cross-Validation Strategy** selector sits beneath the **Interpolation** method buttons. It changes the reported diagnostics only, **never the interpolated map**, with one exception: IDW **Auto (CV)** selects its power under this same strategy, so the selected power (and the IDW surface built from it) can differ between strategies.
     - **Auto (default):** leave-one-out CV at 50 or fewer points, seeded random 10-fold above 50.
     - **kNNDM (Map-Matched):** ten folds matched to your map: each held-out sample is predicted from about as far away as the map predicts its cells (Linnenbrink et al. 2024). Evenly spread samples get ordinary random folds; clustered samples, transects, or a boundary that reaches beyond the samples get folds that hold out whole groups. You get the error of this map over this boundary without having to choose between random folds and blocks. It needs 30 points (LOOCV below) and costs about the same as ten-fold CV. The folds follow the boundary and buffer, not the grid resolution.
     - **Standard LOOCV:** full leave-one-out at any size. Each kriging engine rebuilds its model once per held-out sample, so it usually takes longer than ten-fold CV.
     - **Spatial Block CV:** holds out ten spatially contiguous k-means clusters; below 30 points it reverts to LOOCV.
   - **Which design answers your question.** LOOCV and random folds measure how well the map interpolates within the sampled area: each held-out point keeps its neighbours, as the map does, and for a random sample they estimate that accuracy approximately without bias (Wadoux et al. 2021). On a regular grid they overstate the error: a held-out grid point is a full grid spacing from its nearest neighbour, while the map's cells sit closer to a sample than that. Spatial Block CV measures accuracy away from the sampled clusters, the question for transfer to unsampled ground or for a clustered sample with gaps the map has to bridge (Roberts et al. 2017; Ploton et al. 2020), and it is pessimistic for a map within the sampled field. kNNDM picks between these behaviours for you, from your samples and your boundary. Scientific Guide Sections 5 and 5.1.
   - **kNNDM and your boundary.** Because kNNDM matches the folds to the map, the boundary decides what it does. Under a **Point buffer** the map stays within the buffer radius of your samples, closer than they lie to each other, so kNNDM uses ordinary random folds, and the metrics, like any cross-validation's here, somewhat overstate this map's error. Under a hull or buffered boundary around sparse or unevenly spread samples, the map reaches into unsampled ground, and kNNDM holds out whole groups so that its error is reported too. The **CV Distance Match** panel shows which case you are in.
   - The strategy actually applied is shown in the badge beside the **Model Performance** table and inside each row's *Source* cell; the exported sheet carries it as a *CV Design* column.
   - **Every kriging fold rebuilds its model.** OK, CK, RK, RFK and the OK fallback all re-estimate, from each fold's training samples, everything they estimated for the map: the variogram (or the co-kriging model), the covariate screen, the interpolated covariates, the trend. The Run Log counts, for each covariate, the folds where it could not be kriged and took the map's IDW fallback, and the folds where it showed no spatial structure; the note under the Model Performance table states what the engine on screen re-estimated. The exception is a variogram you saved with **Apply manual model**: it is reused unchanged, and that locality is labelled *conditional on applied variogram*. IDW **Auto (CV)** and TPS **Auto (GCV)** likewise re-select the power or lambda inside every fold. Scientific Guide Section 5.2.
   - **Comparing engines on the same data: the CV Population switch.** RK and RFK can only use samples that carry every selected covariate, while OK by default uses every sample with a measured target. Scoring them against each other then compares two different experiments. With Ordinary Kriging selected, the **CV Population** control offers **Native** (default: every measured sample, the population Co-Kriging is scored on too) and **Comparable** (only the samples that also carry every selected covariate, folded exactly as RK and RFK use them). Under Comparable, OK is trained *and* scored on those samples; the OK map still uses every sample. Choosing Comparable reveals the Auxiliary Variables panel for OK, which is there only to select the samples: OK does not model with them.
   - **The CV population ID** is eight characters shown when you hover the *Source* cell of the Model Performance table, and written to the exported metrics. Two runs on the same uploaded table whose ids match cross-validated the same rows under the same partition, so their scores are directly comparable; different ids mean they did not. kNNDM folds also follow the boundary, so changing the boundary or buffer changes a kNNDM run's id.
   - **Sample accounting.** Each row reads *n = predicted of expected*. If a fold could not be evaluated, its samples carry no prediction, the row is marked **INCOMPLETE**, and the metrics describe only the samples that were predicted; a cross-validation that failed as a whole reads *n = 0 of* its expected count, and the Total (Combined) row counts those samples as expected. The Run Log names the fold and the reason.
   - **Repeated CV (fold-realization stability):** a checkbox under the strategy selector, off by default and hidden under Standard LOOCV. Left off, the metrics come from a single fold assignment. Tick it, pick 3, 5 or 10 realizations, and the cross-validation re-runs under that many fold assignments; the Scientific Analysis tab then shows a **Fold-Realization Stability** table where every metric reads *mean ± SD*. Use the SD as the resolution of your comparison: **if two methods' RMSE values differ by less than it, the ranking is fold luck, not skill.** The map and the Model Performance table are the same either way (realization 1 is the reference run). Each realization costs one more full cross-validation, so five realizations take roughly five times the cross-validation time. Leave-one-out plans, and kNNDM plans that group samples spatially, are deterministic, so those localities contribute a single realization, and the Run Log says so.
   - The summary tables on the Scientific Analysis tab (variogram parameters, model performance, prediction and classification metrics, area coverage, descriptive statistics) are sortable by column header. Hovering a **Model Performance** header shows a plain-language definition of that metric.
   - **Reading the Moran columns.** The table reports Moran's I of the cross-validation residuals (Moran 1950) and, beside it, a two-sided **Moran p** from 999 seeded permutations of the residuals, which cannot report less than 0.002. Hover an I value to see that row's expected value under no spatial autocorrelation, which is −1/(n − 1) and therefore slightly *negative*, not zero: at 30 points a reading of +0.01 sits essentially on the null expectation. A clearly higher value is *consistent with* spatial structure the procedure did not capture; it is a lead to follow, not an instruction to switch to RK or RFK. A value near the expectation is not a clean bill of health either: random folds leave a held-out point's neighbours in the training set and can mask the structure the statistic looks for. An `NA*` in either column means the statistic **could not be computed** for that point set (too few cross-validated points, missing coordinates, or a failed neighbour search) and never that no structure was found; the Run Log states which.
   - **Under Spatial Block CV, and where kNNDM chose spatial folds, the column changes its name and drops its p-value.** Rows scored that way are headed **Block-CV residual clustering** or **Spatial-fold residual clustering**, marked `†`, and their p reads `NA†`; the footnote under the table says why. A locality too small for either was scored by LOOCV and keeps the ordinary reading, as do kNNDM's random folds and a pooled row that mixes fold designs. Scientific Guide Section 5.6.
   - **CV Distance Match** (Scientific Analysis tab, below the Model Performance table) draws, for the selected locality, how far the map predicts from the samples and how far the cross-validation predicted, as two cumulative curves, with the sampling density as a dashed reference. The closer the two curves, the better the metrics describe your map; a cross-validation curve to the left means the metrics are optimistic for this map, to the right pessimistic. W, the area between them in map units, is given for your folds and for random 10-fold. It works under every strategy.
   - **`n/a¹` means the metric does not apply here.** For a target whose observed values span zero (an anomaly or a centred variable), NRMSE (mean) and SMAPE have no interpretation, so the table prints `n/a¹` with a footnote instead of a number, and **NRMSE (SD)** is reported in their place: the error as a multiple of the observed spread, which does not depend on where the variable's zero sits. Distinguish it from `NA*`, which means the value could not be computed.
   - **Displayed precision:** statistics are shown to four significant digits (every integer digit from 1000 up), in scientific notation below 1e-4, and exported at full precision.
   - **Pooled rows are summaries, not scores.** With *Filter Analysis View* set to **Total (Combined)**, a note under the cross-validation badge reminds you that the pooled R² and NSE are computed against the pooled mean of all localities. Where localities sit at different levels that between-locality spread inflates both numbers, and the pooled row can look better than every individual locality. Judge model skill on the per-locality rows; pooled RMSE, MAE and Bias are unaffected.
   - **Run Warnings.** Conditions the interpolation reported for individual localities open the Scientific Analysis tab as their own card, named by locality and surface, and are written into the Run Log. A blank metric cell usually has its explanation here.
   - **The uploaded-prediction card can score a different sample than the model.** *Prediction Performance (Uploaded Data)* is computed on the displayed sample locations that carry both a measured and a predicted value. The model's cross-validation population is chosen by the measured values (and, for RK, RFK, CK or OK Comparable, by the covariates), not by the uploaded predictions, so the two counts differ where a location lacks a prediction or a covariate. When they do differ, a note under the card states both. The card and the classification-agreement table beside it appear only for a run that mapped a prediction side: an Actual-values run reads no prediction column, so it also registers no ML-prediction maps or exports.
   - **Single-locality runs:** the analysis filter selects that locality directly. **Total (Combined)** and combined descriptive/area summaries appear only when the displayed run covers multiple localities. Under **Total (Combined)** the cards that describe one locality (its descriptive statistics, the CV Distance Match) are hidden.
   - **Total (Combined) variograms pool within localities.** The Data Structure, residual and directional variograms pool the point pairs inside each locality; no pair joins two localities. The title gives the number of localities pooled, and the subtitle names any locality left out for having fewer than 10 located values. The lag axis stops at the half-diagonal of the smallest locality pooled, so one small locality shortens the curve for all. The pooled Residual Variogram carries a fitted curve; the others show the empirical points only. Scientific Guide Section 4.4.
   - A **Variable naming** radio next to *Filter Analysis View* switches every diagnostic on the tab (variogram titles, RF importance panels, cross-variogram headers, RK coefficient tables) between the human-readable **labels** from your metadata mapping (default) and the raw **column names**. The toggle is cosmetic; no computed value changes.
   - Every diagnostic plot sits in a card with two header buttons: **download** saves a 300-dpi PNG of exactly what is shown, on a 9 x 7 in page at the type sizes on screen, and **expand** opens a large modal with a *Static (High-Res)* / *Interactive (Hover/Zoom)* toggle. Interactive mode adds per-point hover readouts: lag distance, semivariance and pair counts on variograms; observed, predicted and residual on scatter plots.
   - **Observed vs Predicted** plots each cross-validated prediction (x axis) against its observation (y axis), with the 1:1 line in red and the regression of observed on predicted in blue, whose slope and intercept the subtitle gives. A slope of 1 and an intercept of 0 indicate linear calibration; curved patterns of error can still remain. Slopes below or above 1 describe excessive or insufficient prediction spread relative to the fitted line. Scientific Guide Section 5.5.

**1.c. Covariate helpers (RK / RFK / CK)**
   - **Predictor correlations:** **Rank by correlation** opens a category-filtered table ordered by absolute Pearson correlation, with signed **r**, raw two-sided **p** and finite paired sample count **n**. The target column, localities, subset and row count it was computed on appear above it, and the table refreshes when they change. Candidates with fewer than three finite pairs or constant values are listed as unavailable. A **Maximum p (raw)** selector above the button (All, 0.05, 0.01, 0.001) drops candidates whose raw p exceeds the value chosen.
   - **Correlation target:** Actual view uses measured values and shows no source switch. ML Predictions, Single Split and Residuals views default to uploaded predictions; **Actual values** switches this screen to measurements. CVE uses all rows in the selected localities. Single Split adds a **Correlation data subset** switch initialized from Context's **Data Subset**, allowing an independent All/Train/Test/Validation comparison wherever those partitions exist. Changing Context's subset resets the correlation subset to match it. These switches affect this screen only.
   - **Interpretation:** raw p-values are an exploratory filter, without adjustment for multiple screening or spatial dependence (Scientific Guide Section 8.7). Across-locality correlations can reflect differences between localities; check the intended locality separately. Pearson screens linear association, so weak correlation does not exclude a useful nonlinear RFK predictor.
   - **Multicollinearity gate:** RK, RFK and CK check **each selected locality**. A VIF removal above 10, or an incomplete check, opens **Review covariates by locality**: one card per locality, those with removals first and clean ones collapsed, with chips at the top that jump to each card. Each card charts every covariate's VIF on a log scale with the area above 10 shaded: a hollow circle before Auto-Drop, a filled circle after it, and a cross with its step number where Auto-Drop removes it, one covariate at a time. **Why each removal** gives the removal's VIF, the share of its variation the other covariates explain, the share its strongest partner alone explains, the next highest VIF at that step and its strongest correlations; **All pairwise correlations** opens the full table. A card without removals still names any pair above |r| = 0.95 on the locations where both covariates are measured. When a locality's Actual and Predicted samples differ, the Actual chart holds the checkboxes and **Predicted surface** shows that surface's own check. Tick covariates in a chart, then **Apply removals and recheck**: removals apply to every mapped surface of that locality and leave other localities unchanged. **Reset removals** restores them. Keep at least one candidate per locality; choose another method to run without covariates. After rechecking, choose **Continue with remaining covariates**, or **Auto-Drop remaining**, **Keep remaining** or **Cancel** if a finding remains; the info icon beside the buttons explains each. An incomplete check says so and shows how many values each covariate is missing. RK and RFK fit only the locations that carry every covariate, so their cards count all the target's locations and how many each covariate lacks. Constants, and for CK covariates with fewer than 10 samples co-located with the target, are listed and removed whatever you answer; they alone open no dialog. A sole constant covariate can give an intercept-only trend or a named fallback, recorded in the run warnings. Choices apply to this run only, and changes to its data or settings require a fresh check. **Continue** and **Auto-Drop** repeat automatic screening on every fold's training rows among your remaining candidates, so folds can retain different covariates. **Keep remaining** skips VIF pruning. CV measures performance conditional on your manual choices. The Run Log and Model Performance note report fold differences.

**2.a. Variogram optimization (geostatistical engines only)**
   - Selecting a kriging method reveals the Variogram Panel.
   - **Auto-Fit (default Fitting Mode):** **OPTIMIZE ALL VARIOGRAMS** fits three model families (spherical, exponential, Matérn) by weighted least squares, searching ranges from 1/100 of the longest lag to 10 times it, and keeps the best eligible fit per locality. Where no eligible model fits better than a flat line, the fit is a **pure nugget** (no spatial structure selected) and kriging maps the sample mean. The Gaussian, which assumes an extremely smooth field, is available in **Manual Tuning** only, and a Matérn with a zero nugget is not auto-selected. Review the plotted curve against the scatter points. The button is a **preview**: an Auto-Fit run always fits its own variogram for the variable, data subset and localities it maps, whether or not you pressed it.
   - **The optimizer runs in the background.** The button greys out and reads *Optimizing…* while the search runs, and the rest of the app stays usable. The fitted variograms and a diagnostics dialog appear when it finishes; the dialog names each model (`Nug` for a pure nugget, *not fitted* where there was nothing to fit) with its weighted SSE (`N/A` when unavailable). It cannot overlap an interpolation run: starting one while the other works asks you to wait.
   - **Manual override:** if the auto-fit misses the short-range variability (the points closest to the Y axis), set **Fitting Mode** to **Manual**; the *Manual Tuning* panel opens with a model family, the *Locality to Tune* (and, when the Predicted surface is fitted separately, its *Target*) and three sliders. Set **Nugget** for the variation at very short separations and **Partial Sill** for the rise above it: their sum is the plateau. **Range** sets the model's range parameter *a*, which is not the distance where the curve flattens: that is *a* for a spherical model but about 3*a* for an exponential one, so judge the range on the plotted curve. Once you apply the model, its subtitle reports the practical range. If a variable's variance is below about 0.0001 the sliders cannot represent its steps, and a notification asks you to rescale it in the uploaded file (for example % to g/kg). **Apply manual model** refuses a model whose nugget and partial sill are both zero. In Manual mode a run uses **only** models you saved with that button, for the variable and data subset you tuned them on; a locality with no applied model fits its own variogram, exactly as under Auto-Fit. An applied model stays applied until you apply another, press **OPTIMIZE ALL VARIOGRAMS**, or change the data: interpolation runs, Auto-Fit runs included, do not replace it. Stored models are cleared when you upload data, reassign localities, or change the X, Y, locality or Input CRS mapping. A Gaussian or Matérn model with a nugget below 5% of its sill is applied, but flagged at Apply, in the variogram subtitle and on the map: kriging with it can put predictions far outside the observed range, or return an empty locality. Add a nugget if that happens.
   - Switching to Manual, or changing the *Locality to Tune*, moves the Scientific Analysis locality filter with it, so the variogram you are tuning is the one on screen: the fitted curve carries your manual model as a red dashed overlay with its weighted SSE in the subtitle, using the same criterion as Auto-Fit. Manual "Mat" uses Matérn smoothness 1.5. This works straight after **OPTIMIZE ALL VARIOGRAMS**, before any interpolation has run.
   - **While you are tuning** (Manual mode, or an optimisation not yet followed by a run), the *Actual* and *Predicted Data Structure* cards move to the top of the Scientific Analysis tab, under the locality filter, whatever engine produced the run on the Map Viewer. If that run is IDW or TPS, which fit no variogram, its result cards are held back until tuning ends, with a note saying so; its maps, exports and history are untouched.
   - **A locality that produces no surface says so.** If a fitted model leaves the kriging system unsolvable, the locality is skipped and the Run Log carries a `[WARN]` line naming it and pointing at its variogram panel. For Ordinary Kriging the Run Log adds a line when the cause is the usual one, a Gaussian or Matérn variogram with a nugget below 5% of its sill: add a nugget and run again.
   - **Manual fits apply to Ordinary Kriging only.** A hand-tuned model describes the variogram of the *measured values*, which is what OK kriges. RK and RFK remove a trend first and model the variogram of the **residuals**, and CK fits a linear model of coregionalization across the target and its covariates, so these engines always fit their own. The panel says so while RK, RFK or CK is selected, and starting such a run with stored manual fits raises a one-time notification and a Run Log line.

**2.b. IDW power**
   - Selecting IDW reveals its panel. **Max Neighbors** (4 to 50, default 12) limits each prediction to the closest N samples, so distant, unrelated points cannot distort local predictions.
   - **Power (p) applies to** *All localities* (default), one setting for every locality, or *Per locality*: choose a locality (and, in a view that computes a predicted surface with **Fit Actual/Predicted Separately** ticked, the Actual or Predicted target), choose Fixed p with its value or Auto (CV), and press **Apply per-locality power**. Localities without a value of their own use the setting for all localities. A note under the controls names the selected locality's own value, or the setting it runs with instead, and lists the localities that have values of their own. Values you apply are used only while *Per locality* is selected, and only for the variable and data subset they were applied for; changing the data or the coordinate/locality mapping clears them.
   - **Fixed p** (default p = 2) uses the power you type, any value from 0 to 48; p = 0 weights the Max Neighbors samples equally. The run does not start while Fixed p is missing or outside that range.
   - **Auto (CV)** selects each locality's power from the whole IDW family: equal weights (p = 0), 0.25 to 6 in steps of 0.25, coarser steps up to 48, and the nearest-neighbour limit (p → ∞, where every location takes its nearest sample's value). It takes the one with the lowest cross-validation RMSE under the **Cross-Validation Strategy** you selected (ties go to the smaller power). The selection is part of the model, so every cross-validation fold selects again from its own training samples, and the reported metrics include it. Regional Parameters and the run log list the map's power and the range of the fold powers; the Scientific Analysis tab's **IDW Power Selection** panel draws the RMSE of every power, with the nearest-neighbour limit at the right end (∞). With **Fit Actual/Predicted Separately** unticked, the Predicted surface's power and curve are the measured values', and the panel says so. A locality with fewer than 5 samples, or whose values carry no usable variance, is not searched and uses p = 2, and the run log and the Model Parameters export say so.
   - **A selection at either end of the family is a finding about your data.** *Equal weights* means distance weighting did not help at your sample spacing: the map is the mean of the Max Neighbors nearest samples, so Max Neighbors now sets the smoothing, and Ordinary Kriging models such short-range variation as a nugget. When Max Neighbors reaches every sample of the locality, that mean is a single value over the whole map. *The nearest-neighbour limit* gives a stepped (Thiessen) surface and is raised as a warning; Ordinary Kriging or TPS give a continuous surface that honours the same short-range continuity. A selected power of 24 or more is read the same way, since the map is then practically that stepped surface. The run log and the IDW Power Selection panel say which applies.
   - **How clearly your data choose the power.** In the IDW Power Selection panel, filled points are the powers whose cross-validation error is within one standard error of the best, and hollow points are more than one standard error worse. The panel and the run log say how many are within that band, and whether p = 2 is among them; if it is, your data do not distinguish p = 2 from the selected power. Many filled points mean a flat profile: the choice between them is weak, and a Fixed p (such as 2) is as well supported. The band is for reading; Auto (CV) still takes the lowest error.
   - The table under the panel, *Displayed IDW run (pooled CV)*, appears once an IDW run is on screen and shows that run's pooled RMSE and bias.

**2.c. TPS smoothing**

Regional Parameters shows the lambda actually fitted and its effective degrees of freedom for each surface, and the Model Parameters export carries both as numbers. A warning identifies a near-planar surface (effective df below 3.5), including whether GCV or fixed smoothing produced it.
   - **Smoothing (λ):** *Auto (GCV)* (default) lets generalized cross-validation (Craven & Wahba 1978) choose lambda inside the run, and again inside every cross-validation fold from its own training samples, so the reported metrics include the choice. The Scientific Analysis tab's **TPS Smoothing Selection (GCV)** panel draws each Auto run's GCV curve with the fitted lambda marked. *Exact (λ = 0)* passes through every sample. *Fixed λ* uses the value you type, any number above 0.
   - Lambda acts on coordinates scaled to the unit box, and GCV typically selects values between 1e-6 and 1e-1: type such values in full or in scientific notation (for example `2.4e-06`). The run does not start while a Fixed lambda is missing or not above 0.
   - **When GCV's minimum sits at an end of its range**, the run says what that means. At the smoothest end (effective df about 3) the surface is a least-squares plane with nothing beyond it: at this sampling GCV selects no spatial structure beyond a linear trend, which is a selection, not evidence that none exists. At the least-smoothing end, exact interpolation (λ = 0) lies beyond what GCV can score, so the run cross-validates it on the same folds and reports both RMSEs in the run log, the GCV panel and the Model Parameters export. If exact interpolation predicts better, a warning recommends *Exact (λ = 0)*; the run itself keeps GCV's lambda.
   - **Smoothing (λ) applies to** *All localities* or *Per locality*, where each locality takes Auto (GCV), Exact or a Fixed λ with **Apply per-locality λ**, exactly as for the IDW power (2.b).

## Mapping: Domain & Grid

Where the surface is predicted and at what cell size.

**1. Define the grid resolution**
  Resolution is the pixel size of the final map. Resolutions and their suggestions are always in **metres**, even under a geographic Target Mapping CRS.
* **Auto (Per Locality):** each locality's grid follows its **sampling density** (Hengl 2006): 0.0791 × √(boundary area / sample locations), about 160 pixels per sample location, and never coarser than half the average distance between neighbouring samples, limited to 1-1000 m. Densely sampled fields get fine grids and sparsely sampled ones coarser grids. A finer pixel draws the same surface at smaller steps; it adds no information. Each locality keeps its own grid, so a GeoTIFF export is a zip with one file per locality. To choose the cell size on any other ground, set it yourself in **Fixed**.
* **Auto (Global):** every locality gets **one pixel size**, the finest of the sizes the localities would get under Auto (Per Locality), and the grids are aligned to one shared lattice. Example, on the bundled sample data: Kale grids at 14.6 m and Karacasu at 92.1 m under Per Locality; under Global both grid at 14.6 m, so the large, sparsely sampled locality takes longer. Use it when the localities' maps must be compared or merged cell for cell at an automatically chosen size; **Fixed** does the same at the size you set. The alignment holds when the localities share a working CRS and the Target Mapping CRS is that same system; a different projected Target Mapping CRS resamples every surface onto one new lattice of the same cell size.
* **In the Auto modes the pixel size is set when the run starts**, so the per-locality table under the selector reads *set at run*. After a run, the **Cell Sizes** overlay in the Map Viewer (Overlays menu) lists the pixel size each locality was built at, and the run configuration records it. The table's buffer column shows the dynamic buffer the run will use: from each locality's point spacing in the Auto modes, and from the cell size you set under Fixed resolution.
* Pixels are always square and exactly the stated size: the grid grows by whole pixels until it covers the boundary.
* **Fixed:** manual control, 1 to 500 m. It arrives pre-filled with a value derived from the samples of the selected localities - half their mean nearest-neighbour distance, or the data extent divided by 300, whichever is larger - which you are free to overwrite. Every locality's grid sits on one shared lattice (multiples of the cell size), so a GeoTIFF export holds all localities in one raster, cell for cell, unless their boundaries overlap or they share populated cells, including cells on a shared boundary edge.
    * **Low values (near the 1 m minimum):** high detail, high RAM use, longer processing.
    * **High values (50-300 m):** faster, but local variation may be lost.
    * As a guard, a resolution that would produce more than roughly 4 million grid cells across the map extent is coarsened automatically, and the locality and the size used instead are named in the progress panel, as a notification and in the run log. This applies in all three modes; ordinary resolutions are used exactly as set.
    * The opposite extreme is also caught: a resolution so coarse that no grid node lands inside a locality's boundary, easy to hit with a tight Point buffer, skips that locality with a run-log warning naming the cause.

In every mode the per-locality summary table under the slider follows the current locality selection and describes the next run.

**2. Borders and polygoning logic**
   Define the analysis envelope so the model does not interpolate indefinitely:
* **Concave hull:** shrink-wraps the boundary to the outer perimeter of the points. Best for irregularly shaped fields.
* **Convex hull:** a rubber-band boundary. Best for simple, rectangular fields.
* **Buffered:** a smoothed buffer around the concave hull, so the map covers the field edges.
* **Point buffer:** individual buffers around every point.
* **Buffer Logic (Buffered only):** *Auto (Dynamic)* sets each locality's buffer to a multiple of a base distance, 1x for TPS, 2x for IDW and 3x for the kriging engines, kept between 5 and 2000 m. The base is half the locality's mean nearest-neighbour distance in the Auto resolution modes and the cell size under Fixed resolution. *Fixed (Manual)* uses the Buffer Distance below.
* **Buffer Distance (m):** how far the map extends beyond the outermost samples, and the circle radius in Point buffer mode (default 250 m).

**Match the buffer to the cell size in Point buffer mode.** A grid cell is drawn only when its centre lies inside the boundary, and in Point buffer mode the boundary is just the circles around your points. A sample can sit up to half a cell diagonal from its own cell's centre, so keep the buffer at or above **resolution ÷ 1.41** (equivalently, resolution at or below **buffer × 1.41**). A 175 m buffer on a 350 m grid falls short, and roughly a fifth of isolated samples then appear as points sitting on blank map. The sidebar flags the mismatch under the resolution table when resolution is Fixed, and every run re-checks it against the resolution actually used, raising a notification and writing the corrective numbers to the run log. An uploaded boundary shapefile takes over wherever it matches a locality, so the advisory then concerns only the localities it does not cover. Lowering the resolution is usually the better fix, since widening the buffer enlarges the area the map claims to cover.

*The Boundary Type, Buffer Logic and Resolution Logic configured here apply to **interpolation runs only**. The Classification Suite has its own boundary, buffer and resolution controls in its Spatial Scope panel.*

## Running a Model

**Execution and run estimation**
   - **Run estimate:** the line directly above the **Run Interpolation** button states what the next run will cost before you start it - the estimated duration, how many locality models it will fit, how many points they cover, and the method it will use. It follows every change to the sidebar, and it learns from your runs on this computer: once five localities have been interpolated with the chosen method, it is fitted to how long they took against their sample counts. Before that it uses fixed per-method rates and is approximate.
   - Click **Run Interpolation** and move to the **Map Viewer** tab. The app cross-validates under the strategy selected in 1.b, generates the surface, and populates the performance table with RMSE, R², Moran's I and the rest. The cross-validation seed and the Moran neighbour count are fixed values; Scientific Guide Section 11 says where to change them.
   - **What the Map Viewer shows while a run works:** a panel naming the method being interpolated, a progress bar, and a four-entry phase strip - *Validate*, *Fit variogram* (*Fit model* for IDW and TPS), *Predict grid*, *Cross-validate*. The entry in progress is highlighted and finished ones turn green. The panel stays on screen until the run finishes and you press **Reveal Maps & Enable Analysis**; the rest of the app is usable throughout. When the run completes the button reads *Interpolated* and stays disabled until you reveal the results.
   - **Cancelling a run:** the cancel takes effect at the next checkpoint. Checkpoints sit before each locality's Actual and Predicted surfaces and, for RK and RFK, between covariates as they are interpolated onto the prediction grid, so a cancel during that stage waits for the current covariate. Starting a new run before then does not revive the cancelled one: it still stops at its next checkpoint.
     - **A cancelled run is labelled as one.** The configuration panels read **Run #N - CANCELLED** with a note that no surface, metrics or exports were produced, the Model Performance table carries the same note, the header chip reads *Cancelled*, and the Run Log ends with the cancellation. The results that were on screen were archived or discarded when the run started: to bring back an earlier result, restore it from the Run History Archive.
   - **Too many covariates for the sample size:** Regression Kriging fits one coefficient per covariate plus an intercept, so both the main fit and each cross-validation fold need more points than that. If a locality or a cross-validation fold falls short, the run says so, naming how many points are needed against how many exist. Reduce the covariate count, add samples, or pick a strategy with smaller held-out folds.
   - **Failed regions:** if one or more localities lose a surface to an error (the Actual, or the Predicted surface the run asked for), or stop part-way, a single summary dialog lists **every** failed region with its full error text. Per-region error notifications appear alongside it, and the full text is retained in the run log. A locality whose maps were produced but whose cross-validation failed is not a failed region: its CV error is in the run log and its Model Performance row reads INCOMPLETE.
   - **Results Assembly Failed** means the models completed but collecting their maps, tables or exports failed, so those may be incomplete.
   - **Automatic fallbacks:** if an engine cannot be fitted for a locality (TPS on a degenerate point layout, or a CK/RK/RFK model failure), the app falls back to a simpler engine and reports this in the run log and as a warning notification. Check the log if a map looks different from the method you selected.
     - **The affected diagnostic panels say so in place.** A fallback leaves a locality without the diagnostics belonging to the method you chose: a fallen-back RK locality has no trend model, an RFK one has no forest. The Trend Model Summary, RK coefficient table and RF Variable Importance panels state that the locality's trend model was not fitted and point you at the log. The per-locality residual variogram is titled *Variogram of Measured Values - Ordinary Kriging Fallback*. A cross-validation row that could not be computed is labelled "CV unavailable". Likewise, if an uploaded boundary shapefile cannot be applied to a locality (projection failure or no spatial overlap), the run proceeds with the point-derived boundary and says so in the progress warnings.
   - **Copying a table:** every result table carries a copy button in its title row, on the Scientific Analysis tab and in the Classification, Exploratory and Governing-Factors suites. Pasting into Word or Google Docs gives a table, and pasting into a spreadsheet fills cells. What is copied is what is displayed, at the displayed rounding, headers included, and every page of a paginated table. The button turns into a tick when the copy succeeds.
   - **Diagnostics that do not apply** to the engine or view on screen (RF Variable Importance, internal residual variogram, TPS GCV plot, IDW Power Selection) are hidden.
   - **Directional Variogram (anisotropy check):** a panel in the Scientific Analysis tab, shown for **every** engine, IDW and TPS included. It computes semivariance separately in four compass directions (N-S, NE-SW, E-W, NW-SE). Two switches above the plot choose what it is computed on. **Data** picks the measured values or, when the run mapped an uploaded prediction column, those predictions. **Computed on** picks the values themselves or the cross-validation residuals of that surface; residuals are the more informative view for RK and RFK. Reading the measured and the prediction side against each other shows whether your ML model kept the field's directional structure. Residuals exist only where that surface's interpolation **and** its cross-validation both completed (the Run Log gives the cause when they did not). If the four curves reach their plateau at clearly different distances, the field's structure is directional and a single range under-describes it. This is a diagnostic only: every engine is omnidirectional, so treat a strong split as a caveat to report, not a setting to adjust. Select a locality to compare directions within one field, or "Total (Combined)" to pool each direction within every locality of the run.
   - **Every variogram panel states its model.** The Data Structure, Residual Variogram and Internal Residual Variogram panels, and the variogram figures in the Export Registry, carry a subtitle with the model drawn: family (with the Matérn smoothness), nugget, partial sill, range parameter (a) and practical range, the last marked *at the search limit* when it is a bound and *model-extrapolated* when it lies beyond the longest lag, followed by the nugget interval when your data do not fix the nugget. The subtitle opens with what the model is: *Fitted*, *Heuristic fallback, not fitted* when there was nothing to fit (fewer than five lags, or a constant variable), or *Applied manual model*.
   - **RF Variable Importance (RFK):** per locality, three panels for the trend forest: the increase in out-of-bag MSE when a covariate is shuffled (in the target's squared units; it orders the covariates), the same increase divided by its standard error across trees (randomForest's %IncMSE, which grows with the number of trees, 200 per forest), and IncNodePurity (computed on each tree's own training rows). The exported importance table carries the same three columns.
   - **RK linear trend panel:** for Regression Kriging runs, the Scientific Analysis tab shows the trend model as fit-statistic chips (R², adjusted R², residual standard error, F statistic with p-value, sample size) followed by a sortable coefficient table with each covariate's estimate, standard error, 95% confidence interval, t value, p-value and significance code. Select a specific locality in the analysis filter to view it, since trend models are fitted per locality. The R console summary sits under the collapsible *Raw R model summary* link. **Read the p-values with care:** they come from OLS and assume independent residuals, while RK kriges those residuals precisely because they are spatially autocorrelated, so the standard errors tend to be too small and significance overstated. Treat them as exploratory trend diagnostics. To judge how optimistic the table is, look at the *Internal Residual Variogram* below it: the larger the structured part of its sill against the nugget, the more optimistic the p-values. The Model Performance Moran's I scores the cross-validation errors of the full RK prediction, not these residuals, so it does not check the trend tests.

## Mapping: Map Styling

**Colour palette configuration**
- The **Color Palette** picker holds fourteen scales: Viridis, ten sequential Brewer ramps (Greens, Blues, Oranges, YlOrRd, PuBuGn, Purples, GnBu, YlGn, YlOrBr, Greys) and three diverging ones (RdYlBu, BrBG, Spectral). Each variable opens on a default: a variable whose name or label reads as a nutrient (TN, P, K, Ca, Mg, Fe, Mn, Cu, Zn) on a ramp of its own, a variable whose category is *Environmental Data*, *Terrain Data*, *Landsat Data*, *Sentinel Data* or *Merged Data* on Viridis, any other on YlOrRd. No default is diverging: a diverging scale puts its middle colour halfway between the surface's lowest and highest values, so choose one only where that point means something.
- **A palette you pick belongs to its variable.** Before the first run the picker styles the variable selected in the sidebar. Once a map is displayed it styles that map's variable, and when the sidebar already names another variable for the next run, the pick applies to that one too, so the next run opens in the palette the picker shows. Each variable keeps the palette last picked for it through later runs, Continuous / Binned / Agronomical switches, archive restores and new uploads with the same column names, and **Save config** stores it. The picker is hidden under Agronomical styling, which draws its classes in its own class colours.
- Styling can be changed before or after generating the interpolation models. Switching between Continuous and Binned, changing the palette, or moving between a surface and its SE or variance view in the View dropdown restyles the displayed maps **in place**: the base map, zoom level and overlays stay put. A pulse bar at the top of the page and spinners on the statistics tables show when the app is working.
- The **basemap dropdown** on the Map Viewer toolbar (Satellite (Esri), Topographic, Standard Street, Dark Matter (key), Light / Positron (key)) swaps the imagery under the interpolated surface without redrawing the map: the surface, the overlays, the zoom level and the pan position all stay where they were. **Satellite (Esri)** is the default here and on the Data Setup mini-map.
    * The last two entries, **Dark Matter (key)** and **Light / Positron (key)**, come from CARTO, which requires a free API key for them. Selecting either opens a **CARTO API key** box beside the dropdown; paste your key there (request one at carto.com/basemaps/apikey) and the map reloads with it. Without a key the tiles still draw, but CARTO stamps an "API key required" watermark across them. The key is used only to request tiles for the current session: it is not saved into a run configuration, an export or the run history, so re-enter it after restarting the app. The other three basemaps need no key.
- A variogram warning banner on the Map Viewer describes only fits used by the displayed run. Tuning another locality or preparing the next run does not change that banner; IDW and TPS maps have no variogram-fit banner. Under RK and RFK, a locality whose trend fell back to Ordinary Kriging holds the variogram of the measured values and is described as under OK. The banner carries one band per condition, and each asks for something different:
    * **Variogram fit failed** (red): there was nothing to fit (fewer than five lags, or a variable with the same value everywhere) and a default spherical model was used, so the map's spatial structure was not estimated from your data. The predictions are kept, but no standard error or variance is reported for that locality and surface (Scientific Guide Section 7.4). Treat the surface as indicative and look for the cause in the Run Warnings card on the Scientific Analysis tab.
    * **No spatial structure detected in the variogram** (amber, OK): no model fits the empirical variogram better than a flat line, so the map is the sample mean. The band gives the number of point pairs per lag. This is a model selection, not a significance test: it misses structure more easily with few pairs per lag, so it does not show that no structure exists. IDW and TPS, or a model compared in **Manual Tuning**, are the options. Under RK and RFK the band reads **No residual spatial structure detected by the variogram fit**: the map is the trend plus the mean residual, and the residuals may still carry structure the fit cannot detect. If a Matérn at a zero nugget was the only structured fit, the band reads **Pure nugget used** instead and says so: there a structured model did fit better, but auto-fit does not select it.
    * **Nugget not identified** (amber): several fits with different nuggets, each with its own range, describe the binned empirical variogram equally well, usually because only one lag lies inside the range. These are numerically equivalent fits under the fitting criterion, not a confidence interval. The band names the locality and the nugget's interval; the middle of the interval is used, and Structural Dependency is shown as an interval. More samples at short separations, or replicate samples, would identify it.
    * **Variogram range not resolved within the empirical lag window** (amber): the fit's range falls outside the distances your empirical lags can resolve. *Practical range extends beyond sampled lag support* means the sill is extrapolated past the observed spatial support. *Practical range is below sampled-distance resolution* means it is shorter than the shortest distance the lags resolve (1/100 of the longest lag), so the model behaves almost as a pure nugget. *Range at the search limit* means the fit kept improving up to 10 times the longest lag, where the search stops, so the range shown is a bound, not an estimate. The map is still the best available description of the data; what is limited is what may be read off the model. A wider survey extent addresses the first, denser short-range sampling the second.
    * **Sill not observed; possible large-scale trend** (amber, OK): the empirical variogram of the measured values is still climbing at the cutoff. This can mean long-range dependence or non-stationarity, and the variogram alone cannot separate them. The band notes that modelling the trend with covariates and kriging the residuals addresses the trend case.
    * **Residual variogram still rising at the lag cutoff** (amber, RK and RFK): the same diagnostic read on the residuals of the fitted trend, so the trend model has not removed the large-scale structure and the kriging variance is unreliable at long separations. The variogram cannot say which cause is acting: covariates that do not carry the large-scale variation, a trend form that cannot express the relationship, or a correlation length exceeding the locality's sampled extent, which no covariate or trend model can fix. Review the trend diagnostics and the **Internal Residual Variogram** for that locality on the Scientific Analysis tab. Predictions near sample points depend less on the range and sill.
    * **Gaussian or Matérn model with a nugget below 5% of the sill** (amber): predictions can land far outside the observed range. Check the map against the data or add a nugget.
- **Structural Dependency can read "Not reliably identified."** The percentage is derived from the fitted sill, and where the model reaches that sill beyond the longest lag your samples cover, the sill was never observed. The cell then says so and carries the model-extrapolated figure on hover; the Practical Range cell is qualified the same way. Where your data do not fix the nugget, the cell gives the interval of values that fit equally well, for example "Not reliably identified (70.2 to 100%)", and the Practical Range cell gives its interval on hover. The interval holds fits the criterion cannot tell apart, not a confidence interval, and a value shown without an interval is not thereby precisely known. The exported sheet keeps the number and adds `Max Lag`, `Sill Resolved`, `Nugget Identified`, the structural-dependency and practical-range intervals and `Range At Search Limit`, so a reader can see which rows are supported. They are blank for a model you applied by hand. The sheet's `Fit Status` column says what each row is (fitted, range unresolved, pure nugget, variogram fit failed, applied manual model, or no usable variance, whose parameters are left blank).
- **Hollow map points carry no measured value.** The sampling-point overlay shows every point of the displayed run, and a point whose measured value is missing contributes no measured target to the fit. Its covariates or uploaded prediction can still be used by the models that need them (Scientific Guide Section 1.7). Those points render as an open grey outline with no fill, they are named in the point legend, and their pop-up says so. The count of points on the map can therefore exceed the *n* the Model Performance table reports.
- Choose a classification method:
    * **Continuous:** best for raw gradients.
    * **Binned (5):** splits each surface's value range into five equal-interval bands. Applies immediately.
    * **Agronomical:** class-based management zoning. Selecting it reveals the **Algorithm** picker (Supervised thresholds, Jenks or K-means; Jenks 1967; Lloyd 1982), the **Classes** slider (2 to 5, default 3), and for Supervised the limit boxes with a hint showing the value range of each surface of the run. Nothing recomputes while you adjust them. Press **Apply to maps and statistics** to commit: the maps restyle and the class-area and classification-performance tables recompute in one pass, which takes a few seconds, longer for multi-locality or comparison views. An amber note appears whenever the staged settings differ from what the maps show.
        * **Where the Supervised limits start.** For a recognised nutrient at three classes (total N, Olsen P, NH₄OAc K, Ca and Mg, DTPA Fe, Mn, Cu and Zn), the boxes open on published Low / Moderate / High limits, and the note under them names the extraction method, unit and source; the Fe, Mn, Cu and Zn limits are the local limits of Çokuysal & Erbaş (2004) on the DTPA test of Lindsay & Norvell (1978). The nutrient is read from the column name: `Fe`, `fe_dtpa`, `Iron` and `Fe (mg/kg)` are all iron, `TotalNitrogen` is total N, and a name naming two nutrients, such as `Ca/Mg ratio`, names neither. They are offered only when the variable's unit matches theirs or no unit is recorded, and the note says which. Otherwise, and at any other class count, the boxes open on quantiles of the Actual surface's mapped area (of the measured values before a run), which are not agronomic limits. A class includes its lower limit. Check the limits against your own extraction method before relying on them. Scientific Guide Section 9.2.
        * **Applied limits belong to their variable.** Limits applied for one variable classify that variable's maps only: after a run of another variable its maps stay unclassified, with the amber note, until you apply limits for it. While the variable and the class count stay the same, the boxes keep the values you typed or applied, also after a new run.
        * **Each surface has its own classes.** Jenks, K-Means and Binned breaks are computed from the values of the surface they classify: the Actual map from the Actual surface, the Predicted map from the Predicted surface, whichever map is on screen. Each map's legend and each Area Coverage table therefore describe their own surface, and every Area Coverage table lists the range of each class. A run that maps only the measured values computes only the Actual surface's classes. Tick **Match Scales** to classify both surfaces with one set of breaks computed from the two together. Supervised limits are the same numbers for both surfaces.
        * **Breaks count ground area, not cells.** Jenks and K-Means breaks, and the Supervised quantile defaults, weight each cell by the ground it covers, so a locality gridded at 15 m does not outweigh one gridded at 90 m because it has 36 times as many cells. Scientific Guide Section 2.6.
        * Jenks breaks are the exact natural breaks over every cell of the surface, the grouping that makes the classes as internally uniform as possible. K-Means pursues the same goal by repeated reassignment from seeded starting centres, and can settle on a slightly different grouping. Both are reproducible: re-applying the same settings gives the same class limits. Above roughly 500,000 cells the interactive viewer shows a resampled preview; exports, GeoTIFFs and all area and classification statistics always use the full-resolution raster.
        * Applying the agronomical classification enables the **Agronomical Classes** setting of the *Classification Performance (Uploaded Predictions)* table in the Scientific Analysis section. That table bins each measured value and its uploaded prediction with the Actual surface's classes; its other setting, **Quartiles**, bins observed and predicted values into quartiles and needs no map classification at all. Applying also registers the class-area and classification-performance tables for export, for both surfaces and every locality of the run; re-applying different class limits replaces those sheets rather than adding a second set. The exported class-area sheets carry each class's range and its lower and upper bounds as numbers.

## Finalizing & The Export Registry

The Export Registry standardizes outputs for reports and presentations.

- Open the export styler for individual downloads after choosing a single result, or select several results for a batch download.
- All tabular results selected are written into a single `.xlsx` file with one sheet per table, named after its locality and table. Every statistic is written as a full-precision number: the cards round for reading, the sheets do not.
- **File names say which run a file came from:** `Export_<item>_<method>_<timestamp>` for a single download and `Batch_<item>_<method>_<timestamp>` inside a batch zip, where the item names the locality for a per-locality result. Exported map figures are titled with the variable, the product and the method (for example *Total N - Actual Map - Ordinary Kriging*), their legend names the variable and its unit, and a classified map's legend lists every class, including one no cell of the map falls in. The two ML-prediction error maps carry no method: they are interpolated with a fixed IDW power, whatever engine the run used.
- **Clear Session Registry** empties the export list of the run on screen, after a confirmation. The maps and tables stay on screen and archived runs keep their own items; apart from a Quick export of the map on screen, only a new run fills the list again. Clearing it does not discard the run: the next run still asks whether to archive it.
- **Combined area totals require disjoint locality domains.** If locality boundaries overlap by more than 0.5 m² or share populated cells on the same grid, the table explains why no combined total is reported. Use the per-locality area tables; the unavailable total is omitted from exports.
- **The registry holds every table the Scientific Analysis tab shows.** Per locality: descriptive statistics (actual and predicted side by side), prediction performance, classification agreement, model CV metrics (actual and predicted), fold-realization stability where repeated CV was used, class-area coverage for both surfaces, the empirical variogram points, the fitted variogram parameters, the TPS GCV curve or the IDW power profile of a run that selected them, the CV Distance Match figure with its distance percentiles for each surface, the RF importance table with every importance measure the forest recorded, and the RK coefficient table with its fit statistics. For the run as a whole: pooled CV metrics for both targets, pooled fold-realization stability, the fitted variogram parameters of every locality in one sheet, the IDW power / TPS lambda listing, total descriptive statistics, total prediction performance, total classification performance, and total class-area coverage for both surfaces. Each is the table its card shows, with the same labels; the CV metrics sheet adds the fold plan, the cross-validation population and its ID, the expected and predicted sample counts and Moran's E[I] as columns.
- Class-area and classification-agreement sheets follow the map classification: Binned styling adds the class-area sheets as soon as it is selected, Agronomical adds them, and the agreement sheets with them, when you press **Apply to maps and statistics**, and changing the classification or switching to Continuous replaces or removes them, so an export never mixes two classifications.
- **Variogram Parameters** reports the range parameter *a* and the **practical range**, the distance at which a spherical model reaches its plateau, or another family completes about 95% of its rise above the nugget. Compare localities on the practical range: *a* means a different distance for each model family (about 3*a* for an exponential, *a* for a spherical). A Matérn model shows its smoothness beside the model name. For RK and RFK the card and its exports are **Residual Variogram Parameters**, the variograms of the trend residuals those engines krige; where a locality's trend model was not fitted, the Ordinary Kriging fallback kriged the measured values, and the *Variogram Of* column (a note under a single locality's table) says so.
- **Download Run Configuration (.json)** writes a machine-readable record of the run currently in the registry, at full precision. Keep it beside the exported maps: it lets you reproduce a surface later and supplies the parameter list a methods section needs. It always describes the **current** run, so download it before starting the next one, or restore an archived run first. It is a record, not a setup: **Load config** refuses it and reads only the session configuration that **Save config** writes. It holds:
    * every model setting: method, localities, view, the Input Data and Target Mapping CRSs, boundary and resolution logic, the cross-validation strategy and population, the per-fold refit and covariate screen, the variogram fitting mode, the Actual/Predicted sharing choice, the resolved collinearity rule, original covariate IDs and labels, manual exclusions and effective candidates per locality, and the method's own parameters. The completed record separates constant and automatic VIF removals from final retained covariates per locality and surface, and records CK collocation exclusions;
    * the per-locality values the run consumed: an IDW run's map and fold powers with the CV power profile, a TPS run's fitted lambdas with effective df, GCV curve and any exact-interpolation comparison;
    * the software provenance: app version, R version and platform, and the versions of sf, gstat, fields, randomForest, terra, spdep, FNN, Ckmeans.1d.dp, concaveman and units.
- **Run History Archive.** When a run starts while results are on screen, a dialog asks whether to archive or discard them (tick *Remember my choice* to stop being asked). Up to three runs are kept, the oldest dropped first with a notification. **Remove** deletes an archived run, after a confirmation. **Restore** puts an archived run back as a whole: its maps, the Scientific Analysis tables and plots, its run log and warnings, the configuration panels and the export registry all describe that run again, and the run on screen goes into the archive in its place. A restore is refused while a run is in progress. A cancelled run is never archived.

**1. Colour accessibility and error maps**
   - In the export styler's **Advanced** tab, under **Publication Modifiers**, tick **High Contrast Palette (Colorblind Safe)** for colourblind compliance.
   - Residual and error maps use a zero-centered diverging palette selectable under **Residual / Error Maps** in the Basic tab (default Red-Blue). With the high-contrast option on, a non-colourblind-safe choice is replaced automatically by Purple-Orange.
   - Two error-map assets are registered per run with uploaded predictions: the **Point Error Map** (discrete errors at the exact sample locations, matching the Map Viewer's Point Residuals panel) and the **Interpolated Point Errors Map** (the IDW surface of those errors).

IDW and TPS have no prediction-variance model, so a run using either has no uncertainty item and no uncertainty band in its GeoTIFF. A kriging surface on which no locality's variogram could be estimated (a failed fit, or values the same everywhere up to rounding) has none either, and such a locality is left out of the uncertainty GeoTIFFs of a surface whose other localities have a variance.

   - Advanced options give individual size and orientation control over every figure element, and the configuration can be saved for future sessions.

Nothing is cropped: if an axis label is crowded or clipped in the preview it will be crowded or clipped in the file, so widen the figure, shrink the type, or angle the labels until the preview looks right.
   - **Legend placement follows the item.** An Actual vs Predicted comparison opens with a horizontal legend beneath its two panels; every other item opens with the legend on the right. A position you set by hand lasts until the styler closes, and a configuration loaded with **Load Config** overrides the default.

**3. DPI configuration**
   - Set **Export DPI** under **Output Quality** (72 to 600, default 300): 72 for quick sharing, 300 for internal reports and printing, 600 for journal submission.
   - DPI changes the pixel count only. Layout, type size and margins are identical at 72, 300 and 600 DPI.

**4. Download**
   - Select the format (`PNG`, `TIFF (image)`, `PDF`, `JPEG`, or `GeoTIFF (data)`) and click **Finalize & Download**.

**5. GeoTIFF: the data rather than a picture of it**
   - **GeoTIFF (data)** appears in the format list only for registry items that are a single raster surface: the Actual and Predicted maps, the residual Delta map, the Interpolated Point Errors map, the variance and standard-error surfaces (kriging runs only), and any Quick Export of those views. It writes the raster values, CRS and extent of the surface as the run produced it, in the run's Target Mapping CRS, ready for QGIS or ArcGIS. A run whose localities share one lattice (Fixed or Auto (Global) resolution in a projected Target Mapping CRS), have non-overlapping boundaries and share no populated cells is written as one file holding every locality; otherwise the download is a zip with one GeoTIFF per locality, each at its own cell size, named and tagged with its locality. The Run Log's *[Grid]* line says which layout applies. Exported figures, likewise, draw every computed cell; only the styler's on-screen preview draws about one cell per pixel.
   - **Each band carries its real statistics** (minimum, maximum, mean, standard deviation and the share of cells with a value), which GIS software reads for its default stretch, and the file names its run in metadata tags: `MONOLITH_VARIABLE`, `MONOLITH_UNIT`, `MONOLITH_PRODUCT`, `MONOLITH_METHOD`, `MONOLITH_LOCALITY`, `MONOLITH_RUN_ID`, `MONOLITH_APP_VERSION`, `MONOLITH_TARGET_CRS` and `MONOLITH_CREATED` (a tag with no value, such as a unit the variable list does not give, is left out). Both are stored inside the `.tif`; no `.aux.xml` sidecar is needed. QGIS lists them under *Layer Properties > Information*, and `gdalinfo` prints them. If a GDAL build cannot write them, the file is still written with its values, and a notification and the Run Log say the tags are missing.
   - Because it carries values rather than a rendering of them, **no styling applies**: typography, palette, DPI, dimensions and the preview all switch off while it is selected. Symbolise the layer in your GIS instead. **Kriging** surfaces are written as multi-band files, band 1 the prediction (`var1.pred`) and band 2 the variance (`var1.var`), with layer names kept as band descriptions; a standard-error export is a single band named `var1.se`. Band 2 has no data over a locality whose variogram could not be estimated, and a file in which no locality has a variance is written with band 1 only. **IDW and TPS** surfaces are single-band prediction rasters, since neither engine produces a variance.
   - Two map items are **not** single rasters and stay image-only: the **Actual vs Predicted Comparison** (a pair of surfaces) and the **Point Error Map** (point geometry). The styler says so when one is selected. Export the Actual and Predicted maps separately for the first; for vector geometry use **Class zones** and **Drawn polygons** in the Map Viewer's Downloads menu.
   - In a batch export, GeoTIFF applies to every raster item selected, with per-locality files written into the batch zip directly; anything else in the same batch is written as PNG. Tables are merged into the single Excel workbook; a table that cannot be written is left out and named in the Run Log, and the rest of the batch still downloads.

## Classification Suite

The Classification tab trains a supervised multiclass classifier from co-sampled covariates, either on an existing categorical column or on a continuous variable binned into ordered classes (quantile, equal-interval or Jenks breaks). Method details: Scientific Guide Section 10.

The suite is self-contained: everything a classification run needs (target, predictors, localities, boundary, buffer, grid resolution) is set in its own left-hand panel, independent of the interpolation configuration.

**Setup**
- The **Target** selector opens on *Bin a continuous variable*: pick the variable, the **Number of classes** (2 to 6, default 4) and the **Break style** (Quantile, Equal interval or Natural (Jenks)). Switch to *Categorical column* to classify a text or factor column. Data or label updates keep the selected target while that column remains eligible.
- Choose a method (Multinomial Logistic Regression, Random Forest, or Extreme Gradient Boosting / XGBoost; Venables & Ripley 2002; Wright & Ziegler 2017; Chen & Guestrin 2016). Random Forest is the default. For two-class targets the multinomial option automatically fits the statistically equivalent binomial logistic regression.
- Only text and factor columns are offered as categorical targets. Numeric columns are always treated as continuous, even when they carry few distinct values. If your classes are stored as numeric codes, recode them to text or use the binned-target mode.
- **Balance classes (inverse-frequency weights):** when rare classes matter (100 "healthy" against 5 "diseased"), tick this so each class contributes equally to the fit instead of the model defaulting to the majority. Metrics stay unweighted; expect slightly lower overall accuracy in exchange for better rare-class recall. Not supported by the multinomial learner, which then fits unweighted and says so in the run badge. *Tip: weighting is a stopgap, not new information. The real fix for a 5-sample class is more field samples.*
- **Cross-validation:** Spatial (blocked), the default, clusters nearby points into folds, so the reported accuracy reflects prediction away from the sampled clusters, into unsampled areas. kNNDM (map-matched) forms folds whose held-out points are about as far from their training points as the prediction grid is from the samples: the Standard folds when the samples cover the scope evenly, spatially grouped folds when they are clustered or the scope reaches beyond them. Below 30 points it uses the Standard folds without a search, and the badge names the folds it chose. Standard (random k-fold) estimates accuracy within the sampled area; with a clustered sample it overstates accuracy in the gaps between clusters (Scientific Guide Section 10.2). Its folds are class-stratified. Each fold kriges the covariates at its held-out points from its own training points (and from scoped points that are not scored), as the map kriges them onto the grid, so the reported metrics validate the map task even when **Predict maps** is off. This extra kriging can lengthen runs, especially with many covariates or folds.
- **Covariates and collinearity guardrail:** choose **Spatial Scope** first, then **Covariates** below **Cross-validation**; the covariate check appears beneath the picker. It checks all locations in that scope together and names the covariates Auto-Drop would remove, in removal order. **Review covariates** opens the same VIF chart as the interpolation check, for the whole scope, with categorical covariates listed apart: tick covariates, then **Apply removals and recheck**, which updates the Covariates picker for the whole scope; **Reset removals** restores them. Keep at least one candidate in this dialog. To use categorical spatial 1-NN, cancel and empty the picker explicitly; binned continuous targets require covariates. **Continue with remaining covariates**, offered when the recheck is clean, runs as Run does for a clean selection; **Auto-Drop remaining** repeats the screen in every training split; **Keep remaining** skips it. Large checks show **Checking covariates**; press Run again after the result is ready. On narrow windows, setup and results stack vertically. The VIF threshold is 10, or 5 for **Random Forest**. Correlated covariates can change importance rankings. Removing one can also change predictions. Data, scope, mapping or learner changes invalidate the answer; label edits update the displayed names.
  - **What Auto-Drop does:** the screen runs again on the training rows of every cross-validation fold and tuning resample, so the reported accuracy includes the screening step, and once more on all rows for the final model, whose covariates the map and the downloadable model use. Out-of-fold importance scores a covariate only on the folds that kept it, and one no fold kept has no bar in the importance chart. The run summary says how many folds dropped each covariate; this can differ from the dialog's list, which screens the scoped data before the run.
- **Hyperparameter tuning:** None fits fixed defaults (fast, deterministic); Light and Full search a grid over the folds. The search uses whichever cross-validation strategy you picked, for the scored folds *and* for the final model behind the maps and the exported bundle, so a Spatial CV run tunes under spatial folds throughout.
- **Use nested CV (slower):** appears once tuning is enabled. By default the same folds both choose and score the hyperparameters, which is mildly optimistic; nested CV instead re-runs the grid search inside every fold, on 5 inner folds built from that fold's training rows only, so the reported metrics include the tuning step (Varma & Simon 2006; Cawley & Talbot 2010). Expect roughly 5x the tuning runtime, and the badge then shows "(nested CV)". *Tip: use it for the run you intend to report or publish; the quick estimate is fine while exploring.*
- **Feature importance scored on:** choose whether permutation importance is measured **Out-of-fold** (default) or on **Training rows**. Out-of-fold reuses each fold's own model and shuffles predictors only in the rows that fold never saw, so importance is measured under the same design as the reported accuracy. Training-row scoring is the conventional default but rewards a flexible model for memorising its training data. The design in force is written on the importance plot's axis and into the exported metrics CSV. Switching this control does not change the reported performance: accuracy, kappa, the confusion matrix and the per-class table come out identical either way. *Tip: the two designs are not comparable numbers, so do not read an out-of-fold importance against a training-row one.*
- **One sample is one sampled location.** Rows at the same location are merged before the target is built, as in every spatial model (Data Setup, Step 2): a binned target bins the location's average, with the class breaks computed over the locations, and a categorical target takes the location's most frequent class. Where two classes tie for most frequent, the location is left out, and a warning at launch counts these locations; a text covariate that ties the same way leaves its location out of training. If the rows at a location are depth intervals or repeat surveys, classify one interval or survey at a time from a file holding only its rows.
- If the scoped data are thin (fewer than 20 complete locations, or a class with fewer than 3), the run warns, naming which classes have fewer than 3 samples and their counts, but still proceeds. Results for those classes will be unreliable: widen the scope, merge or exclude rare classes, or use fewer classes for a binned target.
- A warning also appears when a covariate surface could not be kriged; that surface then comes from inverse distance weighting (p = 2, 12 nearest samples). The warning names the covariate and where it happened: on the prediction grid, and in how many cross-validation folds. The same warning names a covariate whose variogram showed no spatial structure (a pure nugget): its surface is its sample mean, so the classifier cannot vary with it on the map. The run summary repeats both.
- A second warning can appear when the run finishes, naming classes that **some cross-validation fold had no training samples of**. This is normal with Spatial (blocked) CV, and with kNNDM where it chose spatial folds, whose folds are geographic groups and cannot be balanced by class: a class confined to one part of the area ends up wholly inside one block, and the model trained without that block cannot predict it. Those samples count as errors. The run is still valid; read the per-class table with the warning in mind. To avoid it, use fewer classes, prefer quantile over equal-interval breaks (equal-interval bins can be nearly empty on a skewed variable), switch to Standard CV if an in-domain estimate is what you want, or widen the scope.
- Binned targets can produce an interval containing no samples at all, most often with equal-interval or Jenks breaks on a skewed variable. Empty classes are dropped automatically, so the class count behind the maps and tables can be lower than the "Number of classes" slider. The run summary always reports how many classes were actually modelled.
- **Predict maps** additionally predicts class, per-class probability and uncertainty (entropy) surfaces on a grid. Boundary type, buffer logic and grid resolution are set in the suite's own **Spatial Scope** panel. If a fixed resolution is too coarse for a small scope, so that no grid cell lands inside the boundary, the run stops with a message. Reduce the resolution or widen the scope.
- **Run progress and cancellation:** the running panel shows a progress bar captioned with the stage running (for example cross-validation fold *k* of *n*, or interpolating covariates onto the grid).
  - *First run of a session:* the caption reads "Starting (loading modelling libraries, first run ~30s)" while the background process loads them; later runs in the same session start almost immediately. The rest of the app stays usable meanwhile, though it may respond slowly.
- The **Cancel Run** button usually takes effect within a few seconds; a tuning grid search or a single covariate's kriging must finish first. A cancelled run keeps no partial results, and the previous run's results stay on screen.

**Spatial Scope**
- The **Localities** picker restricts the run (training, cross-validation, binning breaks and the predicted maps) to the chosen localities. It starts with all localities selected and is never changed by the sidebar's Context section. Leaving it empty means all localities.
- **Boundary Type / Buffer Logic / Grid Resolution** live in this panel and apply to classification maps only: Concave hull (default), Convex hull, Buffered (with dynamic or fixed buffer distance), or Point buffer, applied per locality in scope. The grid is either Auto, a cell size of √(boundary area ÷ 50,000) m, about 50,000 cells inside the boundary, kept between 5 and 1,000 m (a 2 km² scope gets about 6.3 m cells, a 100 km² scope about 44.7 m), or a Fixed cell size of 5 to 500 m. A cell is mapped when its centre lies inside the boundary.
- **A very fine cell size over a wide scope is coarsened.** If covering the bounding box of the whole scope, far larger than the mapped area when the selected localities sit far apart, would need more than 4 million cells, the run enlarges the cell size to the smallest that fits. The live scope note states the cell size the run will use in either mode ("Grid: Auto, 6.32 m cells"), and gives the reason when it was enlarged; an enlarged Fixed size is repeated as a notification when the run finishes. The mapped area is unchanged; only the cell size is.
- Once at least one polygon exists, drawn with the map toolbar or uploaded as a shapefile, a **Polygon scope** control appears: *Ignore polygons*, *Within localities* (points must lie inside both the selected localities and a polygon), or *Polygons only* (the locality filter is ignored).
- The live scope note shows exactly what the run will use: "In scope: x of y georeferenced points", or, where samples share a location, "In scope: n locations from x of y georeferenced points; k locations held more than one sample and were merged". It turns red below 20 locations. Under Point buffer it is joined by a warning whenever the buffer is narrower than half a cell diagonal (**resolution ÷ 1.41**), which leaves isolated samples with no mapped cell beneath them; the finished run repeats it as a notification. It stays silent under *Polygons only*, where the domain is your polygons and the Boundary Type setting has no effect.
- The predicted maps cover the union of per-locality boundaries, or the polygons, so the classifier does not predict across unsampled gaps between distant localities.
- **Classification maps are always drawn in a metric projection.** If your Target Mapping CRS is geographic (WGS 84, degrees), the run is computed and mapped in the WGS 84 UTM zone your data falls in, and the scope note says which one; the maps, rasters and exports then carry that projection. A metric Target Mapping CRS is used as chosen if it passes the suitability gate; a non-metre projected target or a red suitability verdict is refused.

**Results**
- The results panel is a 2 x 2 plot grid: Predicted Class Map and Prediction Uncertainty (normalised Shannon entropy; Shannon 1948) on top, Class Probability Map and Feature Importance below, with a **CV Distance Match** card beneath them: the distance from the prediction grid to the samples against the distance at which the cross-validation predicted, read as in the Spatial Engine's panel (section 1.b), with the Standard folds as the reference and its own PNG download. Below the grid, a **Results table** dropdown switches between the tables (Model performance metrics first, then Confusion matrix, Per-class accuracy, Covariate lift vs baselines, Performance by area, and Class area coverage). Options that do not apply to the run are absent from the dropdown; the CSV export always contains the full metric set regardless.
- **Click any map**, or the expand icon in its card header, to open it full-size at higher display resolution. The Feature Importance plot has the same control, which is the easiest way to read long covariate names. Three default-off **map display options** sit above the maps, beside the run badge: *Scale bar & north arrow*, *Show sample points* (the scoped training samples as white circles, useful for judging where the map is supported by data and where it extrapolates), and *Stretch colour scale*. All three apply to the on-screen maps, the expanded views and the styled PNG exports, and never alter the exported data rasters.
- **Reading a flat-looking map.** The entropy and probability maps are drawn on the absolute 0-1 scale, so the per-class probability maps are comparable with each other and entropy is comparable between runs. A model with little skill keeps every probability near 1 / (number of classes) and every entropy near 1, and that narrow field renders as a single flat colour. Each map's subtitle states its observed range, and *Stretch colour scale* rescales the colours to that range to reveal the structure inside it (at the cost of comparability). The Predicted Class Map's subtitle reports how many of the modelled classes actually appear on the map and the share of cells taken by the largest one; the legend lists the classes present. One class covering the whole grid is the expected output of a model with no skill, so check Overall accuracy against the no-information rate in Covariate Lift, and Cohen's kappa, before reading anything into the pattern.
- **Model Performance** reports pooled cross-validated metrics with plain-language names: Overall accuracy, Cohen's kappa (Cohen 1960), Balanced accuracy, Precision / Recall / F1 (macro averages), ROC AUC (multiclass, Hand & Till 2001), Log loss, and Brier score (Brier 1950). The Estimator column states how each metric extends to the multiclass case, including the denominator a macro average was taken over (*Macro average (K = 3)*) or, for a two-class run, which class counts as the event. Precision, recall and F1 are averaged over **every** class present in the target: a class the model never predicts scores 0 rather than dropping out of the average. The blue badge states the CV design, the scope, the number of locations used for fitting and CV, whether tuning was nested, and whether class weights were applied. Locations with a missing target or a missing selected covariate are excluded from that count; a run without covariates excludes locations with a missing target. The run summary under the results repeats the scope's location count and how many locations were merged.
- **Per-class Accuracy** lists the reference and predicted counts with producer accuracy (recall) and user accuracy (precision) per class. A class the model never assigned reads **no predictions** in the user-accuracy column, and the run summary under the results names it. The confusion matrix and class area coverage in hectares are their own dropdown entries. Class areas are true ground (ellipsoidal) hectares, the same basis the interpolation Area Coverage table and the class-zone export use, so re-measuring a class in a GIS on the flat map plane will differ by roughly a tenth of a percent.
- **Feature Importance** shows permutation importance (Breiman 2001; Fisher et al. 2019): how much the model's log-loss worsens when one covariate is shuffled, with each bar's share of the total in percent. Correlated covariates can change the ranking. A near-zero or negative bar shows no measured predictive contribution under this permutation test; a covariate no fold retained has no bar.
- **Covariate Lift** benchmarks the model against two no-covariate baselines on the same CV folds: always-predict-the-majority-class (the no-information rate, with an info icon for the interpretation), and a spatial-only nearest-neighbour classifier. It states the accuracy difference in points and reads McNemar's test (McNemar 1947) for you: no significant difference, significantly more accurate, or significantly less accurate than spatial position alone. When the covariate model is significantly less accurate, the note points to the alternative: for a binned target, interpolate the continuous variable in the Spatial Engine and classify that surface; for a categorical target, switch the maps to *Spatial 1-NN*. Under Standard (random k-fold) CV it also reminds you that random folds favour the 1-NN baseline, so re-check under spatial blocked CV. *Tip: if the lift is not significant your covariates add little beyond spatial position, and the map may look plausible while the covariates do no real work.*
- **Running without covariates (categorical targets only).** Leave *Covariates* empty and run: the classifier is then the spatial 1-NN assignment itself. You get its cross-validated metrics (class metrics only, no ROC AUC / log-loss / Brier), confusion matrix, per-class accuracy, per-area table, a *Majority-class baseline* table in place of Covariate Lift, and the 1-NN map with its class-area table and Class GeoTIFF. The method, tuning, class-weight and importance settings do not apply; there is no Feature Importance panel and no model download. A binned target still needs at least one covariate: without covariates, interpolate the continuous variable in the Spatial Engine and classify that surface.
- **Spatial 1-NN map (categorical targets only).** A *Maps show* switch above the maps selects the *Covariate model* or *Spatial 1-NN (no covariates)*, which gives every cell the class of its nearest sample. Its accuracy is the *Spatial baseline (1-NN)* row of Covariate Lift. It has hard classes only, so the entropy and probability panels show a notice, the confidence threshold is hidden, and the probability/entropy GeoTIFF downloads are hidden. The class-area table (captioned with the surface), the Class GeoTIFF download (`predicted_class_nn.zip`) and the Styled Maps PNG follow the selection. Each new run resets the switch to the covariate model.
- **Performance by Area**, shown when the scope spans multiple localities or polygons in polygons-only mode, splits the same out-of-fold predictions per area: n, Overall accuracy, Cohen's kappa, Balanced accuracy, macro F1 and **Classes (K)**, plus a Total row matching the headline metrics. An area's macro F1 is averaged over the classes that area actually holds, which is why K is printed per row: two areas' F1 scores are not necessarily over the same class set. NA appears where a metric is undefined for an area, and small-n areas deserve caution.
- **Confidence threshold (abstain below):** a slider above the maps, beside the probability-class picker. Cells whose best class probability falls below the threshold turn grey ("Unclassified") instead of receiving a weak guess. The map, area table and class GeoTIFF update instantly with no re-run, and a note reports how many validation points would survive the threshold and how accurate the survivors are. *Tips: values at or below 1/(number of classes) can never trigger; 0.5 is a sensible start for 3+ classes; treat the grey cells as your next field-sampling plan.*

**Exports**
- **Class GeoTIFF + legend (.zip):** `predicted_class.zip` holds three files: `predicted_class.tif`, the class raster with the map's colour palette embedded, so it opens coloured in QGIS, ArcGIS and most image viewers; `predicted_class.tif.aux.xml`, where GDAL keeps the class names, so GIS software shows each code's class when the two files sit side by side; and `predicted_class_legend.csv`, the `ID,class` table that names the codes on its own. Keep the `.tif` and `.aux.xml` together when you move them. Honours the current confidence threshold.
- **Probabilities / Entropy GeoTIFF:** full-precision floating-point *data* rasters (values 0-1), never masked by the threshold. Like the interpolation GeoTIFFs, each band stores its real statistics and the file carries `MONOLITH_*` tags naming the target, the product, the method, the run and the app version. Generic image viewers show single-band float data in grayscale, so load them in GIS software and apply a colour ramp, or use the styled export below.
- **Styled Maps (PNG):** a zip of publication-style renders (300 DPI) of the class, entropy and currently selected probability maps, with projected coordinate axes in metres (takes around 10-15 seconds to export high cell-count figures, after the click). The grid is drawn cell for cell up to 400,000 cells over the map's bounding box; a larger grid is thinned to that count for the picture only (the GeoTIFFs keep every cell). Each page is 7 in tall and 9 in wide plus the Northing labels. The scale bar, north arrow and sample-point options are honoured as toggled.
- **Metrics CSV:** every result table of the run in one file, with both the display name and the yardstick metric id per row, and a `scope` column separating the sections: the pooled metrics, the per-area rows, the baseline comparison (spatial baseline, majority class, covariate lift, McNemar p), the permutation importances, the **per-class block** (producer and user accuracy with the reference and predicted counts, marked *no predictions* where the model assigned a class to nothing), the **confusion matrix** cell by cell with its orientation written into each row's label, and the **class areas** of the surface on screen, named with the confidence threshold in force.
- **Download Model (.rds):** saves the trained workflow and run metadata. Reuse it in an R session with compatible package versions: `b <- readRDS(file); predict(b$workflow, new_data, type = "prob")`. `new_data` needs the columns listed in `b$predictors`, and preprocessing replays automatically. The metadata records original candidates, manual exclusions, effective candidates and snapshot labels separately from shared-screen VIF/constant removals and the final workflow inputs. It also lists the zero-variance terms removed by preprocessing and the terms fitted by the learner; a raw column can remain required by the workflow even when preprocessing removes its terms. `b$screened_out` / `b$vif_threshold` record automatic screening. Keep the bundle beside the app version; engine versions may affect compatibility.
